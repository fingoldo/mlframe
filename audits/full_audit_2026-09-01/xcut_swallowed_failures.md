# xcut_swallowed_failures
Handlers examined: 2359 broad handlers triaged mechanically, 47 read in surrounding context | files: 2445 scanned, 38 read

## Summary
A whole-tree sweep of `src/mlframe/` found 2359 handlers matching `except Exception` / `except BaseException` / bare `except:` / wide tuples (`contextlib.suppress` is not used anywhere in the package). 504 of those already log at `warning` or above, or re-raise, and are audible by this cluster's standard. Of the remaining 1855, a targeted pass for *completely* unlogged bodies returned only 8, and every one is genuinely inert (temp-file cleanup + re-raise in `training/io.py:171`, `composite/cache_store.py:595`, `wrappers/rfecv/__init__.py:677`, `_key_bank.py:270`; exception-holder plumbing in `_joblib_safe.py:185`; registry rollback in `feature_handling/registry.py:281`; raise-preserving in `training/phases.py:269`; a narrowed KeyError/ColumnNotFound re-raise in `_recipe_poly_cluster.py:55`). The zero-logging form of this defect class has already been swept out of the tree.

The live form that remains is the one the brief calls out explicitly: a handler that changes a RESULT, a BACKEND or a CODE PATH and logs it only at `logger.debug`, behind an `except Exception` broad enough to also swallow a genuine bug in the code it guards. I judged roughly 1530 of the 1855 debug-only handlers inert (cosmetic defaults, chart-title wrapping, teardown, observability scalars nobody branches on, probes whose fallback is provably the same value, and blocks that re-raise or record into an error dict the caller surfaces). The 26 findings below are handlers whose surrounding code I read and judged materially result- or backend-changing. Two sub-patterns dominate: (a) process-wide cached downgrades, where a probe writes a module global on `except Exception` so one transient fault at startup pins the whole process to a slower or different path for its lifetime (the `_select_mi_backend` exemplar, still present in ~14 places); and (b) fail-open statistical gates, where a significance / redundancy / uplift probe substitutes precisely the value that makes the gate pass, so an estimator crash silently widens the selected feature set.

## Findings

### XCUT_SWALLOWED_FAILURES-1 [P0] process-wide-cached-downgrade
**File:** src/mlframe/feature_selection/filters/_kernel_tuning.py :93
**Summary:** Any non-ImportError failure constructing the `KernelTuningCache` singleton permanently sets `_CACHE_SINGLETON = False`, disabling every per-hardware kernel-tuning lookup in the entire `filters` package for the process lifetime, logged only at debug.
**Failure scenario:** `ImportError` already has its own branch at :89, so this second, broader handler can only fire on a non-absence fault: a corrupt or half-written tuning JSON, a Windows file lock held by a concurrent mlframe process (this repo routinely runs several), a disk error, or a genuine bug inside `KernelTuningCache.__init__`. The sentinel is checked first thing at :78, so no caller ever retries. Every downstream `get_or_tune` / `choose` site then falls to its hardcoded source-default heuristic: `_usability_njit_pool.py:728`, `_mi_prange_kernel.py:198`, `_gpu_resident_pair_mi.py:211`, `_wavelet_basis_fe.py:296`, `hermite_fe/_hermite_oracle.py:35`, `_orth_dedup.py:230`, `_pairs_dispatch.py:259`. That is exactly the hardcoded threshold the project convention forbids; on a host whose measured crossover differs from the default it is a whole-run slowdown with no trace above debug.
**Suggested fix:** narrow to nothing new (the ImportError branch at :89 is already the genuine "pyutilz absent" case); make :93 log at warning naming `type(_exc).__name__` and the JSON path, and do NOT latch -- leave `_CACHE_SINGLETON = None` so a transient lock or disk fault is retried instead of poisoning the process.
**Evidence:** read `_kernel_tuning.py:40-109`, including the `is False` short-circuit at :78 and `_reset_for_tests` at :103, which exists only because the latch is otherwise permanent.

**Disposition:** RESOLVED. Bounded retry (`_MAX_INIT_ATTEMPTS = 3`) plus a `logger.warning`, so one corrupt read no longer latches the singleton off for the process. `tests/test_meta/test_transient_faults_do_not_latch_a_downgrade.py`.

### XCUT_SWALLOWED_FAILURES-2 [P1] fail-open-statistical-gate
**File:** src/mlframe/feature_selection/filters/_mrmr_fit_impl/_finalise.py :227
**Summary:** When the permutation-significance probe raises, `_p_value = 0.0` is substituted, which makes the very next line's gate (`if _p_value >= _signif_alpha: continue`) unconditionally pass, so a broken estimator admits every pure-noise candidate into the rescued support.
**Failure scenario:** `_mi_direct_fb` runs 32 permutations per candidate inside the rescue loop. A dtype mismatch on `_q_dtype`, a numba typing failure on a degenerate column, or a transient device fault raises; the handler substitutes p = 0.0, i.e. maximally significant. The comment at :229 frames this as "fall back to the magnitude-only decision (keep)" -- but the gate exists, per its own :309-320 rationale, precisely because coarse-binned plug-in MI is upward-biased so magnitude alone re-injects noise. The caller gets a `support_` padded with noise columns and no warning. The loop scans up to `max(_rescue_cap*4, 16)` candidates, so a systematic estimator failure flips every one of them.
**Suggested fix:** narrow to the estimator's real raises (`ValueError`, `TypeError`, `numba.TypingError`), log at warning naming the exception type and the column index, and substitute the fail-CLOSED value (`_p_value = 1.0`, drop-on-uncertainty) -- matching the convention the sibling `_pairs_core.py:1001` block already adopted for exactly this reason.
**Evidence:** read `_finalise.py:210-250`, including the `_scan_limit` bound and the gate one line after the handler.

**Disposition:** RESOLVED. Fail-closed: the substituted p-value is 1.0 (drop on uncertainty) and the handler logs at warning naming the exception and the column. Verified behaviourally that a raising probe now yields the same support as a genuinely insignificant verdict. `tests/test_meta/test_gates_fail_closed_and_probes_do_not_latch.py`.

### XCUT_SWALLOWED_FAILURES-4 [P1] process-wide-cached-downgrade
**File:** src/mlframe/training/cb/_cb_pool.py :638
**Summary:** A transient failure of the one-shot CatBoost GPU probe fit permanently pins `_CB_GPU_USABLE_CACHE = False`, so every CatBoost model in the process trains on CPU, logged only at debug.
**Failure scenario:** The docstring's stated intent is narrow -- detect a CPU-only CatBoost wheel, which raises `CatBoostError: Environment for task type [GPU] not found`. But `except Exception` equally catches a GPU OOM caused by a concurrent mlframe process (this repo's CLAUDE.md documents running with as little as 1.25 GB free on a 4 GB card), a WDDM TDR reset, or a driver hiccup. The probe runs once under `_GPU_PROBE_LOCK` and the cache is consulted at :607, so there is no retry: one 4-second window of GPU contention at startup costs the whole training suite its GPU CatBoost path. The genuine absence cases are already short-circuited before the try (`_cached_gpu_info()` at :614, `CUDA_VISIBLE_DEVICES` at :625), so this handler guards only the real-fit failure.
**Suggested fix:** catch `catboost.CatBoostError` and match the "Environment for task type [GPU] not found" signature -- that alone should latch False. Any other exception should log at warning naming type and message and leave `_CB_GPU_USABLE_CACHE = None` so the next caller re-probes.
**Evidence:** read `_cb_pool.py:592-652`, including the double-checked lock and both pre-try short-circuits.

**Disposition:** RESOLVED. Only the `Environment for task type [GPU] not found` signature latches `_CB_GPU_USABLE_CACHE = False`; anything else warns and leaves the cache unresolved so the next caller re-probes. Same test file.

### XCUT_SWALLOWED_FAILURES-5 [P1] process-wide-cached-downgrade
**File:** src/mlframe/feature_selection/filters/_internals.py :72
**Summary:** `numba_cuda_can_compile()` latches `_NUMBA_CUDA_CAN_COMPILE = False` for the process on any exception from a probe kernel launch, debug-only, routing every numba.cuda-capable filter to cupy/CPU for the rest of the run.
**Failure scenario:** The docstring names the intended cause precisely -- `NvvmSupportError` from a toolkit/compute-capability mismatch, a genuine permanent property of the host. But `except Exception` equally catches a transient `CudaAPIError` or OOM at `_cuda.to_device` when another process holds VRAM. That single moment permanently downgrades the process, and there is no reset hook. The same shape appears in `feature_selection/filters/_fe_gpu_strict.py:181` and `:186` (`_CUDA_USABLE_CACHE`) and in `training/_gpu_probe.py:18` and `:21`, where module-level `CUDA_IS_AVAILABLE` is resolved at IMPORT time and then gates `XGB_GPU_AVAILABLE` / `LGB_GPU_AVAILABLE` at :61-62 for the entire process.
**Suggested fix:** at each site catch `numba.cuda.cudadrv.error.NvvmSupportError`, `CudaSupportError` and `ImportError` (the real permanent-absence cases) and latch only on those; log anything else at warning naming the type and leave the cache unset so it is re-probed.
**Evidence:** read `_internals.py:39-77` (probe body, latch, no reset path) and all of `training/_gpu_probe.py:1-73` -- the latter's module comment states "degrades silently to CPU-only mode", i.e. the defect written down as a design.

**Disposition:** RESOLVED at both sites. `_internals.numba_cuda_can_compile` latches only on `NvvmSupportError` / `CudaSupportError` / `ImportError`; `_fe_gpu_strict._cuda_usable` latches only on `ImportError`. Everything else warns and leaves the cache unset. `training/_gpu_probe.py` was already corrected in the P0 pass. Same test file.

### XCUT_SWALLOWED_FAILURES-6 [P1] wrong-objective-from-empty-params
**File:** src/mlframe/training/_training_loop.py :110
**Summary:** When `model.get_param()` / `get_params()` raises, `params = {}` is substituted; the next check (`_existing = params.get("loss_function")`) then concludes the user set no loss, so the function overwrites a user-supplied CatBoost objective with `MultiRMSE`.
**Failure scenario:** A CatBoost version whose `get_param` signature drifted, or a partially-initialised model, raises here. The substituted empty dict does not mean "no loss configured", it means "unknown"; collapsing the two makes `_ensure_cb_mtr_loss` call `model.set_params(loss_function="MultiRMSE", eval_metric="MultiRMSE")` over whatever the caller deliberately chose. The model then trains against the wrong objective and every metric downstream is honestly computed on a wrongly-trained model. Identical shape at :164 in `_ensure_cb_multilabel_loss` (overwrites with `MultiLogloss` / `HammingLoss`). The sibling handler at :186 in the same file already logs at warning and spells out its consequence, so the correct pattern exists in the file and simply was not applied here.
**Suggested fix:** narrow to `AttributeError` / `TypeError`, log at warning naming the exception, and return early (leave the objective alone) rather than substituting `{}` -- "params unknown" must never be collapsed into "params empty".
**Evidence:** read `_training_loop.py:100-210`, using the audible :186 handler as the in-file reference.

**Disposition:** RESOLVED at both call sites. `_ensure_cb_mtr_loss` and `_ensure_cb_multilabel_loss` now return early on a failing `get_param`, logging at warning, instead of collapsing "params unknown" into "params empty" and overwriting a user-chosen objective. Same test file.

### XCUT_SWALLOWED_FAILURES-11 [P2] rng-state-divergence
**File:** src/mlframe/feature_selection/filters/_binned_numeric_agg_fe.py :896
**Summary:** The GPU permutation-null batch draws `_n_perm` permutations from `_rng` BEFORE the call that can fail; the host fallback then draws `_n_perm` MORE from the now-advanced generator, so a GPU failure silently changes the null ceiling and therefore the keep/reject verdict.

### XCUT_SWALLOWED_FAILURES-18 [P2] silent-estimator-substitution
**File:** src/mlframe/feature_selection/filters/_group_distance_fe.py :173
**Summary:** When `scipy.stats.wasserstein_distance` raises, a 101-point quantile-grid approximation is substituted, producing DIFFERENT feature values rather than a slower route to the same values, logged at debug.
**Failure scenario:** The numba path is gated out at :163, so this handler runs on hosts without numba.
