# Audit report: reporting_core

**Cluster:** reporting_core
**Scope:** `src/mlframe/reporting/spec.py`, `output.py`, `colors.py`, `catalog.py`, `__init__.py`, `auto_dispatch.py`, `diagnostics_dispatch.py`, `_diagnostics_dispatch_extra.py`, `report_html.py`, `_risk_coverage_diagnostic.py`, `_benchmarks/**`
**Out of scope:** `reporting/charts/**` and `reporting/renderers/**`; `src/mlframe/training/reporting/**` was read only where needed to confirm how this cluster's outputs are consumed.

**LOC reviewed:** 3,398 (`wc -l`: 3,197 for the ten modules + 201 for `_benchmarks/`)

## Summary by dimension

1. **Correctness bugs:** 3 confirmed silent-wrong-output bugs, all verified by running the real code: the `DIAG_MAX_FEATURES` column cap silently no-ops on polars frames (`hasattr(frame, "loc")` gate); `_flat_scalar_metrics` silently drops `np.float32` / `np.int64` metrics from the model-comparison leaderboard (those numpy scalars are not `float`/`int` subclasses); `_save_figure` reports "chart failed" for the merely-not-requested-format case, poisoning the `charts["failed"]` accounting a run can assert on. No P0/P1 — nothing corrupts a persisted numeric artifact or ships a wrong metric value; the drops are omissions and the accounting bug is observability.
2. **Computational efficiency:** one material finding — the error-analysis and slice-finder entry points row-subset the frame BEFORE capping columns, so a wide frame materialises up to `DIAG_ROW_CAP` x ALL columns instead of x 200. No O(n^2) patterns; the heavy numeric work lives in the out-of-scope builders and this layer is genuinely O(builders) as its docstring claims. Two micro-redundancies (a duplicate `_select_feature_columns` call, a discarded probe predict) noted as P3.
3. **Architecture and clarity:** module boundaries are sound and the mutual-import cycle between `diagnostics_dispatch` and `_diagnostics_dispatch_extra` is handled correctly (lazy delegates + module `__getattr__`, reasoning documented). `diagnostics_dispatch.py` at 892 LOC and `_diagnostics_dispatch_extra.py` at 711 LOC are both past the 800-900 "carve now" line in CLAUDE.md. `auto_dispatch.py` repeats the same 12-line render/dpi/save block five times. `catalog.py`'s standalone-diagnostics list has drifted badly from what the dispatchers ship.
4. **Informativeness / consumer value:** the largest yield. Eight rendered diagnostics are recorded as saved but never get a `_record_path`, so they are invisible to the combined HTML report a DS actually opens; the combined report itself flattens every chart into one section named `charts` with raw filename labels and no captions, discarding `report_html`'s own section/description/caption machinery; the catalogue that is supposed to be the discoverability surface omits roughly sixteen shipped diagnostics.
5. **UI/UX:** `report_html` emits `alt=""` on every chart image, collapses all but the first section (sidebar anchors land on a closed `<details>`), applies a per-file base64 threshold with no cumulative page-size budget, and embeds plotly fragments verbatim so N fragments can each carry their own plotly.js. Backend parity: `_save_figure`-based diagnostics (decile table, 2-D PDP) are matplotlib-only and the combined report is matplotlib-PNG-only, so a `plotly[html]`-only operator loses them with no clear signal. `LINE_PALETTE` cycles at 20 with no linestyle variation.
6. **Edge cases and robustness:** the no-crash contract is respected everywhere; degenerate inputs are guarded consistently (`m == 0`, single-class, fewer than 2 members/splits/models). Gaps: the emphasis selector derives its base rate from `count_nonzero` (silent no-op for non-0/1 encodings); `render_target_acf_diagnostic` silently skips when timestamps are shorter than the target; the frozen spec dataclasses document field co-requirements that nothing enforces.
7. **Test coverage:** `tests/reporting/` is broad and healthy (22 tests on `report_html`, dedicated files for colors / catalog / output DSL / auto-dispatch / dispatch helpers). Real gaps: no polars case for the column cap, no numpy-scalar case for the metric flattener, no test that every chart recorded as saved is reachable from the combined report, no completeness test for the standalone-diagnostics catalogue, no enforcement test for the spec dataclass invariants.
8. **OSS hygiene:** a date stamp in `output.py`, finding IDs (`INV-58`, `R-3 / INV-11`) in docstrings, `iter71`/`iter83` wave markers in benchmark filenames and docstrings, refactor-history narration in `_diagnostics_dispatch_extra.py`. On `--`: it is used pervasively and deliberately as the ASCII em-dash substitute here (the catalogue even has ASCII-only tests), so it is treated as house convention rather than flagged per occurrence; `output.py`'s real em dashes and set-membership symbol are the inconsistency worth reporting.

## Narrative detail

**REPORTING_CORE-1 (polars column cap no-op).** `_select_feature_columns` reads `if hasattr(frame, "loc") and not isinstance(frame, np.ndarray): try: return frame[keep], keep`. Polars DataFrames expose neither `.loc` nor `.iloc` — confirmed directly (`hasattr(pl.DataFrame({'a':[1]}), 'loc')` prints `False`) — so the capping branch is skipped and the function returns the FULL name list. The agent then ran the real helper on both formats: a 5-column polars frame with `cap=2` returned shape `(3, 5)` and all five names, while the identical pandas frame returned `(3, 2)` and two names. The consequence matches exactly what the constant exists to prevent ("a pathological thousands-of-columns engineered frame would blow the dense matrix up"). Ironically the row-subset helper directly above (`_subset_rows`) DOES handle polars via its `frame[idx]` fallback, so the polars path reaches the builders — just uncapped.

**REPORTING_CORE-2 (numpy scalar metrics dropped).** The filter is `isinstance(v, (int, float)) and not isinstance(v, bool)`. On this platform `isinstance(np.float32(1), float)` is `False` and `isinstance(np.int64(1), int)` is `False` (only `np.float64` inherits from `float`) — verified, printing `False True False False` for float32/float64/int64/bool_. Running the real function on `{'roc_auc': np.float32(0.9), 'n': np.int64(5), 'brier': np.float64(0.1), 'ok': 0.5}` returned `{'brier': 0.1, 'ok': 0.5}`: the float32 AUC and int64 count vanished with no warning. This feeds the multi-model leaderboard, so a metric bar is simply missing for some models depending on which library produced the number (LightGBM/XGBoost commonly emit float32). P2 rather than P1 because no value is shown WRONG — it is omitted — but the omission is invisible to the reader.

**REPORTING_CORE-3 (not-requested recorded as failed).** `_save_figure` opens with `if "png" not in (plot_outputs or "").lower(): return False`, and both call sites do `ok = _save_figure(...); _record(charts, name, ok)`. Under `plotly[html]`, `charts["failed"]` therefore gains `decile_table` (and `pdp_2d`) on every report though nothing failed. The module docstring advertises this accounting as the thing "a run can assert chart presence" with, so a suite-level alert on non-empty `failed` fires spuriously for every plotly-only user. The same code path is why those two diagnostics have no plotly equivalent at all — they are matplotlib `Figure` builders, not `FigureSpec` builders — which is the backend-parity half of finding 6.

**REPORTING_CORE-4 (eight charts missing from the combined report).** The consumer was traced first: `training/reporting/_reporting_diagnostics.py:462-466` reads `paths = metrics.get("charts", {}).get("paths", [])` and passes it as `chart_paths` to `build_combined_html_report`. The training tree was also grepped for those base suffixes with no compensating append found. **REPORTING_CORE-5 (subset-then-cap ordering).** Both `render_split_error_diagnostics:199` and `render_slice_finder_diagnostic:617` read `_select_feature_columns(_subset_rows(df, idx), feature_names, DIAG_MAX_FEATURES)`. `_subset_rows` fancy-indexes the frame, which for pandas `.iloc[idx]` and polars `frame[idx]` alike materialises a NEW frame containing every column; only afterwards are columns narrowed to 200 — at the documented cap that is 100,000 rows x all columns where 100,000 x 200 would do, in the module whose docstring says "Every entry point pulls column views (never a whole-frame copy)". Column selection is the cheap operation for both formats, so swapping the calls preserves behaviour exactly. Related: line 211 calls `_select_feature_columns(df, feature_names, DIAG_MAX_FEATURES)[0]` a second time for the `n <= DIAG_ROW_CAP` worst-K branch, recomputing what line 199 already computed.

**REPORTING_CORE-7 (catalogue drift).** `catalog.py`'s docstring explains the anti-drift design for panel TOKENS: they come from each chart module's `ALLOWED_*_PANEL_TOKENS` frozenset "so a token added to a chart without a description here surfaces immediately". `_STANDALONE_DIAGNOSTICS` is by contrast a hand-written list of 13 tuples with no such backstop; cross-checking it against the `render_*_diagnostic` functions defined in the two dispatch modules leaves roughly sixteen shipped diagnostics unlisted. `tests/reporting/test_catalog.py::test_standalone_diagnostics_listed_and_described` only checks that listed entries have descriptions — there is no check in the other direction, which is exactly why the drift went unnoticed.

**REPORTING_CORE-8 (combined report loses its own structure).** `report_html.build_combined_report` supports sections, per-section descriptions and per-chart captions, and `tests/reporting/test_report_html.py` covers all three. The only production caller passes `("charts", os.path.basename(p), png)` for every entry and no `section_descriptions`, so the page has a single section named "charts" and headings that are raw artifact filenames. The capability is built, tested, then not used by the one path that matters. The fix is cheap because `catalog.standalone_diagnostics()` already holds one-line descriptions keyed by exactly the suffixes these paths end with — a second reason to fix finding 7.

**REPORTING_CORE-11 (emphasis base rate from count_nonzero).** `select_binary_emphasis_panels` computes `n_pos = int(np.count_nonzero(finite))` then bails when `n_pos == 0 or n_pos == n`. For `{-1,+1}` or `{1,2}` encodings every value is nonzero, so `n_pos == n` and the function returns `requested_panels` unchanged — the data-aware emphasis silently does nothing, with no log line, on precisely the encodings where a reader would still want PR-over-ROC under skew. A quiet no-op rather than a wrong chart (hence P3), but the caller cannot distinguish "balanced, no reorder" from "encoding not understood".

**REPORTING_CORE-16 (collapsed sections vs anchor navigation).** `is_open = " open" if idx == 0 else ""` renders sections 2..N closed, while the sidebar emits `href="#{anchor}"` links into panels inside them. Flagging the alternative reading explicitly: recent Chrome and Firefox auto-expand a `<details>` on fragment navigation, so on an up-to-date browser the links work. What fails regardless of browser is printing and PDF export (collapsed content does not print) and older browsers — hence P3 with a print-stylesheet fix rather than a functional-bug claim.
