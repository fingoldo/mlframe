### Diagnosis of the open leak-test failure (not fixed)

In `run_final_subsumption_prune` the linear guard `_without_linearly_useful` judges `grppct(x0|grp)` with `linear_oos_gain`: t = -0.32, share of variance -8e-6, so it stays dropped. Taking the nested half `grptabin(x0|grp)` (an anchor that the transform does not return) out of the reference set changes nothing (t = -0.27). The reason is that the surviving compound `add(sin(cat_a), log(grptabin(x0|grp)))` contains the target-aware bin index, which was fitted on the same training rows the guard splits into even and odd halves: in-sample it carries the target almost fully, so the guard sees no gain for `grppct`; on the held-out rows the compound reads at AUC 0.5966 while the pure percentile-rank column reads at 0.861. The guard cannot see this because its gain is measured on rows the bins were fitted on. A fix needs the guard (or the target-aware bin index) to be evaluated out of fold, for example by scoring the anchors' linear usability on rows the target-aware bins did not see; not done here.

## Is the CPU under-use a thread cap? (checked)

numba runs the TBB threading layer with 8 threads (`NUMBA_NUM_THREADS` 8) on this host, which is safe for parallel kernels launched from several Python threads at once; no code in the fit path calls `numba.set_num_threads` or lowers the pool. `MLFRAME_EDGE_JOBS` only sizes the Python-side edge pools (default: the logical core count). So the 33 percent CPU mean is not a configured thread cap: it comes from the serial Python stretches and the small kernels between the parallel regions.

## Device Wasserstein-1 for the group-distance family: tried, slower, not shipped (w1_gpu_ab.py, 100000 rows, GTX 1050 Ti)

Every group's values are a subset of the column's finite values, so W1 of group g against the column is the sum over the column's sorted breakpoints of |cumulative share of g - cumulative share of the column| times the gap to the next value; with a one-hot cumulative count per group that is plain cupy (cumsum, abs, a weighted sum), chunked over groups to bound the (groups x rows) matrix. It matches the numba path to 2e-16 to 3e-15, so the formulation is right, but it is slower: 5 groups 4.1 ms against 2.5 ms on the host, 20 groups 6.3 against 3.3, 60 groups 13.5 against 6.2, 300 groups 56.0 against 23.7 (transfers included, float64 on a card with a 1/32 double rate, O(groups x rows) work against the host's near-linear merge). The host W1 is 2.5 to 24 ms per (group, numeric) pair, so it was never the cost of the family; the family's wall is the sorts and the per-pair Python around them, which the radix changes above already cut. No device kernel for this family.

The log of the slow fit has 8 device out-of-memory lines, e.g. `Out of memory allocating 406,400,000 bytes (allocated so far: 868,041,728 bytes, limit set to: 1,062,696,041 bytes)` in `_radix_select_interior_edges` and 275 MB in the null-max, each followed by the fallback to the exact CPU percentile path or to the CPU null-max; the fast concurrent fits (92.7, 104.6 s and the six of `stage_concurrency_ab.py`) have none.

Cause: `_gpu_resident_select._canonical_nan` (added in the merged commit "radix select: a sign-bit NaN is ordered last") was `cp.where(cp.isnan(x), nan, x)`, a full second copy of the candidate block on the device at every call, and each stage's pool limit under concurrency is about 1.06 GB. Fix: one in-place elementwise pass that rewrites NaN payloads to the positive quiet NaN and returns the same array (only the payload of a NaN changes). With it the same fit takes 81.5 s, no out-of-memory line, no CPU fallback, 7.16 million faults, 2.98 cores used on average; test `tests/feature_selection/fe/gpu/test_canonical_nan_in_place.py` (float32 / float64, the returned object is the input) and the 10 radix tests next to it pass.

What this says about the earlier numbers: the 96 to 151 s spread of the same code and the "regression" the user saw were two different things. The spread of identical code on a loaded machine is real (memory 3 to 4 GB free, other processes 1 to 1.2 cores), and a doubling on a quiet machine with device-memory fallbacks in the log is a code regression from a commit that allocated a second copy. A fit whose log has `Out of memory allocating` lines is not comparable with one that has none; `env_sampled_fit.py` plus a count of those lines is the quick check.

## Usability warp kernel, one warp per pair with all forms in one pass: 2.1x slower, reverted (same process, 2026-11-07)

## Host memory at 200k, 500k and 1M rows x 100 columns: peak RSS growth against the frame (rss_scale_fit.py, 2026-11-07)

`rss_scale_fit.py ROWS COLS default` fits a default `MRMR` on a float32 frame and samples the process RSS every 0.2 s, naming the main thread's innermost mlframe frame at each 50 MB step of a new peak (an optional `RSS_TRACEMALLOC=1` takes snapshots of the largest live numpy allocations; numba and device allocations are invisible to it, so the RSS steps are the primary evidence). A guard stops the process when the machine's available memory falls under `RSS_MIN_AVAILABLE_GB`.

Before the changes of this entry: 200k x 100 peak growth 2102 MB (26.3x the 80 MB frame), 500k x 80 4821 MB (30x), 1M x 100 8217 MB (20.5x; wall 299 s). The cost per cell of the frame was about 80 to 120 bytes against 4 for the float32 value itself, so the working set was 20 to 30 copies of the frame. Peak growth at 10M x 80 would have been about 65 GB.

Largest steps found and what was done (each is a pure memory-ordering change; the tests pin equality):
* `_pack_bits` of the honest null built three `(permutations, n)` arrays at once (mask, uint8 copy, padded copy: 1.5 GB for 500 permutations of a million rows): packed block by block.
* the honest null widened the permuted label matrix to int64 (8x): it keeps its own narrow type, and is not copied when the evaluation rows are all rows.
* `build_honest_spec` held the `(n, m)` raw matrix in float64; a float32 frame without NaN now keeps float32 (widening is exact, the quantile edges are still computed in double from the widened sorted column).
* `_njit_null_columns` goes in blocks of columns that fit 192 MB (raw values, NaN flags, codes, int32 sort order, tie flags: about 20 bytes per row and column); each column's null is independent of the others, so the blocks give the single-call values (a test compares a one-column-per-block layout with the single call bit for bit).
* the strict-resident group pre-selection held all candidate columns as float64 (800 MB at 1M x 100) and stacked them again: it scores column blocks of 192 MB in the criterion dtype.
* `dominant_candidate` held the extracted columns, their sanitised copies and the stacked matrix (three frame-sized arrays): blocks of 256 MB beyond that size.
* the family gate's permutation block is narrowed to 192 MB (a fit up to ~190000 rows keeps 256 permutations per block and its permutation stream), and the stacked-group budget counts the bit sets and the transposed copy (3.5 bytes per code instead of 1).
* the degenerate-column audit's dense collinearity matrix is limited to a tenth of the free RAM instead of a fixed 2 GB; beyond it the existing streaming (random projection) pass runs.

## The gate of the group-statistic families (2026-11-08)

`hybrid_grouped_quantile_fe` and `hybrid_group_distance_fe` kept a candidate when `MI(candidate; y) >= 1e-4` and `MI(candidate; y) - MI(source; y) >= 0`. A noise column has a plug-in MI of `(Bx-1)(By-1)/(2n)` (1.5e-4 nats at 30000 rows, 10 bins, a binary target), above the floor, and the sign of its uplift over a noise source is a coin flip; a column that only re-encodes its source has an uplift of zero and passes or fails with the sign of the estimation noise. On a frame without any signal (30000 rows, 6 seeds) `grouped_quantile` returned 8 of 8 possible columns in every seed and `group_distance` 6, 0, 6, 5; the percentile rank of the one informative column inside an irrelevant group passed in 1 seed of 6. The gate now also requires a significant `p_added`: the G-test of `CMI(candidate; y | source)` (`_added_information_gate.py`, chi-square with `occupied source bins * (Bc-1)(By-1)` degrees of freedom, Bonferroni over the candidates scored, `alpha = 0.05`); a table with fewer than five expected rows per cell is not tested and is left to the other gates. Result on the same frames: no column on noise, none for a copy, and when the target depends on the rank of x inside its group the single column `grppct(x0|g1)` in 6 of 6 seeds (it was one of 8, seven of them noise). `grouped_agg` and `composite_group_agg` return nothing on these frames with or without the test (their CMI is conditioned on the raw columns), so they are unchanged. `refit_winners` opens the gate (`alpha` is not passed there, the winners were chosen on the subsample).

## Device twin of the masked Spearman dedup kernel (2026-11-09)

## materialise_and_finalise at 200000 rows (9.9 s against 1.4 s at 100000): the within-stratum shuffle sorts (2026-11-09)

cProfile of `materialise_and_finalise_fe_candidates` at 200000 x 100 (11.0 s with the profiler): cupy `argsort` 2184 calls 2.26 s and `sort` 274 calls 1.88 s (device sorts, each waiting for its kernel), pandas `take` 1255 calls 0.88 s. The sort callers are `_fe_cmi_perm_null_gpu._column_argsort` / `conditional_perm_null_gpu` (79 calls, 2.06 s cumulative: the within-stratum permutation null shuffles a candidate column by sorting random keys per permutation, one 1-D sort per permutation column from 80000 rows) and `_floor_mean_from_nulls_dev` (79 calls, 1.75 s: a device sort of the null vector for its quantile). The number of sorts is nperm x candidates; at 200000 rows each is ~1 ms on this card. Correction on `_floor_mean_from_nulls_dev`: its input is the null vector of `nperm` values (hundreds), a sort of that size takes microseconds, so the 1.75 s attributed to it is the host waiting at the first synchronising call for the null kernels queued before it, not the sort. A selection instead of a sort would save nothing. Levers on the shuffle sorts themselves, none taken: (b) a device Fisher-Yates per stratum would replace the key sorts but changes the random stream (selection-level equivalence only, not bit-identical); (c) the analytic null that `mi_direct` already uses above its row threshold (the nperm -> infinity limit) for this gate too.

Analytic stand-in for the conditional permutation null (experiment only, nothing shipped; `nullcmp.py` in D:/Temp): `conditional_perm_null_gpu` (99 permutations, quantile 0.95) against the chi-square limit of the Miller-Madow-corrected CMI, floor = (chi2.ppf(0.95, df) - df) / (2 n) with df = (Kx-1)(Ky-1)Kz, on independent random codes:

| n | Kx x Ky x Kz | permutation floor | analytic floor | ratio | permutation time |
|---|---|---|---|---|---|
| 20000 | 10 x 2 x 8 | 5.85e-4 | 5.2e-4 | 0.89 | 40 ms |
| 100000 | 10 x 2 x 12 | 1.06e-4 | 1.2e-4 | 1.14 | 97 ms |
| 200000 | 10 x 2 x 20 | 8.72e-5 | 7.5e-5 | 0.86 | 195 ms |
| 200000 | 16 x 3 x 30 | 1.81e-4 | 1.75e-4 | 0.97 | 174 ms |

(The uncorrected chi-square floor df-based, chi2.ppf/(2n), is 4-15x higher than the permutation floor, because the gate scores the bias-corrected CMI whose null mean is near zero.) The corrected analytic floor agrees with the 99-permutation floor within the permutation quantile's own sampling noise (about 15 %), so on dense strata it would be a statistically equivalent replacement that costs nothing and removes the per-permutation sorts. Not shipped: it changes what the gate computes on sparse tables (expected count per cell under 5, where the chi-square limit fails) and every borderline candidate's verdict would move by the sampling noise, so it needs a selection-level check on the planted generators and a sparse-table guard first.

Correction to the analytic-null lever above (found 2026-11-09 while wiring it): the analytic chi-square CMI null already exists and is the first thing the gate tries, `_fe_cmi_redundancy_null._analytic_cmi_null` (floor = chi2.ppf(q, df) / 2n, null mean df / 2n, so the bias-corrected floor is exactly the formula I tested), from n = 20000 rows (`MLFRAME_CMI_ANALYTIC_NULL_MIN_N`) with a sparse-cell guard (average expected count per occupied joint cell at least `_min_expected_cell()`, `MLFRAME_MI_ANALYTIC_NULL_MIN_CELL`). Counted in one 200000 x 100 fit (the stage-scale data): 115 hits and 82 misses of 197 calls; at 200000 rows 37 hits / 71 misses, at 100000 rows 76 hits / 11 misses, no exceptions on the way (debug log). The misses return `None` through the sparse-cell or non-positive-df branch and go to the permutation null (69 `_resident_support_null`, 13 `_conditional_gpu_resident_null` calls), where the chi-square limit is not valid. So there is no new dispatch to add: the permutation sorts left in `materialise_and_finalise` are the sparse-table cases the guard is there for. Why a 200000-row call has more sparse supports than a 100000-row one (the selected-column joint has more occupied cells at the later steps) was not checked.
