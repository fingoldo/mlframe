### Diagnosis of the open leak-test failure (not fixed)

In `run_final_subsumption_prune` the linear guard `_without_linearly_useful` judges `grppct(x0|grp)` with `linear_oos_gain`: t = -0.32, share of variance -8e-6, so it stays dropped. Taking the nested half `grptabin(x0|grp)` (an anchor that the transform does not return) out of the reference set changes nothing (t = -0.27). The reason is that the surviving compound `add(sin(cat_a), log(grptabin(x0|grp)))` contains the target-aware bin index, which was fitted on the same training rows the guard splits into even and odd halves: in-sample it carries the target almost fully, so the guard sees no gain for `grppct`; on the held-out rows the compound reads at AUC 0.5966 while the pure percentile-rank column reads at 0.861. The guard cannot see this because its gain is measured on rows the bins were fitted on. A fix needs the guard (or the target-aware bin index) to be evaluated out of fold, for example by scoring the anchors' linear usability on rows the target-aware bins did not see; not done here.

## Time the threads wait for the GPU (sync_wait.py: `cp.asnumpy` and the runtime synchronizes wrapped, one process, wall 75.4 s)

Seconds spent inside device-to-host copies, summed over all threads: 7.03 s (direct `.get()` calls and the compiled `Stream.synchronize` are not wrappable and are not counted, so the figure is a lower bound). About 10 percent of the wall is spent waiting for the device through these copies; the rest of the wall is host work. By caller: `honest_null_columns_device` 1.51 s in one copy (the wait for `root_split_accept`), `_hermite_fe_mi._plugin_mi_classif_batch_cuda_resident` 1.17 s over 1267 copies (0.9 ms each), `batch_pair_mi_gpu._try_cuda_shared_fused` 0.72 s (one copy, the wait for `pair_mi_shared_fused`), `_triple_mi_scores` 0.37 s, `_lof_transform` 0.34 s, `_tied_on_device` 0.28 s, `_try_gpu_fourier_detect` 0.28 s over 380 copies, `joint_entropy_gpu` 0.20 s over 843 copies. This matches the nsys kernel total (about 14 s GPU time) and the 21 percent GPU utilization: the single-launch kernels `root_split_accept` and `pair_mi_shared_fused` are waited for (2.2 s together), the rest of the GPU work overlaps with host work, so making GPU kernels faster can only shorten the wall by their waited-for part, a few seconds.

The 1267 copies of `_plugin_mi_classif_batch_cuda_resident` (1.17 s) are the calls' own results: each call bins, histograms and scores one candidate batch on the device and returns its host MI vector, so the 0.9 ms per copy is that batch's kernel time being waited for, not transfer overhead. Folding the copies together would not remove it; only fusing the calls' batches would, and the callers choose the next batch from the previous result, so it is not done.

### Correction: the leak-test failure was the test's downstream fit, not the selection

Scored one by one the kept compound `add(sin(cat_a), log(grptabin(x0|grp)))` reads at AUC 0.881 on the training rows and 0.848 on the held-out rows, so it generalizes; the `final_subsumption` verdict that dropped `grppct` was sound. The 0.5966 came from `_downstream_auc` of `test_fe_target_aware_leak_contract.py`, which fitted an unscaled `LogisticRegression(max_iter=400)` on the three kept columns together: one of them (`min(reciproc(grp), exp(tcol))`) is on the scale of exp(x) next to unit-scale ones, the lbfgs fit does not converge and the AUC measures the optimiser. The helper now standardises the columns before the fit (the 0.72 floor and every other assertion are unchanged); all 13 tests of the file pass, the permuted-target null tests included. The two paragraphs above that attribute the failure to the subsumption pass and to the in-sample bins are wrong and are kept only as the record of the diagnosis path.

## Is the CPU under-use a thread cap? (checked)

numba runs the TBB threading layer with 8 threads (`NUMBA_NUM_THREADS` 8) on this host, which is safe for parallel kernels launched from several Python threads at once; no code in the fit path calls `numba.set_num_threads` or lowers the pool. `MLFRAME_EDGE_JOBS` only sizes the Python-side edge pools (default: the logical core count). So the 33 percent CPU mean is not a configured thread cap: it comes from the serial Python stretches and the small kernels between the parallel regions.
