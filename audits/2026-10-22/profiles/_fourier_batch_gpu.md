# `_fourier_batch_gpu` (the Fourier detector over a block of columns) and its backend choice

Measured 2026-11-14, GTX 1050 Ti (sm_61, 112 GB/s, double rate 1:32), 16 columns x 100000 rows (float64 input, 32-point grid, `max_freqs` 6; a tone of frequency 3, 2 or 4.25 on three columns of four, noise on the fourth). Kernel details of the periodogram, gram and deflation kernels: `_orthogonal_univariate_fe.md`.

## What changed in this pass

1. **Host or device by the kernel-tuning cache.** `detect_fourier_freqs_batch` took the device batch whenever the strict-residency flag was on. Measured per call (same lists on both sides), host loop of the single-column detector against the device batch: 4 columns 5000 rows 0.021 / 0.027 s, 20000 rows 0.082 / 0.037, 100000 rows 0.361 / 0.095, 400000 rows 1.188 / 0.223; 16 columns 5000 rows 0.098 / 0.040, 20000 rows 0.318 / 0.076, 100000 rows 1.421 / 0.274, 400000 rows 4.837 / 1.013. The host wins only for a handful of short columns, so the entry `fe_fourier_batch_backend` (`_fourier_detect_batch._SPEC`, axis: median rows of the jobs, sweep on 8 columns) decides, fallback 12000 rows, `MLFRAME_CMI_GPU=1` still forces the device. The sweep was run for real: it picked the device at 5000, 20000 and 100000 rows with `max_abs_diff` 0.0 against the host lists. The host side is `_detect_fourier_freqs_host`, the former body of the single-column detector (its coarse basis and power reductions are `njit(parallel)` kernels), split out so the sweep times the host and not the single-column device route.
2. **Column blocks.** `detect_fourier_freqs_batch_gpu` stacked every column of a group (same train and validation sizes) in one device allocation of about 22 row vectors per column. It now runs the group in column blocks, `_column_block_width(n_rows, n_cols)` halving the width from the whole group until `fe_gpu_has_vram_cushion` admits it (`_BLOCK_COLS` forces a width). A group that fits runs as one block exactly as before; the lists of width 1, width 3 and the whole group are identical (test).

## Host profile (cProfile, one call, 16 columns x 100000 rows, device batch)

0.231 s in total, 8142 function calls. Top by own time: `cupy.std` 0.071 s over 120 calls (it waits for the kernels queued before it, so it carries GPU time), the host-to-device uploads of the stacked splits `cupy.array` 0.042 s (436 calls), `_host_split_for_detect` 0.042 s (16 calls: the sort-free stride split and the partition of the train slice, on the host), `.get()` 0.041 s (280 calls), the group loop itself 0.029 s, `concatenate` 0.027 s. Nothing in the host profile is a per-column Python loop of device calls: the calls per detector iteration are per block.

## Kernel launches per call and GPU profile (nvprof 11.8-style summary, same call)

Launches per call: 38 `periodogram_power_b` (a coarse scan, two refinements and a confirmation per detector iteration, for the whole block at once), 16 `sincos_gram_b`, 16 `apply_deflate_b`, no launch per column. GPU time 349 ms under the profiler: `periodogram_power_b` 65 % (227 ms, 6.0 ms per launch), `sincos_gram_b` 10 %, the cupy standard deviations 7 %, `apply_deflate_b` 5 %, the batched cubic-detrend GEMVs 3.7 %.

`periodogram_power_b` metrics: achieved occupancy 0.28 to 0.54 (the small refinement launches sit low, the coarse scan at 0.54), multiprocessor activity 80 to 99 %, global load efficiency 82 %, device-memory read throughput 1.3 to 28.8 GB/s of 112 (peak at the coarse scan), write throughput 0.03 to 3.0 GB/s. The kernel is bound by the arithmetic around the sine-cosine, not by memory (see `_orthogonal_univariate_fe.md`); the whole-GPU utilization is the multiprocessor activity above, the launch count is small enough that the card is not starved between launches.
