# `_feature_engineering_pairs` (the pair feature-engineering pipeline: 24 `_pairs_*` modules, judged as one unit)

The modules `_pairs_abs_corr_gpu`, `_pairs_analytic_gpu`, `_pairs_chunk_codes`, `_pairs_chunks`, `_pairs_code_bins`, `_pairs_common`, `_pairs_core`, `_pairs_core_helpers`, `_pairs_core_parts`, `_pairs_core_steps`, `_pairs_dispatch`, `_pairs_emit`, `_pairs_emit_extval`, `_pairs_gate_dedupe`, `_pairs_gates`, `_pairs_gpu_gates`, `_pairs_materialise`, `_pairs_operand_floor`, `_pairs_score`, `_pairs_score_helpers`, `_pairs_score_recompute`, `_pairs_score_step4`, `_pairs_score_steps`, `_pairs_setup` are one pipeline split by the file-size ceiling (`CARVED_FAMILIES`): the family has this one record, and each file is covered while it lives in the package and the package meets every point.

Measured 2026-11-14, GTX 1050 Ti (sm_61, 112 GB/s), the profiling fit of `_benchmarks/profiling/_fe_fit_fixture.py` at 100000 rows x 100 columns, strict-resident mode, second (warm) fit. **VRAM conditions:** the card is shared with the desktop (836 MiB held before the fit, about 1.1 GiB free during it, 1024 MiB cushion required by `fe_gpu_has_vram_cushion`), so the pair-adjacent grouped-quantile MI path declined twice for lack of memory (`OutOfMemoryError ... limit set to 414 MB`) and ran its host binner; the figures describe this machine as it is used, not an empty card.

## Host profile (cProfile of the warm fit, 602 s under the profiler)

The pair stage `check_prospective_fe_pairs` is 206 s cumulative of 602 s (34 %), 4 calls. Under it: the per-pair scoring `_score_one_pair` 188.6 s over 1070 calls (step 1 reading the buffer 81 s over 497 to 539 calls, the serialisation point of step 4 22.6 s, the column treatment of step 3 23.3 s with 6.5 s of its own time), and the pair family gate `apply_pair_family_gate_from_state` 53.3 s over 31 calls. Own time by module: `_pairs_abs_corr_gpu` 7.9 s, `_pairs_score_steps` 6.7 s, `_pairs_chunk_codes` 5.1 s, every other module under 1 s. Waits on the device (the `.get()` of the scored vectors) are what the cumulative numbers of step 1 and the family gate mostly are.

## Kernel launches per fit and the GPU profile (nvprof, one warm fit, 100000 x 100, 223 s of GPU time under the profiler)

Launches per fit of the pair-stage kernels, with the share of the fit's GPU time: `fe_materialise_cm` 1734 launches 5.6 %, `analytic_obs_mi_bins_i8` 883 launches 4.6 %, `bin_codes_f32e_int8` 1101 launches 2.7 %, `rows_ent_nnz_i32_split` 551 launches 2.5 %, `gram_scaled` 15568 launches 0.9 %, `pair_mi_perm` 3 launches 0.45 %, `rows_ent_nnz_i32_lut4` 1459 launches 0.12 %, `pack_bins_multi` 17 launches, `abs_corr_tiled` 172 launches, the rest below 0.1 %: about 17 % of the GPU time of the fit is the pair stage. The launch counts are close to the 1070 scored pairs for `analytic_obs_mi_bins_i8` (883) and larger for the materialisation (1734), so the scoring is launch-per-pair-ish rather than one launch per chunk of pairs: the launch count of the pair stage is the open lever (about 4000 launches of the five main kernels per fit), not the kernels themselves.

Kernel metrics (nvprof), `analytic_obs_mi_bins_i8` at 100000 x 1500: achieved occupancy 0.48, multiprocessor activity 96 to 98 %, device-memory read throughput 32 to 45 GB/s of 112, global load efficiency 39 % (the kernel was reworked in `FC11-17`, 1.65 to 1.85x, and reads its int8 matrix four bytes per thread). The two largest pair kernels with their own records: `_batch_pair_mi_cuda_shared_fused.md` (achieved occupancy 0.987, 97 % activity, 99.8 % load efficiency, 37 GB/s) and `_pair_mi_perm_cuda.md` (occupancy 0.56, activity 98 %, bound by shared-memory atomics). The per-kernel throughput of the whole pair stage is therefore latency and atomics bound, not bandwidth bound; the card is not idle inside the kernels.

## Column blocks, backend choice, host twin

The pair chunks are the column blocks (`pair_chunks_by_operand_block`, `operand_block_limit`; `_pairs_chunks`, `_pairs_chunk_codes`), sized from the free VRAM; the device-versus-host choices are the tuner entries of the family (`fe_pair_usability_corr_backend`, the batch pair-MI entry `_BPMI_SPEC`, the analytic gate's thresholds); the host twins are the njit scorers of the same modules.

## Optimisation pass (before / after, same fit and command)

Two changes came out of the profile above (tracker FC11-82 and FC11-83): the split-K row entropy now takes `c * ln(c)` from a lookup table (`rows_ent_nnz_i32_lut_split`: 10.9x, 6.0x and 5.2x on 8 x 2M, 26 x 4M and 8 x 8M cells), and the permutation null builds every contingency table in one launch (`perm_joint_counts`: 14x to 33x). On the whole warm fit (nvprof, GPU seconds, launches): `cupy_scatter_add` 6.80 s (620) gone, `cupy_add__int64_int32_int64` 3.82 s (620) gone, `cupy_add__int64_int64_int64` 3.06 s -> 0.06 s, `cupy_copy__int64_int64` 2.95 s -> 0.28 s, `rows_ent_nnz_i32_split` 5.54 s (551) -> `rows_ent_nnz_i32_lut_split` 2.11 s (460), new `perm_joint_counts` 0.94 s (586): about 17 GPU seconds fewer on a 170 s profile (10 %). The pair kernels `fe_materialise_cm` (12.6 -> 13.0 s, at the bandwidth floor: 12 bytes per cell, 5.4 ms against 7.2 ms measured per launch), `analytic_obs_mi_bins_i8` (10.1 -> 10.4 s, reworked in FC11-17) and `bin_codes_f32e_int8` (6.1 -> 6.2 s, already tiled) were reviewed and left. What remains the largest cost of the fit is the radix select (4284 launches, 83 s, about half of the profile), which this pass did not touch.

## `analytic_obs_mi_bins_i8`: counters and the load-depth experiment (2026-11-14)

nvprof counters, 30000 x 2048 int8 codes, 10 x 2 cells (128-column tile, 1024 threads): achieved occupancy 0.47, global load efficiency 56 %, device-memory read throughput 38 GB/s of the card's ~112, issue slot utilisation 47 %, warp execution efficiency 100 %, issue stalls 70 % data request and 21 % execution dependency, synchronisation 0.5 %. The shared-memory transaction counts per request (530 loads, 7117 stores) come from the atomic adds into the per-column histograms.

Load depth: the loop with four independent loads in flight per thread was rebuilt with 6, 8 and 12 (same outputs, `eq=True` against the shipped kernel): 100000 x 6000 18.79 ms at 4 loads, 18.50 at 6, 20.42 at 8, 22.85 at 12; 30000 x 2048 1.57 / 1.75 / 1.92 / 2.32 ms; 100000 x 1500 x 16 cells 4.04 / 4.18 / 4.70 / 5.50 ms. More loads in flight is slower from six on, so the kernel is no longer latency bound at four: what is left is the rate of shared-memory atomic adds (about 6e8 adds in 18.8 ms at 100000 x 6000, with a four-way bank conflict from the 20-word column stride). Not changed.

Not tried because of the cost: private per-thread histograms without atomics (four times the shared memory at the same tile, or a 32-column tile whose 32-byte row pieces already measured slower than the wide tile) and four-byte code loads (needs the row length to be a multiple of four, which the producer's chunk widths do not guarantee). The kernel is 4.6 % of the GPU time of the fit.
