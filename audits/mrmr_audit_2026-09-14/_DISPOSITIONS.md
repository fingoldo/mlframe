# mrmr_audit_2026-09-14 — implementation dispositions

Every one of the 201 findings gets an explicit disposition. No finding is dropped, deprioritised away, or
silently omitted — including P3/Low, per the owner's instruction to implement all of them.

**Disposition vocabulary**
- **RESOLVED** — fixed in source, covered by a regression test, verified.
- **DOC** — the code is correct; the defect was in a comment/docstring/name, now corrected.
- **FUTURE** — genuinely deferred, with the reason and the concrete next action recorded.
- **REJECTED** — examined and found not to be a defect, with the reason recorded.

Batches are committed as they close (the repo's convention: ~20 fixes per commit, each with its test).

- **NUM-12 severity nuance (recorded, not dropped):** the outer handler already logged at `warning` with

### int_nondense note (IMPL-8, new finding)

Integer target with labels {1, 2, 5}, n=1500, default `MRMR()`. The pre-RO-4 baseline (captured at 00:01 on the tree of `be24033fe`, third of five fits in one
process) did NOT select `x1__relu_gt1.09186`. Every later run selects it with an otherwise identical set: the RO-4 after-fit (same in-process order), all 19
encoder sites swapped back to the legacy cast, a clean `git archive` of HEAD, and a clean `git archive` of `be24033fe` itself, the latter two each in 2 fresh
processes. So RO-4 and `2e15c07ac` are both ruled out: the same source produced a different selection in that one baseline run. Within a process, two back-to-back
fits always agreed. Candidates, none yet confirmed: state that one fit leaves behind for the next in the same process, the on-disk kernel-tuning cache (the logs show
DEFAULT-cache misses that write regions), or a GPU-dispatched kernel.

**FUTURE (open, next wave)** — reproduce by running the baseline's exact five-case sequence repeatedly in fresh processes, and separately with the tuning cache
pinned read-only and with CUDA hidden, to name the source before any fix. A selection that depends on anything besides (X, y, params, seed) is a correctness bug.
