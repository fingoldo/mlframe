# H - Repeated work across FE families (100000 x 100, all_families_wall)

Scope: read-only audit of HEAD 871110e1f, direction H. Evidence is either a tracker row / profile number (cited) or "by reading" (code path confirmed, no timing). Excluded as already decided: MRMR-RADIX-EDGES-CACHE (rejected, address and content keys measured), MRMR-OPAT-FAST, MRMR-SERIES-SELECTION-EQUIVALENCE, MRMR-CUPY-OPS-BY-FUNCTION, MRMR-BIN-FINGERPRINT-FUSED, FC11-70 (repeat count 60 of 875 calls, no lever).

Checked and dropped (false positives or not in the benchmark):
- `_fit_cache.py:47` and `:111` both call `_full_x_content_hash(X)`: the second call is served by the single-entry memo in `_mrmr_fingerprints.py` (`_x_hash_memo_hit`), so the full frame is hashed once per fit.
- `_candidate_pool.raw_column_pool` (per-column codes and MI, 14 callers in `_hybrid_orth_family_variants/_group2..4.py` and `_fe_stage_cascade_early_a.py:417`, `_fe_stage_cascade_mid_b.py:666`): runs only when `fe_shape_pool == "relevant"`; the default is `"all"` (`mrmr/_mrmr_class.py:3026`) and the benchmark does not set it, so it costs nothing in the measured fit.
- `compute_col_edges` (194 calls) and `mdlp_bin_edges` (167 calls): 1 and 0 repeats by content (2026-11-08 profile, `audits/2026-10-22/profiles/stage_sample_100k_gpu_2026_11_05.md:508`). No cache to add.
- Decision-subsample gathers in the cascades: the shared index `_fe_shared_subsample_idx` is already used by every stage that takes `shared_subsample_idx`; the 36 per-family gathers of MR11-15 are no longer in `_mrmr_fit_impl` (grep finds no `iloc[idx]` there).

Total of the five findings below: about 1.2 to 1.6 s of single-thread work, which is roughly 0.8 to 1.1 s of wall after the 0.7 wall-per-isolated-second factor in the findings memo. None of them alone, nor all together, reaches the 30 s goal; direction H is worth a few seconds at most on this fit.

Findings, largest expected saving first.

### F01 - Raw operand matrix re-assembled on the device for every orthogonal GPU build

- **Expected saving**: about 0.5 s of thread time (0.63 s `assemble_resident_matrix` measured single-thread over the 4 `_gpu_build_and_score_univariate` calls of one fit, MR11-16 in `audits/2026-11-09/_TRACKER.md`), about 0.3 to 0.4 s of wall. Evidence: tracker numbers plus by reading that the calls share the raw column list.
- **Location**: `src/mlframe/feature_selection/filters/_orthogonal_univariate_fe/_orth_gpu_resident.py:249` (`_gpu_build_and_score_univariate`) and the raw-matrix block at `_orth_gpu_resident.py:~296-302` (`assemble_resident_matrix(X[raw_cols].to_numpy(dtype=_rm_dt), raw_cols, ("orth_raw_mat", tuple(raw_cols)), dtype=_rm_dt)`); the assembler itself at `src/mlframe/feature_selection/filters/_fe_resident_operands.py:316`. Callers of the build: `_orthogonal_univariate_fe/__init__.py` (the univariate generator, one call per family that asks for the orthogonal basis).
- **Problem**: every build re-runs the per-column resident path (`resident_operand` per column: contiguous copy, `_content_hash_memoized`, lookup) for a raw matrix whose columns and dtype are the same as in the previous build when `raw_cols` is the same list. The result is an identical device array, rebuilt. The memo `_content_hash_memoized` is keyed by object identity, and `X[raw_cols].to_numpy(...)` creates a new host array on each call, so the id memo misses and each column is hashed again.
- **Proposed change**: a fit-scoped memo of the assembled device matrix keyed by `("orth_raw_mat", tuple(raw_cols), dtype.str, n_rows, device id)`, holding the device array only while the fit scope is open (the same scope mechanism as `dedup_collinear_memo_scope` in `_orth_dedup.py`), and freed by the existing cache releaser. Content check on hit: the per-column `_content_hash` of each column (already needed by the assembler), so a key collision cannot return different data. Bounded memory: one `(n, k)` float32 device matrix per fit (400 MB at 100000 x 100 is the worst case, so the memo must be skipped when `_vram_fits` is False). Selection-equivalent: the values are bit-identical to the rebuilt matrix.
- **Risk**: device memory pinned for the whole fit on a 4 GB card, which competes with the concurrent stages (the VRAM-slot limits in the findings memo). Mitigate by releasing it after the last orthogonal build of the stage, or by keeping only the content-hash list, not the array.
- **Disposition**: OPEN

### F02 - Column keys for the orthogonal dedup memo and the basis memo rebuilt from the frame on every call

- **Expected saving**: about 0.7 s of thread time (0.43 s `_dedup_cache_key`, 0.26 s `_basis_memo_key`, MR11-16 single-thread), about 0.4 s of wall. The key is built before the memo lookup, so even a hit pays for it.
- **Location**: `src/mlframe/feature_selection/filters/_orthogonal_univariate_fe/_orth_dedup.py:81-101` (`_dedup_cache_key`, called at `_orth_dedup.py:625` on every dedup call inside a memo scope); `src/mlframe/feature_selection/filters/_orthogonal_univariate_fe/_orth_basis_memo.py:37-62` (`_basis_memo_key`, called from `_orthogonal_univariate_fe/__init__.py:364` on every call of the basis generator, 17 calls and 4 distinct inputs per fit).
- **Problem**: both keys read every candidate column in full (`X[c].to_numpy()`, a dtype cast, and for the basis key a `np.ascontiguousarray` and a full xxh3 pass over the native column), once per call. The same columns are then read again by the family itself. The dedup key casts to the criterion dtype and samples rows; the basis key uses the native dtype and the full column; the two keys therefore hash the same content under two conventions. Within one fit the source columns do not change, so the per-column work is repeated 17 + the dedup call count times.
- **Proposed change**: one fit-scoped per-column fact record keyed by `(column name, source buffer identity via the frame's block, n_rows)` with lazy fields: `native_hash`, `crit_sample_hash`, `crit_f32_array`, `isfinite_all`, `int_as_cat`. The dedup key and the basis key read these fields instead of re-reading the column. Identity key: the pandas block array id plus the weakref guard already used by `_content_hash_memoized`. Bounded memory: the facts are hashes and booleans (about 100 bytes a column); the f32 array is held only inside the scope, at most one copy per column (40 MB at 100000 rows, 100 columns). Selection-equivalent: the hashes are the same functions of the same bytes.
- **Risk**: a column whose block identity changes but whose content does not will miss the memo (a performance miss, never a wrong result). A column mutated in place between calls inside one scope would return stale facts: the fit does not mutate X, but this should be asserted with a test that mutates a column and expects a new key.
- **Disposition**: OPEN

### F03 - Candidate operand preparation (cast, finite and integer-as-category checks) repeated per family

- **Expected saving**: about 0.14 s of thread time (MR11-16, single-thread), about 0.1 s of wall. Small on its own; it is the same column walk as F02 so the two can share one pass.
- **Location**: `src/mlframe/feature_selection/filters/_orthogonal_univariate_fe/_orth_gpu_resident.py:30-47` (`_candidate_operands`, called at `_orth_gpu_resident.py:311`); the same `np.asarray(X[c].to_numpy(), dtype=...)` pattern in `_orthogonal_univariate_fe/_orth_scoring_memo.py:56` (`_col_hash`, f64 cast of the whole column) and `_orth_scoring_memo.py:96` (`_content_hash(col_arr)` per column, per call, on the raw matrix column).
- **Problem**: the same source column is cast, tested for finiteness and integer-as-category, and hashed again by every family that routes through `_gpu_build_and_score_univariate` or the raw-MI baseline. The `_col_hash` at `_orth_scoring_memo.py:56` uses an f64 copy of the column only to make the key dtype-independent, which doubles the cast traffic for the f32 operands the same families already built.
- **Proposed change**: `_candidate_operands` reads the per-column fact record of F02 (`crit_f32_array`, `isfinite_all`, `int_as_cat`) and returns the cached arrays (`np.ascontiguousarray` of a cached array is a no-op). `_col_hash` reads `native_hash` from the same record instead of casting to f64 and hashing again. Key: column name plus block identity, as in F02.
- **Risk**: returned arrays are shared, so a caller that writes into them corrupts the cache. `_candidate_operands` callers only read (verify with grep before relying on it). Same stale-identity risk as F02.
- **Disposition**: OPEN

### F04 - The same raw column content is hashed several times per fit by different callers

- **Expected saving**: up to 0.9 s of thread time in the 2026-11-08 profile (`_content_hash` 8793 calls, 6815 of them repeats of an earlier input, 0.9 s; `audits/2026-10-22/profiles/stage_sample_100k_gpu_2026_11_05.md:508`), about 0.5 s of wall at the best. The repeats are not all removable: the id memo already catches the same array object, so the saving is only the hashes of rebuilt views of the same column.
- **Location**: `src/mlframe/feature_selection/filters/_fe_resident_operands.py:100` (`_content_hash`) and `:144` (`_content_hash_memoized`, id-keyed); unmemoised callers: `_orthogonal_univariate_fe/_orth_scoring_memo.py:56,89,96`, `_orthogonal_univariate_fe/_orth_dedup.py:99`, `_fast_host_ops.py:96`, `_content_memo.py:59`, `_wavelet_basis_fe.py:339`, `_y_encoding.py:111` (the y hash, per call, cheap but repeated per family), and `_qbin_block_gpu.py:151` (memoised).
- **Problem**: the memo is keyed by object identity, so each family's fresh `to_numpy()` / cast view of the same column misses and is hashed again. The owner's policy asks for keys by content or by column number within one fit; the id key is neither for rebuilt views.
- **Proposed change**: a fit-scoped `(column name, dtype.str, n_rows) -> content hash` table, filled by the first caller and read by the others, with the key the column name (column number within the fit's frame) and a cheap strided signature (`_content_array_signature`) as the guard. Memory: one 8-byte hash per column per dtype. Selection-equivalent when the strided guard matches and the full hash is taken on a guard hit only once per fit. Note the guard is not a proof of equality; the full hash must remain the key, and the saving is only the hashing pass of rebuilt views, so measure before building it.
- **Risk**: a hash is only a proof of equality when computed over the full bytes; a column-name key with a strided guard can return a stale hash if a column is changed in place. Keep the full hash on every miss and do not key on the strided signature alone.
- **Disposition**: OPEN

### F05 - The orthogonal families each re-draw and re-gather the decision subsample, bypassing the fit's shared index

- **Expected saving**: by reading, under 0.2 s of wall. Each call draws the same random subsample and copies the frame; the frame copy is 20000 to 50000 rows by 100 columns (about 16 to 40 MB) and costs a few tens of milliseconds, the draw about 5 ms. The gain is small; the reason to fix it is that it bypasses the shared index, which is the policy of `feedback_cache_the_subsample_everywhere`.
- **Location**: `src/mlframe/feature_selection/filters/_orthogonal_univariate_fe/_orth_extra_basis_fe_generate.py:605-611` (`np.random.default_rng(int(subsample_seed)).choice(_full_n, size=..., replace=False)`, then `X.iloc[_sub_idx].reset_index(drop=True)`); `src/mlframe/feature_selection/filters/_orthogonal_univariate_fe/__init__.py:843-850` (the same draw and gather for the orthogonal generator); `_orth_extra_basis_fe_generate.py:265-280` (`_adaptive_cols_by_relevance`, a per-column `np.asarray(X[c].to_numpy())[rows]` for every column, on 50000 rows, repeated per call).
- **Problem**: the two generators compute the identical `_sub_idx` from the same seed and size, each on its own, and each makes its own gathered frame. The shared subsample index that the rest of the FE stages use (`_fe_shared_subsample_idx`) is not consulted here, so these generators can select different rows from the stages they feed. The per-column gather in `_adaptive_cols_by_relevance` is repeated for the same columns on every call.
- **Proposed change**: draw the index through the shared helper (`_subsample_row_index` in `_mrmr_fit_impl/_helpers.py:442`) only when that index is set, and otherwise keep the seed formula so the result is unchanged. Cache the gathered frame keyed by `(id(X), n_rows, subsample_seed, subsample_n)`, bounded to one entry per fit. Selection-equivalence holds only if the chosen rows stay the same: keep the seed formula on the non-shared path, and verify with the selection dump (`fit_dump.py` pattern) before and after.
- **Risk**: switching these two generators to the shared index changes their rows, which changes the selection; this is a behaviour change, not a cache, so it must go through the equivalence check, not be taken as a pure speedup. The cache alone (same seed, same rows) is safe.
- **Disposition**: OPEN
