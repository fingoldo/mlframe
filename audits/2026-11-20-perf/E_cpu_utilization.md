### F01 - Edge-worker share is fixed for a whole wave, so a finished cascade leaves its cores idle

- **Expected saving**: about 1 to 2 s on the 100000 x 100 wall (about 3 to 5 %). Evidence: the stage walls of the two waves end 0.5 to 1.5 s apart (`[9.77, 10.53, 10.03]` and `[6.24, 7.51, 7.74]` s, tracker MRMR-WAVES-BALANCED). For that gap the surviving cascades still run with `8 // 3 = 2` edge workers each while about four logical cores sit idle, and the per-column edge work (MDLP / quantile edges, the largest pool consumer) runs there. Both waves: about 2 x 0.8 s of the last cascade at reduced parallelism. By reading; not measured.
- **Location**: `src/mlframe/feature_selection/filters/_adaptive_nbins.py:696-720` (`_resolve_edge_jobs` reads `_ACTIVE_STAGES[0]` once per call); `src/mlframe/feature_selection/filters/_mrmr_fit_impl/_fe_stage_concurrency.py:219-221` (`concurrent_stages(len(stages))` wraps the whole pool for the wave); `src/mlframe/feature_selection/filters/_edge_pool.py:21-30`.
- **Problem**: `_ACTIVE_STAGES` is the number of cascades of the wave, set when the wave starts and reset only when the whole wave's `with` block exits. `_resolve_edge_jobs` divides the logical core count by that number for every edge call. When one cascade of the wave finishes early, the remaining cascades keep their share of 2 workers instead of growing to the freed cores, for the rest of their stage. The divisor is not the number of cascades still running.
- **Proposed change**: keep a live count of running stages. In `run_stages_concurrently._run` (`_fe_stage_concurrency.py`, where `walls[i]` is written in the `finally`), decrement a lock-protected counter in `_edge_pool` (new helper `stage_finished()`), and have `_resolve_edge_jobs` divide by the live count (min 1). Edge results are written by column index, so the output does not depend on the worker count (the same property the existing code relies on). Selection-equivalent by construction. No change to the scheduler's device slots.
- **Risk**: low. A stage that starts after another has finished still gets the old divisor until its next edge call; the counter must be decremented on the exception path too (put it in the `finally`). Verify with the `stage walls` log that the wave tail shrinks and that edges are equal (`np.array_equal` on the per-column edges of a 20000 x 30 fit).
- **Disposition**: IMPLEMENTED, NEUTRAL 2026-11-20 - `stage_finished()` in `_edge_pool.py` called from the stage worker, `_resolve_edge_jobs` divides by the live count; sensor `test_edge_pool_live_stage_share.py`. Alternating A/B on the 100000 x 100 benchmark (4 pairs, GPU 64-74 C, 1708-1733 MHz): old 41.1 / 39.2 / 39.8 / 39.7 s, new 39.8 / 39.4 / 40.5 / 40.5 s, means 39.95 vs 40.05 s: no measurable gain. Kept (correct by construction, results are folded by column index).

### F02 - The process-wide `_edge_pool` is sized by whichever caller creates it first and then shared by all cascades

- **Expected saving**: 0 s on the benchmark if the pool is already created at 8 workers by the screening stage that runs before the waves (likely, to be checked). If it is first created inside a wave, every MDLP per-column edge call of all three cascades shares a 2-worker FIFO: up to 3 to 5 s of the wave (the edge work of all three stages then runs on 2 threads). This is a latent throughput cap that can silently appear with a different call order.
- **Location**: `src/mlframe/feature_selection/filters/_adaptive_nbins.py:644-663` (`_edge_pool` grows the pool but never shrinks it; the old pool is appended to `_RETIRED_EDGE_POOLS` and not shut down); `_adaptive_nbins.py:818-823` (the one caller that uses the shared pool, `_edge_pool(_resolved_jobs).map(...)`).
- **Problem**: the pool size is the `_resolved_jobs` of the first call that creates it or grows it; later callers with a smaller share (2 per cascade in a wave) get the same pool, so three cascades queue their chunks on one pool of two threads. The other edge callers (`map_on_edge_pool`, `build_honest_spec`, composite group agg, binned numeric agg redundancy, stability vote) create a per-call pool of their own share and do not have this problem, so the behaviour is inconsistent. Retired pools are kept alive forever (threads are never joined).
- **Proposed change**: make the shared pool capacity the core count (`psutil.cpu_count(logical=True)`), not the share, and use the share only as the number of chunks submitted (`_workers = min(_resolved_jobs, len(_rest))` already does that). Then the pool never needs to grow and never retires; the 2-worker cap of a cascade is kept by the chunk count. Output is unchanged (results are folded by column index).
- **Risk**: low. Oversubscription is not possible because the chunk count still limits each call's in-flight work. Confirm first (a one-line print of `_EDGE_POOL_WORKERS` at each call of the benchmark) whether the hazard is reachable in the benchmark at all.
- **Disposition**: IMPLEMENTED, NEUTRAL 2026-11-20 - the shared `_edge_pool` of `_adaptive_nbins.py` is created at the logical core count whoever creates it first (a caller share is the chunk count); sensor `test_shared_edge_pool_is_created_at_core_count`; measured together with E-F01 (no wall change, see there): the first-caller hazard is not reachable in the benchmark.

### F03 - `build_honest_spec` prepares every column serially on the calling thread before its pool runs

- **Expected saving**: about 0.1 to 0.3 s per call on the benchmark. The calls are per fit (MDLP honest spec); the leaf `build_honest_spec:149` shows 0.4 s of pool wait in the sampler, and the serial loop is in front of it. By reading: about 0.5 to 1 ms per column (`to_numpy` float64 copy, `isinf`, `isnan`, the NaN fill, `is_numeric_dtype` on `X[c]`) times 100 columns.
- **Location**: `src/mlframe/feature_selection/filters/_honest_spec.py:108-124` (the serial `for` loop calling `X[c]` and `_median_filled_column`); `_honest_spec.py:145-152` (the pool that only runs the edge computation).
- **Problem**: the per-column preparation (pandas column access, a float64 copy, two reductions) is pure per-column work that holds the GIL in the main thread while the eight pool workers sit idle. The edge computation after it is already on the pool.
- **Proposed change**: move the per-column block of the loop (everything after the `continue` checks, including `_median_filled_column(X[c])`) into the pool task together with `_edges_of`, and collect `nan_by_col`, `filled` and `numeric_js` in column order from the results. The `None` return (an infinite column) becomes a per-column result that the caller checks before the fold. Output identical; order preserved by index.
- **Risk**: low. `X[c]` on a pandas frame from several threads is read-only; check that the pandas getitem cache is not mutated. The early `return None` must still cancel the rest (run the preparation for all columns, then return None if any was None, which is what the serial code effectively does).
- **Disposition**: REJECTED 2026-11-20 (measured) - the serial per-column preparation of `build_honest_spec` for 100 columns of 100000 rows takes 0.032 s, not the 0.1-0.3 s estimated by reading.

### F04 - `_host_replays` sizes an 8-thread pool per fold without the cascade share

- **Expected saving**: 0.2 to 0.5 s on the benchmark, only when the device replay declines some recipes (host fallback). Evidence: `_REPLAY_THREADS = 8` and `min(8, len(recipes), os.cpu_count())`; the stability vote replays per fold (5 folds), and each call creates and tears down a new pool. By reading; not measured.
- **Location**: `src/mlframe/feature_selection/filters/_fe_stability_vote.py:306` (`_REPLAY_THREADS = 8`), `:324-333` (`_host_replays` pool), `:373` (the call inside the fold loop).
- **Problem**: this pool ignores `_ACTIVE_STAGES`. When the stability vote runs inside a wave, three cascades can each open an 8-thread pool, so about 24 threads compete for eight logical cores and the GIL; the pool is also created and joined once per fold. The replays are numpy ufuncs, which release the GIL only on large arrays, so the extra threads mostly add switching.
- **Proposed change**: size the pool with `_resolve_edge_jobs(None, len(recipes))` (the same share rule as every other edge pool), and create it once per vote call rather than once per fold (pass the executor in from the caller). Results are folded in recipe order, so output is unchanged.
- **Risk**: low. If the vote is run with no wave active the share is the full core count, so the single-stage case is unchanged.
- **Disposition**: IMPLEMENTED 2026-11-20 - `_host_replays` takes the cascade share of the cores (`_resolve_edge_jobs`) instead of eight threads per call; effect not separable on the benchmark (host replay is the fallback path); folded in the batch A/B.

### F05 - The frame fingerprint copies and hashes every column on the main thread on a memo miss

- **Expected saving**: 0.2 to 0.4 s per fit (the sampler leaves show `_full_named_frame_hash` 0.2 s, `_take_nd_ndarray` 0.2 s and `_column_values` in the main-thread list). By reading: 100 columns of 100000 float64 are copied with `np.ascontiguousarray` (80 MB) and then hashed with blake2b on one thread (about 0.1 s of hashing plus the copies), while the other seven logical cores are idle at this point of the fit.
- **Location**: `src/mlframe/feature_selection/filters/_mrmr_fingerprints.py:635-660` (`_full_named_frame_hash`; the column loop at 645-649 and the hash update loop at 651-653).
- **Problem**: the column extraction and copy are GIL-held numpy/pandas work done serially, and the copy exists only to feed the hasher. The memo short-circuits repeated calls but the first call of a fit always pays it on the main thread.
- **Proposed change**: hash per column in a pool (each column's digest is independent; `blake2b` releases the GIL on large buffers), then combine the per-column digests in column order with the same name / dtype / categories suffixes into the outer hasher. Pass a `memoryview` of the column instead of a contiguous copy when the column is already contiguous. The combined digest changes its value, so the memo key semantics stay the same but the stored fingerprint strings change: this needs a one-time migration note for any on-disk cache keyed by it.
- **Risk**: medium. The fingerprint is a cache key; a change to its value invalidates persisted caches. Keep the old function as `_full_named_frame_hash_reference` and add an equality test before switching.
- **Disposition**: REJECTED 2026-11-20 (measured) - `_full_named_frame_hash` is 0.039 s on a miss and called twice a fit (0.21 s in the fit including cold caches); a parallel digest would change the fingerprint value for at most 0.15 s.

### F06 - Per-call thread pools bypass the cascade share and are created and joined on every call

- **Expected saving**: below 0.1 s in total (thread start-up is about 50 to 100 us per thread, and there are a few dozen such calls per fit). Listed because it is the same root cause as F03 and F04: four sites size their pools from the core count or from the work size, not from the share.
- **Location**: `src/mlframe/feature_selection/filters/_edge_pool.py:76-77` (`map_on_edge_pool`, a new pool per call; the share comes from `_resolve_edge_jobs`, so this one is already correct); `_composite_group_agg_fe.py:644-648`, `_binned_numeric_agg_redundancy.py:209-210`, `_honest_spec.py:150-152` (new pools per call, correct share, but not the shared pool).
- **Problem**: the three sites that open a pool per call do not reuse the process pool that F02 discusses, so each wave can run up to three independent sets of short-lived threads on top of the stage pool. No measured cost; a cleanup rather than a speed-up.
- **Proposed change**: once F02 is applied, route these through one helper (`_edge_pool(share).map(...)`), so there is a single pool and a single share rule.
- **Risk**: low; depends on F02.
- **Disposition**: OPEN

### F07 - Python double loops over the p x p correlation matrix in the orthogonal cluster and diff-basis families

- **Expected saving**: about 5 to 10 ms per call (4950 pairs at p = 100, a numpy scalar index and two comparisons each), so below 0.1 s per fit. Listed because the loops hold the GIL on the calling thread and sit in families that run inside the cascades. By reading.
- **Location**: `src/mlframe/feature_selection/filters/_orthogonal_cluster_basis_fe.py:176-181` (`for i in range(p): for j in range(i + 1, p): c_ij = float(abs_corr[i, j]) ...`); `src/mlframe/feature_selection/filters/_orthogonal_diff_basis_fe.py:180-184`, same shape.
- **Problem**: the pair filter `np.isfinite(c) and c >= threshold` is computed element by element in Python on a matrix that is already a numpy array.
- **Proposed change**: `iu, ju = np.triu_indices(p, 1)`; `c = abs_corr[iu, ju]`; `keep = np.isfinite(c) & (c >= thr)` (the exact threshold expression of the loop); build the edge list from `iu[keep]`, `ju[keep]` in the same row-major order that `triu_indices` produces, which is the loop's order. Identical output.
- **Risk**: very low; the ordering must match the loop, which `triu_indices` does (row-major upper triangle).
- **Disposition**: OPEN
