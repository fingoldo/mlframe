# F - GPU utilization and kernel efficiency (read-only audit, HEAD 871110e1f)

Scope: host syncs inside stages, per-item launches, repeated uploads, per-call device queries, and kernel layout, read from the code of `src/mlframe/feature_selection/filters/`. No source edited, no GPU job run. Evidence is either a number from the existing findings (memory file `project_mrmr_30s_goal_findings_2026_11_19.md`, tracker rows MRMR-LAUNCH-COST-FLOOR, MRMR-LAUNCHES-BY-FAMILY) or "by reading". Savings are estimates from the 25 to 82 us host cost per device call measured on this box (MRMR-LAUNCH-COST-FLOOR) multiplied by call counts that were NOT measured for these sites; each one needs a counter run before it is trusted.

Already decided and not re-raised: the per-column loops of binagg, logistic CV, rank binning, RFF maxima, permuted labels, usability CV, gate taus, fold cell moments, guard min/max (MRMR-GUARDMINMAX), root_split_accept lane cut and table layout (MRMR-ROOT-SPLIT-ACCEPT-*). Coverage limit: `family_null_bits_v3` and `radix_select_f32_v5` were not analysed beyond the tracker numbers; the kernel-side findings below are therefore about host orchestration, not about the two largest kernels.

### F01 - Final subsumption: per-candidate host sort of y, upload of y and a sync, all repeated for every candidate
- **Expected saving**: about 0.1 to 0.5 s on the 100000 x 100 wall (by reading). Per candidate the device path does `np.unique(y, return_inverse=True)` on the full 100000-row label vector (a host sort, about 3 to 6 ms), a host-to-device copy of the inverse codes, a `cp.asnumpy` of the joint table (one sync), and `_conditional_perm_null` with `y_arr` a host array. The `final_subsumption_prune` loop runs this once per non-anchor candidate, and the function sits on the serial tail (`_assign_support_tail` / `_final_subsumption_stage`, a 2.7 s block in the 2026-11-19 findings). Candidate count not measured.
- **Location**: `src/mlframe/feature_selection/filters/_fe_retention_subsumption.py:126-136` (`_device_max_conditional_excess`), `:168-297` (`retention_form_is_subsumed`, with `_conditional_perm_null`, `_quantile_bin` of the incumbents and `_cmi_from_binned` per call); loop at `src/mlframe/feature_selection/filters/_fe_final_subsumption.py:37-51`; caller `src/mlframe/feature_selection/filters/_mrmr_fit_impl/_final_subsumption_stage.py:230`.
- **Problem**: every per-candidate call rebuilds state that depends only on `y_binned` and on the anchors: the label encoding (`np.unique`), the label upload, the incumbent binning (`_bin_resident` / `_quantile_bin` of each anchor, the anchors are the same for all candidates), and the renumbered support `z_support_dev`. `_fe_final_subsumption.py:33` already converts `anchor_values` once, but the binning is not hoisted. Each candidate also pays one blocking `cp.asnumpy(joint)` for a table of a few hundred cells.
- **Proposed change**: in `final_subsumption_prune`, encode `y_binned` once (`yi`, `ky`, and a resident copy), bin the anchors once and build `z_support_dev, zcard` once; pass them into a `retention_form_is_subsumed_prepared(...)` variant that skips the per-call work. The existing function stays as the entry point for other callers and its verdict is unchanged, because the inputs are identical. Keep the per-candidate permutation null (its seed is per call) and the CMI legs. Batching the `(z, y)` count tables of all candidates into one `cp.bincount` with a candidate offset would remove the last sync per candidate; that is a second step.
- **Risk**: low for selection (the same arrays feed the same functions), but the verdict depends on the subsample seed; the test must compare the dropped list on the captured candidates, not only the code paths. The incumbent set is built from `candidates` and is constant across the loop, so no ordering risk.
- **Disposition**: OPEN

### F02 - Pair scoring of the additive fusion: three blocking reads per candidate pair
- **Expected saving**: about 0.05 to 0.2 s (by reading; the pair count is not measured). Each pair does two `float(_cmi_from_binned(...))` reads and one `cp.asnumpy` inside `_pair_multiple_r_gpu`'s consumer `multiple_r_from_gram`, plus the `float(ydev.std())`-type reads of the stage. At 25 to 80 us of host time per blocking read and a drained queue each time, the GPU idles between pairs.
- **Location**: `src/mlframe/feature_selection/filters/_fe_additive_fusion_gpu_resident.py:210-263` (`_gpu_evaluate_pair`, syncs at 255, 256, 263), `:69-82` (`_pair_multiple_r_gpu`, `cp.asnumpy(cp.matmul(m.T, m))` at 82).
- **Problem**: the four CMI and OLS scalars of one pair are read one at a time, each forcing a device synchronisation before the next pair's kernels are queued. The module's own comment at 390 says the design is "one host read for all halves", which is what the other loop does not do (see F04), so this per-pair chain is the same pattern at pair level.
- **Proposed change**: return the pair's device scalars (both CMIs and the 4 x 4 Gram) as one device vector from `_gpu_evaluate_pair`, and collect them with one `cp.asnumpy` per block of pairs; compute `multiple_r_from_gram` on the host for the whole block afterwards (it is a 4 x 4 solve per pair, cheap on the host). The decision logic (`_mi_sub > _mi_add + margin` etc.) moves to the host after the batch, with the same comparisons on the same float64 values.
- **Risk**: the decisions are threshold comparisons on float values; keep the float64 conversion point identical so the comparisons do not change. Pairs are processed in order, so a batched read must keep the order of acceptance (the first fusion wins the cap).
- **Disposition**: OPEN

### F03 - Pair residual test: two blocking reads and one allocation per block pair, and each off-diagonal block re-uploaded for every pair
- **Expected saving**: about 0.05 to 0.15 s (by reading). With `p = 100` and `block_cols` of 16 to 32 there are roughly 10 to 28 block pairs per call; each costs an allocation, a kernel, `int(cp.argmax(out))` (one sync), `float(out[m])` (a second sync), and `xp.asarray(b_t)`, a full-n int8 host-to-device copy of the off-diagonal block. The off-diagonal upload happens once per pair of blocks, so each block is uploaded about `B` times instead of once.
- **Location**: `src/mlframe/feature_selection/filters/_fe_sufficient_summary_pairs.py:320-333` (`_block_best_gpu_fused`, syncs at 332 and 333; `cp.empty` at 325), `:405-421` (the block loop, `xp.asarray(b_t)` at 420, `get_block` per pair at 413).
- **Problem**: the comment at 346 says the data is "resident on the device", but the block loop re-uploads the off-diagonal block for every `(ia, jb)` pair, and the winner read costs two syncs where one would do. The `out` buffer is allocated per pair too.
- **Proposed change**: upload every block once before the loop (total int8 size `p * n`, 10 MB at 100 x 100000) and index into the resident list; return `cp.stack((out[m].astype(cp.float64), m.astype(cp.float64))).get()` as one read; reuse one `out` buffer of the largest size across pairs. The CPU fallback paths stay as they are.
- **Risk**: device memory: keeping all blocks resident adds up to `p * n` bytes; at 100 x 100000 that is 10 MB, but at the 1000-column scale it competes with the VRAM budget that `_gpu_block_cols` sizes against. Keep the per-pair upload as the fallback when the resident set does not fit the free VRAM.
- **Disposition**: OPEN

### F04 - `_raw_half_scales`: one blocking read per raw column, contradicting its own comment
- **Expected saving**: about 0.03 to 0.1 s (by reading; H is the number of raw value columns of the stage, about 100 plus engineered halves here). Each iteration runs `astype`, `ravel`, `cp.nanstd` (several reductions internally) and a `float()` read, so the stage makes about H blocking syncs before any scoring starts.
- **Location**: `src/mlframe/feature_selection/filters/_fe_additive_fusion_gpu_resident.py:85-92` (loop with `float(cp.nanstd(...))` at 89); caller `:391`; the comment that promises one read at `:390`.
- **Problem**: the scales are independent per column, so they can be one device reduction over the `(n, H)` matrix that `_upload_and_subsample` already holds (`vals_dev`, line 380-ish), with one `cp.asnumpy` of the length-H vector. The contract "one host read for all halves" in the comment at 390 is not what the code does.
- **Proposed change**: compute `nanstd` over axis 0 of the stacked `(n, H)` float64 matrix (`cp.nanstd(vals_dev, axis=0)` on the resident matrix, or `cp.stack` of the H columns once), then one `.get()`. Non-finite or zero spreads still map to 1.0 with the same `np.isfinite(sd) and sd > 0.0` rule applied on the host.
- **Risk**: `nanstd` over an axis of a float64 matrix gives the same per-column values, but the reduction order differs, so the last bits may move; the scale is a ratio used in a weighted sum, and the test should check the scales to a relative 1e-12 and the selection.
- **Disposition**: OPEN

### F05 - `cp.cuda.Device().attributes[...]` read on every call in the device launch wrappers
- **Expected saving**: unknown until measured; plausible 0.05 to 0.3 s over a fit (by reading, the call counts are not measured). The attribute property of the cupy device object builds a dictionary of the device attributes from the driver on each access (cupy's `Device.attributes` is a Cython property in `cupy/cuda/device.cp311-win_amd64.pyd`; the source is not in the install, so the per-access cost is NOT verified here).
- **Location**: `src/mlframe/feature_selection/filters/_fe_batched_qbin.py:167`, `_gain_stats_codes_gpu.py:114`, `_fe_batched_mi_cmi.py:201`, `:315`, `:556`, `_fe_batched_mi_cmi_hist.py:707`, `_fe_batched_qbin.py:167`, `_family_maxt_cuda_bits.py:315` (inside `_v2_applies`, called per family-null launcher), `_extra_fe_families_dispersion_resident.py:166` and `:228`, `_fe_device_scheduler.py:46`, `_fe_resident_operands.py:250`, `:435` (`cp.cuda.Device().id` per cache key).
- **Problem**: `MultiProcessorCount`, `MaxSharedMemoryPerBlock` and `L2CacheSize` are constants of the device, but each wrapper queries them on every call, and some do it inside per-chunk launch loops (`_fe_batched_qbin.py:167` is in the per-block path, `_family_maxt_cuda_bits.py:315` per family-null launcher). The `Device().id` key at `_fe_resident_operands.py:435` is also a per-call query on the content-cache hot path.
- **Proposed change**: one module-level memo `_device_attr(name)` keyed by `cp.cuda.Device().id` (a dict filled once, under the existing lock pattern), used by all sites above. The values are constant per device, so the selection is unchanged. The `_fe_resident_operands` key can read the current device id once per call through the cupy runtime, which is cheap.
- **Risk**: multi-GPU runs (the device scheduler) must key by device id; a single-device box is unaffected. No numerical change.
- **Disposition**: OPEN

### F06 - Conditional quantile rank: full-column device-to-host copy, three blocking reads and a Python per-bin loop in the same call
- **Expected saving**: about 0.02 to 0.1 s (by reading; the call count of the conditional rank is not in the tracker). Per call the code reads `int(counts[0])` (sync), `cp.asnumpy(counts[1:])` (sync), `cp.asnumpy(sv[...])` (a copy of the whole sorted column, up to 800 KB float64 at 100000 rows), `cp.asnumpy(out)` (the ranks, a second full copy), and then builds `sorted_bins` with a Python list comprehension over `top + 1` bins.
- **Location**: `src/mlframe/feature_selection/filters/_conditional_quantile_rank_gpu.py:60-80`.
- **Problem**: the per-bin sorted arrays are only needed by the caller for per-bin lookups; they are rebuilt on the host after a full copy of the sorted values and a `np.split`. The same per-bin boundaries are available on the device (`counts`, `starts` are already device arrays), so the host copy and the loop are avoidable if the consumer accepts segment offsets.
- **Proposed change**: return the sorted device array with the `starts` offsets (one `.get()` of the counts vector, which is `top + 1` long), and let the consumer slice per bin, or, if the consumer must have host arrays, do one copy of `sv` and build the splits from the offsets with one `np.split` (no Python per-bin comprehension). Read `counts` once as `counts.get()` instead of `int(counts[0])` plus `cp.asnumpy(counts[1:])`.
- **Risk**: the consumer contract (`with_sorted_bins`) must be read first; the change alters the return type only if the consumer is changed too. Values are identical.
- **Disposition**: OPEN
