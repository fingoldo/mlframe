### DSC-01 [P1] Grouped causal bases copy each row's own target into the first row of every group
- **Where**: `discovery/_grouped_causal_bases.py:62` (lag), `:81` (expanding mean), `:105` (trailing mean). The default is `engineer_causal_first_fill="group_first"` in `_composite_target_discovery_config_base.py:48`, and the behaviour is pinned by `tests/training/composite/discovery/test_biz_val_grouped_causal_bases.py::test_single_row_group_fills_own_value`.
- **What**: For in-group position 0, all three kernels write `first = y_sorted[lo]`, which is that same row's own `y`. `lag<k>` also writes it into positions 1..k-1. For example, with `y=[5,6,7]`, `g=[solo,pair,pair]` and `lag1`, the output is `[5,6,6]`: the `solo` row gets base == its own target (the test asserts exactly this). On every group's first row the composite `T = y - base` is therefore exactly 0 (or `y - alpha*y`). These columns are added after the leakage guard and the forbidden-corr filter (`_fit.py:201-211`), so no leakage check ever sees them.
- **Why it matters**: This is plain target leakage on 1/group_size of the rows, and more than that for small groups and `lag>1`. At serve time a new group's first row has no observed `y`, so this value can never be computed. The MI screen, the tiny rerank and the honest gates all score these bases as better than they really are. The biz_value test's measured `RMSE_lag/RMSE_raw ~= 0.018` is flattered for the same reason: every holdout well's first row reconstructs perfectly.
- **Suggested fix**: A history-less row must never read its own `y`. Default `first_fill` to `"nan"`, which downstream pairwise masking already handles. If a finite fill is kept, use a train-only statistic that excludes the current row, such as the global train median.
- **Test to add**: For a one-row group, the engineered base must not equal that row's `y` under the default config. Also add a biz test that compares holdout reconstruction RMSE on first-in-group rows against the other rows.
- **Disposition**: COMPLETED - engineer_causal_first_fill defaults to 'nan' (config and the builder), so a history-less row is left undefined for the downstream masking to drop instead of being handed its own y; opting back into 'group_first' logs a warning naming the leak (test_biz_val_grouped_causal_bases.py::test_default_fill_never_writes_a_rows_own_target_into_its_causal_base and ::test_single_row_group_is_nan_not_its_own_value, which pinned the old fill)

### DSC-02 [P1] Engineered `__gcausal_*` bases exist only in discovery's private frame, so kept specs cannot be rebuilt downstream
- **Where**: `discovery/_grouped_causal_bases.py:319` attaches the columns to discovery's local `df`, and `_fit.py:209-212` rebinds `df` only inside `fit`. The consumer is `core/_phase_composite_discovery.py:827` (`_build_full_column_from_splits(_spec.base_column, train_df_pd, val_df_pd, test_df_pd, ...)`), and `core/_misc_helpers.py:199` silently skips any column that is absent from a split frame. A repo-wide grep for `gcausal` / `attach_grouped_causal_bases` finds no producer outside `discovery/`.
- **What**: Engineering is on by default (`engineer_causal_bases=True`). When `group_column` is set and present in the discovery frame, the `y__gcausal_*` columns join both `usable_features` and `base_candidates`, and specs on them are kept (the biz test asserts `any(s.base_column == "y__gcausal_lag1" ...)`). `export_specs()` then hands the suite a `base_column` that none of the train/val/test split frames contain. `_build_full_column_from_splits` returns an all-NaN column, `domain_check` fails on every row, `T` is all-NaN, and the median fill finds no finite train `T`. The composite target is garbage. `_stacked.py:20-26` / `_warn_unrebuildable_oof_specs` already documents the same all-NaN mechanism for `_oof_*` columns and warns about it, but there is no equivalent warning or exclusion for `__gcausal_*`. In addition, because the engineered columns also sit in `usable_features`, every tiny-rerank, honest-gate and yscale-gate model is fit with lag-of-y features that the deployed per-spec models will not have. That inflates the gate scores for all specs, not only the gcausal-based ones.
- **Why it matters**: When a group column is configured, discovery can promote a spec that the suite trains on a NaN target, and every gate verdict for that target was measured with features that do not exist downstream.
- **Suggested fix**: Either persist the engineering recipe on the spec (op, k, group field, time column) and rebuild the column in the suite before `_build_full_column_from_splits` and at predict time, or leave engineered bases out of `export_specs` and `usable_features` until that rebuild exists. Separately, make `_build_full_column_from_splits` raise, or at least warn, on a column that is missing from every split.
- **Test to add**: An end-to-end suite smoke with `group_column` set: every exported spec's `base_column` must exist in the train split frame, or the phase must reject the spec loudly. A unit test should also assert that the materialised `T` for each shipped spec is not all-NaN.
- **Disposition**: COMPLETED - the discovery phase drops any kept spec whose base (or extra base) column is in none of the train/val/test frames, recording one failure entry each, and the shared column builder now warns instead of answering a name it cannot find with a silent all-NaN column. Engineered causal bases stay screening-only: they are functions of past y, which a predict frame does not carry, so there is nothing to rebuild downstream (test_composite_spec_base_materialisable.py, 5 tests; the builder probe fails at origin/master)

### DSC-03 [P1] The "never-touched" honest holdout is used for selection and then reported as an honest post-selection estimate
- **Where**: The carve is at `_honest_holdout.py:120-156`. It selects in three places: (1) the drop gate at `_honest_rmse_gate.py:61-205`, called from `_fit.py:716-722`; (2) the ranking key at `_tiny_rerank.py:565-605` (`honest_oof_reconstruction_rmse` on `honest_holdout_idx_`, then `agg_scores[i] = _hv`); (3) the floor reject at `_tiny_rerank_waic.py:18-54`. It is reported at `_honest_holdout.py:180-340`, called from `_fit.py:728-734`. It is ranked again across targets at `core/_phase_composite_discovery.py:866-878` (the budget sort key is `honest_holdout_rmse_gain / honest_holdout_raw_rmse`).
- **What**: The docstrings (`_honest_holdout.py:9-17`, config `honest_holdout_frac`) promise that the holdout is carved before screening and that only the final winners are re-scored on it, which removes the winner's curse. In practice the same rows decide which specs survive (honest RMSE gate), which order they rank in and whether they pass the floor (honest-OOF, whenever group ids exist). The surviving specs then get `honest_holdout_gain`, `honest_holdout_rmse` and `honest_holdout_rmse_gain` stamped from those rows, and the suite's `max_total_composite_targets` budget picks winners by that number. The re-score is therefore conditioned on having passed a filter measured on the same rows. The mechanism is the same post-selection bias the module exists to remove.
- **Why it matters**: The only "honest" generalisation numbers discovery exports are optimistic, and they get more optimistic as the gates reject more candidates. Downstream consumers (budget ranking, `honest_holdout_gains_`, reports) treat them as unbiased.
- **Suggested fix**: Split the holdout in two: a selection holdout for the honest-RMSE gate and the honest-OOF rank/floor, and a report holdout that no decision reads. Stamp the honest fields and feed the cross-target budget only from the report holdout. Rename whatever is left on the selection holdout (for example `selection_holdout_rmse`).
- **Test to add**: Use a synthetic with many noise candidates where the gates keep the top few. Assert that the mean reported `honest_holdout_rmse_gain` of the survivors on the report holdout does not exceed the value measured on fresh rows drawn from the same DGP by more than noise. With today's code this fails because the gain is conditioned on the gate.
- **Disposition**: COMPLETED - the carve halves the holdout into honest_holdout_select_idx_ and honest_holdout_report_idx_: the drop gate and the honest-OOF ranking key read the selection half, the final re-score stamps its gain from the report half that no gate or ranking touched. A holdout too small to leave two usable halves keeps both roles on all rows (prior behaviour). The two winner's-curse biz tests now run on 2x the rows so the report half carries the sample size their thresholds were calibrated on; thresholds unchanged (test_honest_holdout_select_report_split.py, 5 tests)

### DSC-04 [P1] Tiny-rerank CV scores every fold with transform params fit on all rows; the per-fold refit fix exists but is never called
- **Where**: The params come from `_eval.py:344` (`transform.fit` on all valid screening-pool rows). They are reused per fold at `_screening_tiny_perbin.py:203` and `:220` (`forward(..., fitted_params)` on the whole CV population) and at `:338` (`inverse(..., fitted_params)`), passed in from `_tiny_rerank.py:403`, `:440` and `:642`. The fix is `refit_transform_on_fold` at `_eval.py:124-238`. Its only references are its own definition and `tests/training/composite/eval/test_eval_perfold_refit.py`, which exercises a hand-written harness (`_cv_heldout_rmse`) and not the production CV.
- **What**: For each spec, the tiny CV computes `T` for the train and validation folds with params that saw the validation fold's rows (linear_residual alpha/beta, PCHIP knots of `monotonic_residual`, the `smoothing_spline_residual` fit, `polynomial_residual_deg2`, and so on). The raw-y baseline has no such fitted stage, so the comparison is biased toward composites, most of all toward flexible ones. - **Suggested fix**: In `_tiny_cv_rmse_y_scale._one_fold`, call `refit_transform_on_fold(transform, y_clean[train_fold], base_clean[train_fold])`, then forward and inverse both folds with the fold params, falling back to the global params when it returns `None`. - **Test to add**: Drive `_tiny_cv_rmse_y_scale` itself with the degree-13 poly transform from `test_eval_perfold_refit.py`. The reported RMSE must match the per-fold-refit harness and must not match the global-fit number.
- **Disposition**: COMPLETED - _tiny_cv_rmse_y_scale's _one_fold now calls refit_transform_on_fold on the fold's own train rows and forwards/inverses that fold with the fold-local params (the helper existed and was tested but had no production caller); a degenerate fold returns None and keeps the global params, so a spec that scored before still scores (test_tiny_cv_refits_transform_per_fold.py, which fails at origin/master where both scores are identical)

### DSC-05 [P1] `time_ordering` sorts only the MI screen; the CVs that claim to be forward-walks run on row-position order
- **Where**: The sort is at `_fit_temporal.py:84-105` (called from `_fit.py:244`) and sets `self._screen_time_ordered_=True`. The consumers ignore that order: the tiny rerank draws its own sample at `_tiny_rerank.py:117` (`_sample_indices` returns position-sorted indices) and then sets `time_aware` from the flag at `:246` and `:388`; multi-base stepwise uses `_fit_multibase.py:108` on `y_train` in `train_idx` order; the alpha-drift halves at `_eval_stats.py:286-306` split `train_idx` positionally.
- **What**: MI is invariant to row order, so the sort in `order_screen_by_time` changes nothing that is computed from the screen. Its only effect is setting the flag. Every consumer then runs `TimeSeriesSplit` (or a first-half vs second-half drift test) over rows in frame-position order, not time order. Take a frame in shuffled or grouped row order with `time_ordering` supplied (the case the parameter exists for). The "forward-walk" folds are then arbitrary contiguous position blocks: they neither prevent future-to-past leakage nor keep KFold's shuffling. The alpha-drift "rolling-origin" test compares two arbitrary halves. The `_fit.py:235-241` comment ("Sorting once here makes every per-spec / raw-baseline / stepwise tiny-CV time-correct") does not hold.
- **Why it matters**: Leakage protection on temporal data is silently absent whenever frame order differs from `time_ordering`, which is the reason to pass it.
- **Suggested fix**: Store the time key (or a per-row time rank) on the instance. In `_tiny_model_rerank`, multi-base stepwise and the drift gate, sort each consumer's own sample by time before building splits and halves. Alternatively, sort `train_idx` by time once at the top of `fit`, after the holdout carve, so every downstream positional order is time order.
- **Test to add**: Shuffle a strongly autoregressive frame's rows and pass `time_ordering`. Assert that the tiny-rerank folds, as captured through a `cv_splitter` spy, are monotone in time, and that the drift gate's halves are the time halves.
- **Disposition**: COMPLETED - fit stores the caller's time key on the instance and the new _fit_temporal.order_rows_by_time re-applies it where a consumer draws its own rows: the tiny rerank orders its sample before the TimeSeriesSplit, and the alpha-drift gate orders train_idx (and the cached base pool with it) so its halves are the time halves (test_time_ordering_reaches_consumers.py: a 1.0 -> 5.0 slope break scores z=3.92 ordered vs z=0.89 in row order, the latter under the 3.0 threshold, and the probe fails at origin/master)

### DSC-06 [P2] The bin-MI `mi_gain` compares a de-duplicated `MI(T,X)` with a non-de-duplicated `MI(y,X)`
- **Where**: `_fit.py:433-443` prunes `_x_prebinned` with the dedup keep-mask (on by default, `dedup_x_remaining_for_mi_baseline=True`). `_fit.py:459-470` builds `mi_y_for_base` from `_per_feat_y_full` excluding only the base column, with no keep-mask. `_eval.py:515` computes `mi_t` on the pruned `_x_prebinned`, and `_eval.py:564` sets `mi_y_compare = mi_y_for_base` whenever the domain filter kept every row.
- **What**: With `mi_aggregation="mean"`, `mi_t` averages over K de-duplicated columns while `mi_y` averages over all F-1 columns. When a near-duplicate block carries high MI (the lag family this dedup targets, per `_fit.py:399-407`), `mi_y` is inflated and `mi_gain` is biased low for exactly those bases. The bias is also inconsistent: a transform whose domain filter drops even one row goes through `_eval.py:538-562`, which recomputes `mi_y_compare` on the pruned matrix. So two specs on the same base are scored on different bases depending on domain coverage. The knn path is correct (`_surviving_orig_idx` is pruned in lockstep). The comment at `_fit.py:404-406` says the decomposed vector is pruned too, which is not true on the bin path. The bootstrap replicates (`_eval.py:606-611`) use the pruned matrix for both halves, so under bootstrap the LCB and the point estimate are on different feature sets. Separately, `rescore_specs_on_holdout` (`_honest_holdout.py:159-177`, `:307-324`) never de-duplicates, so its docstring's "directly comparable to the in-screen mi_gain" is not true either.
- **Why it matters**: On `screening="mi"`, `mi_gain` is the ranking key (`_filter_and_gate.py:65`) and the rerank pre-order, and it is the fallback budget gain at `core/_phase_composite_discovery.py:876`.
- **Suggested fix**: When `_keep` prunes columns, derive `mi_y_for_base` by aggregating `_per_feat_y_full[_surviving_orig_idx]`, as the knn branch does. Apply the same keep-mask in `_build_x_remaining_holdout`.
- **Test to add**: Use a frame with an exact duplicate of a high-MI feature and a full-domain transform. Assert that `spec.mi_y` equals `_mi_to_target_prebinned(pruned_matrix, y)`, and that the gain matches between a full-domain transform and the same transform forced through the shrunk-domain path.
- **Disposition**: COMPLETED. When the dedup prunes columns, the bin-path `mi_y_for_base` is aggregated over `_per_feat_y_full[_surviving_orig_idx]`, the columns `MI(T, X)` sees, as the knn branch already did. The selection logic moved to `_fit._mi_y_baseline`. An exact duplicate of a high-MI feature no longer changes `mi_y`. The holdout rescore computes both halves on one holdout matrix, so it was already consistent. Tests: tests/training/composite/discovery/test_scorer_invariance.py (fails pre-fix).

### DSC-07 [P2] The tiny rerank ranks and gates on a mix of honest-holdout RMSE and optimistic in-group CV RMSE
- **Where**: `_tiny_rerank.py:585-590` replaces `agg_scores[i]` only for specs with a finite honest-OOF measurement. `_honest_oof_select.py:131-148` returns `None` (no measurement) when a spec has fewer than 50 valid fit rows, when forward raises, or when fit or inverse raises. The gate at `_tiny_rerank.py:683-686` then compares every score with the honest raw baseline, and `:767` / `:921` sort them together.
- **What**: `_honest_oof_select.py:9-12` documents group-internal CV as optimistic (about 9 vs 13.6 on the prod case). A spec whose honest measurement degenerated keeps its optimistic internal-CV score, sorts above honestly measured specs, and is tested against an honest-scale threshold that it passes easily. It also skips the floor reject (`_tiny_rerank_waic.py:31-32`). The specs the honest path could not measure are therefore the ones most likely to be promoted to top-M.
- **Why it matters**: The ranking is not monotone in any single objective, and a spec that could not be measured beats specs that were measured.
- **Suggested fix**: Keep the two populations separate. Rank measured specs by honest RMSE and put unmeasured specs after them, or rescale their CV score by the raw-y honest/CV ratio measured on the same run. Apply the gate threshold on the scale each score came from.
- **Test to add**: Take two specs, one with honest RMSE 12 and one forced to `None` with internal CV 9 (monkeypatch the transform to raise in `forward` on the holdout fit only). Assert that the unmeasured spec does not rank first.
- **Disposition**: COMPLETED. `_put_unmeasured_on_the_honest_scale` multiplies an unmeasured spec's group-internal CV score by the raw-y honest/CV ratio measured on the same run, before ranking and gating. Without that ratio, the spec is placed after every measured one. An optimistic CV score can no longer outrank honest measurements. Tests: tests/training/composite/discovery/test_scorer_invariance.py (fails pre-fix).

### DSC-08 [P2] The y-scale gates score a spec on its finite rows only, while raw-y is scored on every row
- **Where**: `_yscale_holdout_gate.py:403-416`, `_honest_rmse_gate.py:180-193`, `_honest_oof_select.py:163-169`, and `_auto_chain.py:288-291`.
- **What**: A spec is rejected only when fewer than `max(50, 0.5*n)` inverse predictions are finite. Otherwise `rmse_y = rmse(y_eval[finite], y_hat[finite])` is compared with a raw RMSE over all `eval` rows. A spec whose inverse blows up on 49% of holdout rows (exactly the unseen-base tail these gates exist to catch) is scored on the 51% where it behaves, and can pass. `_auto_chain._y_scale_cv_rmse`'s docstring says off-domain validation rows are "kept on the val side scored against y_val directly ... dropping it from val would flatter the chain". The code drops every non-finite `y_hat` row at `:288`, which does the opposite. The production estimator fills such rows with `y_train_median` (the emulation in `_screening_tiny_perbin.py:317-350`), so the gates are measuring a different predictor from the one that ships.
- **Why it matters**: The collapse gates under-reject the partial collapses they were written for.
- **Suggested fix**: Score every eval row. Replace non-finite `y_hat` with the train-fold median, as `CompositeTargetEstimator.predict` and `_tiny_cv_rmse_y_scale` do, then compute RMSE on the full population. Keep the finite-fraction reject as an additional check.
- **Test to add**: Use a transform whose inverse is NaN on 40% of holdout rows and near-perfect on the rest. The gate must reject it, or score it at least as high as the median-fill RMSE.
- **Disposition**: OPEN

### DSC-09 [P2] Gate exceptions keep the spec (fail-open), and an all-NaN tiny-CV score passes the raw-baseline gate
- **Where**: `_yscale_holdout_gate.py:363`, `:377`, `:384`, `:397` and `_honest_rmse_gate.py:142`, `:165`, `:174` (`survivors.append(spec)` on an unknown transform, a domain/forward failure, or a fit/inverse exception, logged at DEBUG). In the tiny rerank, `_tiny_rerank.py:538` assigns `inf` when every family is NaN, and `:767` rejects only `math.isfinite(score) and score >= threshold`.
- **What**: If a spec's `transform.inverse` raises on the unseen-group or holdout rows (the regime that will also raise at predict time), both collapse gates keep it with no WARNING. A spec whose tiny CV failed in every family (for example, non-finite `T` on domain-valid rows makes `_tiny_cv_rmse_y_scale` return NaN) gets `agg=inf`, is not rejected by the raw-baseline threshold, and stays in `reranked`. With fewer than `top_m` survivors it is shipped.
- **Why it matters**: A failure inside a gate disables that gate for the spec that failed, which is the opposite of what a safety gate should do.
- **Suggested fix**: Treat an inverse or forward exception on eval rows as a collapse (reject, with a ledger entry). Treat a non-finite `agg_score` as a reject in the threshold gate. If a lenient mode is wanted, log at WARNING and record a ledger stage for it.
- **Test to add**: Monkeypatch a registered transform's `inverse` to raise on inputs outside its train range. Assert that the yscale and honest-RMSE gates reject it and that `rejection_ledger` records why. Separately, force a spec's tiny CV to NaN and assert it is not in `specs_`.
- **Disposition**: COMPLETED. Both collapse gates reject a spec (WARNING plus a ledger row, via `_rejection_ledger.gate_error_reject`) when its forward, fit or inverse raises on the gate's rows, and when its transform is not registered. Before this, such a spec was kept with a DEBUG line. A degenerate measurement (fewer than 50 valid rows, a raw baseline that cannot be fitted) still keeps the spec, because nothing sound exists to judge it by. In the tiny rerank, `_reject_unscored_specs` drops every spec whose aggregated score is non-finite before the raw-baseline gate, so the all-NaN case is rejected even when the raw baseline itself is non-finite and no threshold runs. Tests: tests/training/composite/discovery/test_gate_evaluation_errors_reject.py (the gate cases fail on the pre-fix gates).

### DSC-10 [P2] The WAIC tie-break compares log predictive densities of different target scales
- **Where**: `_tiny_rerank_waic.py:89-99` computes WAIC on `T = transform.forward(...)`. `_eval_waic.py:150-170` computes `lpd = -0.5*(log(2*pi*sigma2) + r^2/sigma2)` with `sigma2` in T units. Within the 2% RMSE band, `_tiny_rerank_waic.py:126-127` reorders by `-waic`.
- **What**: `elpd` contains `-0.5*log(sigma2_T)`. A transform whose `T` is on a smaller scale (for example `log_y`, `cbrt_y`, `quantile_normal_y`, or a chain's cbrt stage) gets a higher WAIC by roughly `log(scale_y/scale_T)` nats per row, with no Jacobian correction back to the y density. The tie-break therefore systematically favours compressive transforms over residuals of equal y-scale RMSE, and that is not the "generalises vs overfits" signal the config comment (`transform_waic_validation_enabled`) describes.
- **Why it matters**: The tie-break is on by default and changes the top-M order among near-tied specs for a reason unrelated to predictive quality.
- **Suggested fix**: Compute WAIC on the y scale. Either invert the OOF `T` predictions and score y residuals, or add the per-row log-Jacobian `log|dT/dy|` to each `lpd`. The alternative is to restrict the tie-break to bands whose members share one target scale (all residual-type transforms).
- **Test to add**: Take `y` and `a*y` style transforms of identical y-scale quality (for example `T=y-base` vs `T=(y-base)/100`, equivalent under squared loss). They must get equal WAIC and must not be reordered.
- **Disposition**: COMPLETED. The WAIC tie-break re-orders a noise band only when every member's transform is additive in T (`Transform.additive_in_t`: T in y units). A band that mixes in a compressive transform (log, cbrt, a ratio) keeps its y-scale RMSE order, so the ~log(scale_y/scale_T) per-row bias cannot decide the order. Tests: tests/training/composite/discovery/test_scorer_invariance.py (fails pre-fix).

### DSC-11 [P2] WAIC and auto-chain CVs use shuffled KFold, ignoring groups and time

### DSC-27 [P3] Per-group discovery gates each group's specs on the whole val frame and loses the rerank group ids
- **Where**: `_per_group.py:84-96`.
- **What**: Each per-group `fit` receives the full `val_df` / `val_y` for every group, so the yscale gate for group A's specs is evaluated on val rows from all groups, a different population from the one these specs are routed to. - **Why it matters**: The opt-in path gates on the wrong population and silently loses group-awareness.
- **Suggested fix**: Filter `val_df` / `val_y` to the group's rows (by `per_group_column`), and copy `_group_ids_for_rerank` and `_hint_strengths_pct` onto the delegate.
- **Test to add**: With `per_group_discovery_enabled`, assert that the delegate's yscale gate sees only the group's val rows and that `_group_ids_for_rerank` is set on it.
- **Disposition**: COMPLETED. Each per-group delegate now gets only its group's val rows (`_group_val_rows` filters `val_df` / `val_y` by `per_group_column`). When the val frame lacks the column or has no rows for the group, the delegate's y-scale gate falls back to its own train rows. The delegate also inherits `_group_ids_for_rerank` and `_hint_strengths_pct` from the parent. Regression test `test_a_group_delegate_gets_its_groups_val_rows_and_the_rerank_grouping` in test_per_group_discovery.py fails before the fix (every delegate got both groups' 400 val rows and no rerank grouping).

### DSC-29 [P3] The knn cost guard runs after the most expensive knn work

### DSC-30 [P3] The stratified MI sampler gives non-finite-y rows a full stratum share
- **Where**: `screening.py:925-948`.
- **What**: Non-finite `y` rows form stratum `n_strata`, and the water-fill gives it the same share as each finite stratum. With 1% NaN targets, `n_strata=10` and `sample_n=100k` on 1M rows, the NaN stratum takes about 9.1k of 10k NaN rows, so roughly 9% of the MI screen budget goes to rows that every MI and fit step drops (`isfinite` masks). The effective screen shrinks by that fraction.
- **Why it matters**: The screening budget is wasted and the sample is smaller than configured on targets with NaNs.
- **Suggested fix**: Exclude non-finite `y` from the sampler (or cap that stratum at 0), since no downstream consumer can use those rows.
- **Test to add**: With 1% NaN `y`, assert the sampled rows contain no non-finite `y`, or at most their natural frequency.
- **Disposition**: COMPLETED. Non-finite-y rows are excluded from the stratified sampler: they no longer form a stratum with a full water-fill share, since every MI and fit step drops them. Tests: tests/training/composite/discovery/test_splitter_contract.py (fails pre-fix).
