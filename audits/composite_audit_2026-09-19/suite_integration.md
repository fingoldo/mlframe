### INT-01 [P0] A saved suite serves composite-target models in T-scale: the on-disk `.dump` is the unwrapped inner model
- **Where**: `training/train_eval.py:541` (`save_mlframe_model(model, fpath, lean=True)` inside `process_model`, which runs before any wrapping). `core/_phase_train_one_target_post.py:219-247` and `core/_phase_composite_wrapping.py:247,418` wrap the entry in `CompositeTargetEstimator` in memory only. No later code re-saves the entry. `core/_predict_main_suite.py:429` (the CTE branch never fires for disk-loaded models) and `core/_predict_main_suite.py:600-619` (the regression ensemble averages every float prediction across all targets). `core/predict.py:660` (`load_mlframe_suite`) has no re-wrap step either.
- **What**: After training, the in-memory `models["regression"]` held `CompositeTargetEstimator` for `target-linres-TVT_prev` and `target-chain_linear_residual_cbrt-TVT_prev`. On disk, all three `.dump` files deserialised to a bare `Ridge`. `predict_mlframe_models_suite(df, models_path)` then returned:
  - `.../target/...` mean 9.421, std 2.928 (y mean 9.419, std 2.951);
  - `.../target-linres-TVT_prev/...` mean -0.500, std 0.599;
  - `.../target-chain_linear_residual_cbrt-TVT_prev/...` mean 0.454, std 0.635.

  The composite predictions are residual/T values returned under the composite target's key, with no warning. The suite-wide `ensemble_predictions` for a regression suite is `combine_float_predictions` over all of these arrays, so it mixes y-scale and T-scale numbers (and raw predictions of different targets). Metadata still carries `composite_target_specs`, so the loader has everything it needs to wrap, but it never does.
- **Why it matters**: Any saved suite with discovery enabled (including the auto-enabled default for heavy-tail or skewed targets) produces silently wrong production predictions for every composite target. The regression suite ensemble is corrupted as well.
- **Suggested fix**: Persist the wrapped form. Either re-save each composite entry after the wrap (the per-model hook already has `fpath` semantics via the entry's model dir), or save a small "composite wrap manifest" and have `load_mlframe_suite` / `predict_mlframe_models_suite` rebuild `CompositeTargetEstimator.from_fitted_inner(...)` from `metadata["composite_target_specs"]` for any target dir whose original name is a spec name. Also key the regression float ensemble per `(target_type, target_name)`, as the probability branch already does, instead of averaging across targets.
- **Test to add**: End-to-end: train with composite discovery on the TVT fixture, save, then call `predict_mlframe_models_suite` and `load_mlframe_suite` + `predict_from_models`. Assert that each composite target's prediction mean and std are within a tolerance of y's, and equal the in-memory wrapper's output. The existing `tests/inference/test_predict_round_trip_parity.py` passes `CompositeTargetDiscoveryConfig(enabled=False)` everywhere, and the fuzz combo suite (`tests/training/_fuzz_combo/`) has composite axes but never calls a predict or load entry point. Add a composite-on variant to both.
- **Disposition**: COMPLETED - post-processing re-saves each wrapped dump, so a loaded suite serves the wrapper; predict_from_models 10.361 -> 0.301 RMSE on the TVT fixture (dbe77db39; test_composite_suite_persistence.py::test_composite_dumps_hold_the_y_scale_wrapper)

### INT-03 [P1] Every y-scale consumer feeds `CompositeTargetEstimator` a frame from the wrong pipeline stage
- **Where**: `core/_predict_main_from_models.py:570` and `core/_predict_main_suite.py:429-431` pass `df_pre_pipeline` (before the suite pipeline, row-wise extensions and the model's own pre_pipeline). `core/_phase_composite_wrapping.py` metric and chart blocks call `_wrapper.predict(test_df_pd / filtered_val_df / filtered_train_df)` (per-model hook `:263`, wrap pass `:464` and `:520`). The CTE passes X straight to the inner estimator (`composite/estimator/_predict.py:273`).
- **What**: The inner model was trained on the post-pipeline frame, including the default-ON `row_summary_*` / `row_extreme_*` columns and its pre_pipeline (`inf_to_nan, imp, scaler, to_float32`). In the repro:
  - (a) `predict_from_models(df, models, metadata)` logged "Error predicting with model regression_target-linres-TVT_prev_Pipeline" (`ValueError: Feature names seen at fit time, yet now missing: row_extreme_top1_score, ...`) and dropped the composite model from the results. The raw-target model predicted fine (RMSE 0.301).
  - (b) The suite's recorded `composite_target_y_scale_metrics` test RMSE for `target-linres-TVT_prev` was 0.607, while the same model's T-scale test RMSE was 0.334. For an additive `linear_residual` the two must be equal. Calling `cte.predict` on the post-main-pipeline frame reproduced the degraded 0.578 over all rows.

  The "CTE-RAW-X" fix routed raw X so the base column is unscaled. That also stopped the inner model from receiving its own preprocessing. The two needs conflict because the CTE has only one X.
- **Why it matters**: Composite models cannot be served through the in-memory predict entry point. The y-scale metrics, charts and verdicts the suite reports for composites (and uses for COMPOSITE_BEATS_RAW / MoE / dummy-floor decisions) are computed on a mis-fed inner model.
- **Suggested fix**: Give the CTE two inputs, or have it own its inner's preprocessing. Read `base_column` values from the stage discovery used (the post-suite-pipeline frame the spec was fitted on, e.g. `filtered_train_df`) and run the inner through the entry's own feature pipeline (pre_pipeline + row-wise extensions + column subset), exactly as `_apply_pre_pipeline_with_passthrough` does for raw models. Apply the same routing in both predict entry points and in the wrap-pass metric blocks.
- **Test to add**: On the TVT fixture with an additive `linear_residual` spec, assert `|RMSE_y(wrapped, test) - RMSE_T(inner, test)| < 1e-6` from the suite's recorded metrics, and assert that `predict_from_models` returns a finite y-scale prediction for every composite key.
- **Disposition**: COMPLETED - the predict entry points hand the wrapper the suite-stage frame instead of the per-model subset; recorded y-scale test RMSE 0.607 -> 0.334, equal to the inner T-scale error (dbe77db39; test_additive_composite_y_error_equals_inner_t_error)

### INT-04 [P1] Auto-enabled discovery is not propagated: post-processing still sees `enabled=False` and skips the cross-target ensemble and lag failsafe
- **Where**: `core/_phase_composite_discovery.py:81-116`. `_maybe_auto_enable_discovery` returns a `model_copy(update={"enabled": True})` that stays local to `run_composite_target_discovery`. The suite passes its original config to post-processing (`core/_main_train_suite.py:766`), which gates on `.enabled` at `core/_phase_composite_post.py:159,194,233`.
- **What**: With a heavy-tailed target (y = lognormal base * exp(0.3*x1 + noise)) and `CompositeTargetDiscoveryConfig(base_candidates=["b"], ...)`, with `enabled` left at its default, discovery auto-enabled and trained `target-logY` and `target-cbrtY`. The run ended with keys `['target', 'target-logY', 'target-cbrtY']`. The same config with explicit `enabled=True` produced `[..., '_CT_ENSEMBLE__target']`. The composites are trained and wrapped, but the combiner, the `always_build_ct_ensemble_for_raw` lag_predict failsafe, the dummy-floor/AR(1) gates and the "entry" banner never run.
- **Why it matters**: The default path for heavy-tail/skew targets silently gets a different, weaker pipeline than an explicit opt-in. A corrective mechanism is off in exactly the regime that auto-enable targets.
- **Suggested fix**: Return the effective config from `run_composite_target_discovery` (or stamp `ctx.composite_target_discovery_config` / `metadata["composite_discovery_effective_enabled"]`) and use it in `run_recurrent_finalize_and_composite_post`.
- **Test to add**: Heavy-tail fixture with `enabled` unset. Assert that `_CT_ENSEMBLE__<target>` exists and matches the explicit-`enabled=True` run.
- **Disposition**: COMPLETED - the discovery phase publishes metadata['composite_discovery_effective_enabled'] and the three post-processing gates (value report, lag failsafe, cross-target ensemble) read config.enabled OR that flag, so an auto-enabled heavy-tail suite gets the same pipeline as an explicit opt-in; an explicit enabled=False still publishes nothing and stays off (test_auto_enabled_discovery_reaches_postprocessing.py, 4 tests)

### INT-05 [P1] Auto-chain transforms exist only in the training process's registry, so a pickled composite model fails in a fresh process
- **Where**: `composite/discovery/_opt_in_steps.py:248` (`_TRANSFORMS_REGISTRY.setdefault(cand.chain_name, ...)` at discovery time). `composite/estimator/_predict.py:216` (`get_transform(self.transform_name)` at predict time). `composite/discovery/_auto_chain.py:177` `reregister_auto_chain_transforms` is called only on the discovery cache-replay path (`core/_phase_composite_discovery.py:591-592`), never on load or unpickle.
- **What**: `auto_chain_discovery_enabled` defaults to True, and the repro's discovery surfaced `target-chain_linear_residual_cbrt-TVT_prev`. In-process, `get_transform("chain_linear_residual_cbrt")` resolves. After `dill.dump(cte)` and `dill.load` in a new interpreter, the same lookup raises `UnknownTransformError "Unknown transform 'chain_linear_residual_cbrt'. Registered: [...]"`. So `predict` on any such wrapper, or any `_CT_ENSEMBLE__*` component holding one, fails once INT-01/INT-02 are fixed, and fails today for callers who pickle the returned `models` dict themselves.
- **Why it matters**: A default-ON discovery feature produces models that cannot be served outside the training process.
- **Suggested fix**: Call `reregister_auto_chain_transforms` from `CompositeTargetEstimator.__setstate__` (or lazily inside `get_transform` for `chain_*` names), and from `load_mlframe_suite` / `predict_mlframe_models_suite` over the metadata specs' transform names.
- **Test to add**: A subprocess test that trains or constructs a CTE with an auto-chain transform, pickles it, and predicts in a fresh interpreter.
- **Disposition**: COMPLETED - the wrapper re-registers its own auto-chain transform on unpickle and the loaders re-register every transform named by the saved specs (dbe77db39; test_fresh_process_serves_every_composite_target)

### INT-06 [P1] The documented precomputed `composite_target_specs` fast path never trains any composite target
- **Where**: `core/_main_train_suite_phases.py:200-223` and `:599-609`. `training/_precompute.py:164,181-187,255-265` documents `bundle.composite_target_specs = prior_run_metadata["composite_target_specs"]`.
- **What**: When the bundle slot is truthy, discovery is skipped and only `metadata["composite_target_specs"]` is seeded. The docstring says "target_by_type is left unchanged because the caller-supplied specs imply the augmented targets already live in it". But the FTE only returns raw targets, and the forward-apply loop that materialises T columns into `target_by_type` (`core/_phase_composite_discovery.py:818-927`) lives inside the skipped function. Result: the per-target loop trains no composite model. Post-processing finds specs with no models, and metadata advertises composites that do not exist. `_init_composite_discovery_metadata` is also skipped, so `composite_target_failures`, `composite_target_filter_drops` and `composite_target_env_signature` are never initialised. Existing tests (`test_precomputed_bundle_deepcopy.py`, `test_main_train_suite_split.py:161-177`) only check the metadata copy.
- **Why it matters**: A documented reuse path silently discards the feature it is meant to speed up.
- **Suggested fix**: On the precomputed path, still run the forward-apply + dedup + global-cap section of discovery (the same code the cache-replay branch uses, including `reregister_auto_chain_transforms`), and run `_init_composite_discovery_metadata`. Alternatively, route precomputed specs through the existing `_CacheReplay` branch.
- **Test to add**: Train once, feed `metadata["composite_target_specs"]` into `TrainMlframeSuitePrecomputed` for a second run, and assert that the same composite target names appear in the returned `models`.
- **Disposition**: COMPLETED - caller-supplied specs are now replayed through the discovery phase exactly like a cache hit (same forward-applier, auto-chain re-registration, dedup and global cap) instead of only seeding metadata, and the replay runs even with enabled=False since reuse means skipping the search, not the training (test_precomputed_composite_specs_train.py, 4 tests; they fail at origin/master, where the phase has no such parameter)

### INT-09 [P2] Listing any grouped transform in `transforms` makes discovery raise, which removes every composite for that target
- **Where**: `composite/discovery/_eval.py:344` (`transform.fit(_y_train_valid, _base_train_valid)` with no `groups`, no try/except). `composite/transforms/_grouped_extra.py:37-41` (`_require_groups` raises). The exception propagates out of `_fit.py:616` to `core/_phase_composite_discovery.py` "fit failed", which records one failure and trains no composites.
- **What**: Direct `CompositeTargetDiscovery.fit` on a 400-row frame. `transforms=["linear_residual"]` gives `['y-linres-b']`. `transforms=["linear_residual", "quantile_residual_grouped"]` with `group_column="g"` raises `ValueError: quantile_residual_grouped.fit: groups kwarg is required`. The same holds for `ewma_residual_grouped`, `rolling_quantile_ratio_grouped`, `frac_diff_grouped` and `monotonic_residual_grouped`. The config accepts these names without validation, and `group_column` ("Also consumed by linear_residual_grouped") suggests they are supported.
- **Why it matters**: One unsupported entry silently disables discovery for the target (a WARNING through `log_throttle`, so it appears once per process).
- **Suggested fix**: Either thread `groups` (from `group_column`) into `eval_one_transform` and the forward-apply loop for `requires_groups` transforms, or reject them in a `transforms` validator. In either case, make `eval_one_transform` convert a per-transform fit error into a per-candidate rejection instead of aborting the whole fit.
- **Test to add**: The config above either yields `y-linres-b` plus a rejection row for the grouped transform, or fails config validation with a clear message.
- **Disposition**: COMPLETED. `eval_one_transform` rejects a `requires_groups` transform as a per-candidate ledger row: discovery screens without group labels, and the row points to `CompositeTargetEstimator(group_column=...)`. Any other evaluation error of one (base, transform) candidate likewise becomes that candidate's rejection, logged at WARNING and ledgered, instead of aborting the whole fit. Threading group labels through the screen, tiny rerank and honest gates was not done; that is a separate feature. `transforms=['linear_residual','quantile_residual_grouped']` with `group_column='g'` now yields `y-linres-b` plus a rejection row per base, where before it raised `groups kwarg is required`. Pinned by tests/training/composite/discovery/test_config_restriction_contract.py.

### INT-11 [P2] Specs dropped by the global `max_total_composite_targets` cap stay in `metadata["composite_target_specs"]` with no failure record
- **Where**: `core/_phase_composite_discovery.py:912-927`. Compare `core/_phase_composite_discovery_dedup.py:62-70`, where equivalence drops are removed from the exported specs and logged as failures.

- **Suggested fix**: Mirror the dedup helper. Remove capped specs from `metadata["composite_target_specs"][tt][target]` and append `{"name", "rejected": True, "reason": "global cap max_total_composite_targets=K"}` to `composite_target_failures`.
