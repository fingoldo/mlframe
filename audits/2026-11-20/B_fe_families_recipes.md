# Direction B: FE families and recipe replay (read-only audit)

Scope: fe_* families under `src/mlframe/feature_selection/filters/` (grouped agg / delta / quantile, lagged diff, pairwise modular, integer columns, binned numeric agg, conditional gate, offset product, row stat), the FE stage merge, the deadline module, and the recipe replay adapters in `engineered_recipes/`. MRMR.__init__ and `mrmr/_mrmr_class.py` were skipped per the standing decision. Earlier dispositions were checked in `audits/2026-11-16/_TRACKER.md`, `audits/2026-11-17/03_fe_data_signal.md` and `CLAUDE.md`; none of the findings below repeats a closed item.

Method: code read of each fit and replay pair, plus three small numpy one-liners that check the arithmetic (float32 subtraction, int64 product wrap, mod residue). No tests or heavy processes were run.

Verified and dropped: grouped agg and grouped delta fit/replay use the same `_broadcast_lookup` / `_map_group_keys` on both sides, and unseen-group and NaN handling match; the offset-product clip and fills are stored in the recipe and replayed; the `_fe_merge_new_columns` and hybrid fold keep-first rules are order-stable.

### F01 - float32 operand casts quantize within-group deltas and lagged diffs for offset columns
- **Severity**: High
- **Location**: `_ratio_delta_fe.py:268`, `_ratio_delta_fe.py:288-292` (grouped delta fit), `_ratio_delta_fe.py:337` (grouped delta replay), `_ratio_delta_fe.py:409` and `_ratio_delta_fe.py:460` (lagged diff fit and replay), `_grouped_agg_fe.py:152` and `_grouped_agg_fe.py:261` (grouped agg fit and replay), `_grouped_quantile_fe.py:267` (grouped quantile fit)
- **Problem**: Every one of these casts the source column with `dtype=_crit_np_dtype()`, which is `np.float32` by default (`_fe_usability_signal.py:154-165`). The subtraction `x - per_row_mean` (or `x_t - x_{t-p}`) then runs in float32. For a column whose level is large relative to its spread (prices, timestamps in seconds, sensor readings with an offset) the float32 ulp swamps the deviation. Fit and replay are both float32, so the recipe is self-consistent, but the stored feature is not the value the formula defines, and the selection can change silently. The grouped quantile `pct_rank` has the same issue: values that differ in float64 but round to the same float32 become ties.
- **Failure scenario**: Column `price` = 1000000.00 + 0.01 * k inside one group, with k = 0,1,2,3. Float64 gives the within-group deviation [-0.0156, -0.0156, -0.0156, +0.0469]. The float32 path (checked with numpy: `x - mean` on float32) gives [0, 0, 0, 0.0625]. The z-score for three of four rows is 0 where the true value is about -1.5 standard deviations, so the engineered column carries a different signal and MI can rank it differently from the float64 run. The same effect applies to lagged diffs of a level series near 1e6 and to a group whose true std is below the float32 ulp, which is replaced by the 1.0 fallback.
- **Suggested fix**: Keep the operand and the per-group mean/std in float64 for the subtraction (cast the centred values, `x - x.mean()` on the group, in float64 before the float32 narrowing, or centre by a per-column float64 offset before the cast). Add a regression test with a column offset of 1e6 and a 1e-2 spread that asserts the float64 deltas are reproduced to 1e-6 relative. Confirm the selection is unchanged on the benchmark set before shipping, per the selection-equivalence rule.
- **Disposition**: FIXED 2026-11-20 (subtractions) - the group-mean deviation, z-score, ratio and the lagged difference are computed in float64 and the stored column is narrowed after (`_ratio_delta_fe.py`, `_grouped_agg_fe.py`, `_grouped_coerce_shared.broadcast_lookup(dtype=)`); sensors in `test_float64_deviation_for_offset_columns.py` fail on the old code; benchmark selection identical (support, n_features, engineered). The grouped-quantile pct_rank and the broadcast stats are WON'T FIX: no subtraction is involved, a float32 tie needs two values within 6e-8 relative.

### F02 - lagged diff at replay is computed only inside the transform frame, so a new batch starts with zeros
- **Severity**: Medium
- **Location**: `_ratio_delta_fe.py:432-469` (`apply_lagged_diff`), with the fit side at `_ratio_delta_fe.py:354-430`
- **Problem**: `apply_lagged_diff` sorts `X_test` by time and computes the lag from rows inside `X_test` only. The fit-time column zeroes the first `period` rows of the TRAINING series. At transform time, the first `period` rows of whatever frame is passed get 0, even when the true previous observation sits in the training history. Nothing in the recipe carries the last training values, so the replay cannot see them. The recipe docstring describes this as "a pure function of the test frame", which makes the discrepancy a design choice that is not documented where users will meet it.
- **Failure scenario**: Fit MRMR on daily rows through 2020-12-31 with `fe_lagged_diff_periods=(1,)`. Transform a 2021 holdout that starts 2021-01-01. The first holdout row's diff is 0, not `x(2021-01-01) - x(2020-12-31)`. Transform a single new row (a live scoring call) and every lagged feature is 0. The model sees a non-zero distribution at fit and a column of zeros at serve time, with no error.
- **Suggested fix**: Persist the last `max(periods)` values per entity (sorted by time) in the recipe at fit, prepend them at replay, and drop the prepended rows before returning. Alternatively, raise or warn at transform when the frame is shorter than the max period or does not overlap the fit history, so the zeros cannot pass silently. Add a test that transforms one row and asserts the lag equals the fit-series lag.
- **Disposition**: OPEN

### F03 - pairwise modular products silently wrap int64 on large integer operands
- **Severity**: Medium
- **Location**: `_pairwise_modular_fe.py:442-456` (`_combine`, `prod` at 453 and `sum3` at 455), replay at `_pairwise_modular_fe.py:764-779`
- **Problem**: `_combine` multiplies two int64 arrays with no overflow guard. `_integer_columns.is_integer_like_col` admits any integer-valued column regardless of magnitude, and nothing in the modular path bounds the operands. numpy wraps int64 silently. The residue `np.mod(wrapped, m)` is then deterministic (so fit and replay agree) but is not `(a*b) mod m`, so the feature means something different from its name and is not a residue of the product at all. The integer-lattice sibling already guards its lcm for the same reason (`_integer_lattice_fe.py:150`), so this path is inconsistent with the codebase's own fix.
- **Failure scenario**: Two integer columns, `ts_ms` (Unix milliseconds, about 1.7e12) and `count`. The `prod` combiner computes `ts_ms * count` in int64; with `ts_ms` about 1.7e12 the product exceeds 9.2e18 and wraps. Checked with numpy: for `a` = 1700000000000 + 0..9 and `b = a + 3`, all 10 residues mod 10 differ from the exact `(a*b) mod 10`. The engineered column is noise that can still pass the MI gate by chance and be selected.
- **Suggested fix**: Detect overflow before combining: compute the product in float64 (or Python int via object dtype on the few rows that exceed `2**62`) and mark rows whose magnitude exceeds the safe bound as NaN, or skip the `prod`/`sum3` ops for a column pair whose max absolute values make `max|a|*max|b| >= 2**63`. Add a test with ms timestamps asserting that the residue equals the exact modular product or is NaN.
- **Disposition**: OPEN

### F04 - optional-enrichment deadline stops the sweep silently, so the engineered set depends on wall-clock time
- **Severity**: Medium
- **Location**: `_binned_numeric_agg_fe.py:442-447` (group-column loop break), `_conditional_gate_fe_helpers.py:45-52` (gate-column loop break), `_cat_confirm_bandit.py:246-248` (UCB shuffle loop break)
- **Problem**: When `fe_deadline_passed()` is true these loops `break` and return what they have. None of the three logs anything at the point of the break (the step-level skip in `_mrmr_fe_step/_step_score_parts2.py:39` logs that a whole stage was skipped, but not that columns or pairs were dropped inside it). The group columns are visited in a fixed order (`_visited_group_cols`), so the cutoff drops the late-ordered columns entirely. The cut point is set by machine speed, so two runs of the same fit on the same data can select different features with no trace in the log. The bandit break is subtler: pairs keep the shuffle counts they had, so their p-values rest on fewer permutations than the others, which the code treats as valid evidence without recording it.
- **Failure scenario**: `max_runtime_mins` is set so the budget expires during the binned-aggregate sweep. The sweep stops after group columns `a` to `f`; `g` to `z` produce no candidates and nothing is logged. A rerun on a faster machine finishes the sweep and selects a column from `g` to `z`. The user sees two different supports and no warning that the first one was truncated.
- **Suggested fix**: Log once (`log_throttle`, WARNING level when a budget is in force) with the number of group columns or pairs skipped and the stage name at each break. Record the truncation in the fit report (for example an `fe_budget_truncated_` attribute listing the stages that broke early). For the bandit, report the minimum shuffle count across pairs when the loop exits on the deadline. Test with a deadline already expired at entry and assert the warning and the attribute.
- **Disposition**: OPEN

### F05 - lagged diff turns a missing value into "no change" (0) for the row and its successor
- **Severity**: Low
- **Location**: `_ratio_delta_fe.py:420` (fit) and `_ratio_delta_fe.py:469` (replay)
- **Problem**: `np.nan_to_num(diff, nan=0.0)` maps a NaN difference to 0. A missing current or lagged value therefore produces the same output as a flat series, and the following row's lag is NaN again. Fit and replay agree, so this is not a train/transform split, but the feature encodes "missing" as "unchanged" and MI gates cannot separate the two.
- **Failure scenario**: `value` = [5, NaN, 7, 9] with period 1. The diffs are [0, 0, 0, 2]: the NaN row and the row after it both read as "no change", while the true diffs are undefined and 2. For a sparse sensor, a column that is 60% missing gets a large mass at exactly 0, which can rank well for a target that is itself often flat.
- **Suggested fix**: Keep NaN where either operand is NaN (let the downstream imputer or the MI binner handle it), or carry a separate missing-indicator. Add a test asserting NaN at the masked rows. This changes the output of rows that currently read 0, so it needs the selection-equivalence check.
- **Disposition**: OPEN

### F06 - integer-column eligibility cache keyed on a 64-row fingerprint can answer for a different frame
- **Severity**: Low
- **Location**: `_integer_columns.py:77-94` (`_fingerprint` and the cache key)
- **Problem**: The cache key is `(len(X), columns, hash of 64 evenly spaced rows)`. Two frames with the same length and column names whose values agree on those 64 rows but differ elsewhere share an entry, and the cached per-column verdict (`known[c]`) is returned for the second frame without rescanning. The cache is process-wide (LRU of 4), so a second fit in the same process can inherit an integer verdict from a different dataset.
- **Failure scenario**: Fit 1 on a frame with a column that is integer-valued everywhere. Fit 2 in the same process on a frame of equal length and column names where that column is continuous except at the 64 sampled rows (for example, a copy that was edited in the middle). Fit 2 still treats the column as integer, so the pairwise-modular and lattice sweeps build residues from rounded continuous values.
- **Suggested fix**: Include a full-column checksum for the columns actually queried (for example a hash of the whole column's bytes, which is one linear pass and cheap next to the MI work), or key the entry by column object identity plus a version counter. Add a test with two frames that differ only outside the sampled rows and assert the second verdict is recomputed.
- **Disposition**: OPEN
