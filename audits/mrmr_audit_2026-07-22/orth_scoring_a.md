# orth_scoring_a: CMIM / JMIM / three-gate-OOF / bootstrap-MI / adaptive-arity / adaptive-degree / total-correlation / KSG / copula / dCor / HSIC scorer-zoo FE

This cluster covers 11 opt-in scorer-zoo members of the "hybrid orth-poly FE" family (Layers 57/62/63/65/66/67/71/72/73/74/78):
`_orthogonal_cmim_fe.py`, `_orthogonal_jmim_fe.py`, `_orthogonal_three_gate_mi_fe.py`, `_orthogonal_bootstrap_mi_fe.py`,
`_orthogonal_adaptive_arity_fe.py`, `_orthogonal_adaptive_degree_fe.py`, `_orthogonal_total_correlation_fe.py`,
`_orthogonal_ksg_mi_fe.py`, `_orthogonal_copula_mi_fe.py`, `_orthogonal_dcor_fe.py`, `_orthogonal_hsic_fe.py`. Each
module swaps out either the MI **estimator** (plug-in vs KSG k-NN vs copula-rank vs dCor vs HSIC) or the **selection
rule** (marginal uplift vs JMIM/CMIM redundancy-aware min vs K-fold-OOF three-gate vs bootstrap-LCB vs adaptive
per-column degree/arity search vs Watanabe total-correlation) on top of the SAME `generate_univariate_basis_features`
engineered-column pool Layer 21 produces, then emits `EngineeredRecipe`s so `MRMR.transform()` can replay each
appended column deterministically. None of these families are wired into `MRMR.fit` by default; each is behind its
own `fe_hybrid_orth_*_enable=False` flag.

**Prior-audit cross-reference.** The 2026-07-20 audit's `c7b_orth_scoring_fe.md` covered this exact file set and found
B-17 (missing frozen fit-time `preprocess_params` -> transform-time replay drift) and B-18 (label-truncation
destroying fractional/continuous-y signal) across most of the scorer zoo. Commits `f067e0d44` (B-17) and `2cc59a6b1`
(B-18) fixed the **univariate** `*_with_recipes` builders in all 11 files here -- verified directly: every
`_coerce_y_int64`/`_coerce_y_classif` helper in this cluster now densifies via `np.unique(return_inverse=...)`
(B-18 closed), and every univariate recipe-build call now threads `preprocess_params=_pp` recomputed via
`_evaluate_basis_column(..., return_params=True)` (B-17 closed for the univariate path). The one gap the "fix"
commit left behind is ORTH_SCORING_A-1 below. The adaptive-arity GPU-resident fallback's unlogged
`except Exception: return None` at `_orthogonal_adaptive_arity_fe.py:412` (prior report's own P2) is unchanged --
still open, no new severity assigned here. mypy is clean on all 11 files (`Success: no issues found in 11 source
files`); no file in this cluster exceeds the ~800-900 LOC guideline (`_orthogonal_adaptive_arity_fe.py` is the
largest at 769 LOC). Angle 9 (SQL/HTTP/UI): confirmed N/A -- no DB/network/UI/telemetry surface in any of the 11
files; the only "generated artifact" is the returned scores `DataFrame` and the `EngineeredRecipe` objects, neither
of which does string interpolation into HTML/markdown/log messages built from untrusted feature-name content beyond
plain `%r`/`%s` logging (safe).

## Proposals

- **(coverage_gap)** Fix ORTH_SCORING_A-1 by adding `preprocess_params_i/j` (arity 2), `preprocess_params_i/j/k` (arity 3), `preprocess_params_i/j/k/l` (arity 4) to the three recipe-build call sites in `hybrid_orth_mi_adaptive_arity_fe_with_recipes`, computed the same way the arity==1 branch already does (recompute `_evaluate_basis_column(X[leg].to_numpy(), basis, degree, return_params=True)` once per distinct leg -- a leg shared across several winning tuples should be recomputed once and cached, mirroring the triplet/quadruplet siblings' per-leg dedup). Add a `TestRecipeFreezesPreprocessParams`-style slice-replay regression test (model directly off the one added to `test_jmim.py` in commit `f067e0d44`) for arity 2, 3, and 4 to close ORTH_SCORING_A-2 in the same change, per CLAUDE.md's "every bug fix ships a regression test" rule.
- **(coverage_gap)** Add a lightweight grep-based CI gate (proposed already in the 2026-07-20 report for the univariate case, worth widening now): flag any `EngineeredRecipe(kind="orth_pair_cross"/"orth_triplet_cross", ...)` or `build_orth_quadruplet_cross_recipe(...)` call whose `extra`/kwargs do not include the corresponding `preprocess_params_*` keys. This exact "fix landed on the univariate copy, not the multi-leg copy" failure mode is now confirmed to have slipped through code review once already (the B-17 fix commit itself); a static check would catch it mechanically.
- **(fe_idea)** KSG/copula/dCor/HSIC (Layers 65/66/67/71) score every candidate purely against its own raw source baseline; unlike CMIM/JMIM/three-gate/TC (Layers 63/72/73/74) they never accept a `current_support` parameter for redundancy-aware ranking. Given the four estimators are already proven complementary dependence measures, threading `current_support` through them (redundancy gate via e.g. `KSG-CMI` / partial-dCor) would let the auto-scorer/ensemble bake-off (Layers 68/69, outside this cluster) compare apples-to-apples redundancy-aware scores across all 8 marginal + redundancy-aware families instead of mixing marginal-only and redundancy-aware scorers in one ranking.
- **(edge_case)** `_orthogonal_total_correlation_fe.py`'s `_build_support_bins` bins the support DataFrame via the scalar per-column `_quantile_bin` loop even though the same file already has a batched `_bin_dataframe_batched`/`_quantile_bin_batched` fast path used for the candidate columns. Support sets are typically small (a handful of already-selected features) so the win is modest, but reusing the existing batched helper here would be a one-line simplification with no behavioural change (same bit-identity contract already established for the candidate-column path).
