# FE Step B audit -- `_mrmr_fe_step/_step_pairmi.py`, `_step_pairs_rank.py`, `_step_score.py`

## Scope

These three modules are the middle third of `MRMR._run_fe_step` (the FE-pair pipeline), carved verbatim
out of `_step_core.py` on 2026-06-22 (commit `1355bb4b2`) to keep that module under the 1k-LOC ceiling.
`_step_pairmi.py` (523 LOC) runs the engineered-operand feed-forward cap, dispatches the batched/legacy
pair-MI sweep (CUDA/CPU/loky), and computes the order-2 Westfall-Young maxT permutation-null floor.
`_step_pairs_rank.py` (746 LOC) ranks gate-surviving candidate pairs by joint-MI uplift, resolving the
prevalence + maxT + synergy + usability-admission gate state per pair (with a batched usability pre-pass)
and produces the `prospective_pairs` ranking plus the prevalence-rescue ledger for auto-escalation.
`_step_score.py` (1131 LOC) is the back half: the conditional-MI redundancy gate, two over-materialization
prunes, the discretize+append+recipe-build materialize loop, auto-escalation, C2 additive-fusion, and the
cross-fold stability vote. All three are pure orchestration/dispatch code over numpy arrays and dicts --
no DB, network, or browser-facing surface exists anywhere in this cluster (confirmed by full read); items
7/9 of the checklist (security / SQL-HTTP-UI) are N/A here beyond the generic env-var-gated feature-flag
pattern already used throughout the package, which is not attacker-reachable input.

Prior audit cross-reference: grepped `audits/mrmr_audit_2026-07-20/`, `audits/full_audit_2026-07-21/`, and
`_benchmarks/mrmr_critique_2026_07/` for these three filenames. Only two hits, both already resolved on
current HEAD (see table). The bulk of this cluster's code (the usability-admission batching, the CMI
redundancy-gate filtering, the gate-composite/cross-group over-materialization prunes, C2 additive-fusion,
the cross-fold stability vote) postdates or was never touched by the 2026-07-20 audit, so this report is
almost entirely new-finding territory rather than a re-verification pass.

| FE_STEP_B-2 | P1 | efficiency / design flaw | `_step_pairmi.py:491-521` | The "auto" prevalence-debias fallback (fires when `fe_min_pair_mi_prevalence=="auto"` and the maxT-floor path left `_pair_mm_bias` empty, i.e. `fe_mm_debias_prevalence=False`) does `_auto_pairs = list(combinations(numeric_vars_to_consider, 2))` -- a full, unchunked O(k^2) materialization of every candidate pair as Python tuples, then runs `pairwise_mm_joint_bias` over the whole array in one call. This directly contradicts the module's own stated design one screen up (comment at line 122-125: "avoiding `list(combinations(...))` materialisation (O(k^2) tuples, ~300 MB at k=5000)... before chunking even starts") and the "NO POOL-SIZE CAP (removed 2026-07-09)" rationale (lines 143-151) that explicitly exists to prevent exactly this "catastrophic-runtime cliff" at a wide production pool. At k=5000-10000 (a realistic post-multi-step operand pool per that same comment) this allocates 12.5-50M tuples/array entries with no RAM-bounded chunking, unlike every other pair-consuming code path in this file (`dispatch_batch_pair_mi_chunked`, `_lazy_chunks`). Note the sibling `compute_pair_maxt_floor` (in `_mrmr_fe_step_helpers.py`, out of this cluster's scope) has the identical `list(combinations(...))` pattern by default whenever `fe_pair_maxt_null_permutations>0` and `n_pairs>=fe_pair_maxt_min_pairs` -- both are default-on -- so this is not an isolated slip but a recurring anti-pattern across the pair-MI-floor machinery; flagging the instance that is in-scope here. | NEW |
| FE_STEP_B-3 | P1 | correctness / robustness | `_step_pairmi.py:196-201` (write), `_step_pairs_rank.py:281,537` (defensive sorted-read) | `cached_MIs` pair-tuple keys are never canonicalized on write anywhere in this cluster (`cached_MIs[_p] = ...` with `_p=(int(_pair_a_arr[_i]), int(_pair_b_arr[_i]))`, ordered by whatever position `numeric_vars_to_consider`'s current iteration yields) -- yet `numeric_vars_to_consider` is rebuilt as a **brand-new** `set` object every FE step (`build_fe_operand_pool` in the sibling `_step_pool.py`, called fresh from `_step_core.py` each of the `num_fs_steps` iterations, does `set(numeric_vars_to_consider) - set(categorical_vars)` and further `&`/`-` ops). Empirically confirmed that Python's set iteration order is **not** guaranteed ascending once a set mixes small and large ints (e.g. raw indices 0-19 plus later-appended engineered indices like 105/210/999): `list(combinations(set(range(20)) | {87,105,210,999}, 2))` yields inverted pairs such as `(210, 87)`. Since `cached_MIs` is the *same* dict object threaded through every FE step and finally stored to `self.cached_MIs`, a pool that includes the same logical pair `{a,b}` in two different FE steps (or after any of the several `set(...) - ...` reconstructions inside `compute_pair_mis_and_floor` itself) can legally produce **two divergent dict entries**, `(a,b)` and `(b,a)`, for one physical variable pair -- doubling MI computation, doubling `checked_pairs`/`vars_usage_counter` bookkeeping in `score_prospective_pairs`, and potentially yielding two independently-scored (and for asymmetric binary forms like `div`/`sub`, genuinely different) engineered columns for what should be one candidate. The codebase is clearly aware pair-key order is not trustworthy -- `_pair_mm_bias` is written with `tuple(sorted(...))` (`_step_pairmi.py:519`, `_mrmr_fe_step_helpers.py:470`) and read the same way in `_resolve_pair_prevalence_gate` -- but that discipline was never applied to `cached_MIs` itself, the structure this whole pipeline treats as the pair identity. Reachable under `fe_max_steps>1` (a supported, non-default config); default `fe_max_steps=1` fits are unaffected because the operand pool is built once. | NEW |
| FE_STEP_B-4 | P1 | efficiency | `_step_pairs_rank.py:356` and `:521` | `score_prospective_pairs` calls `sort_dict_by_value(cached_MIs)` twice over the identical, unmutated dict: once inside `_prepass_gate_and_usability_candidates` (to build `_gate_cache`/`_need_usability`), and again at the top of the main loop. `pyutilz.pythonlib.sort_dict_by_value` does a full `sorted(dct.items(), ...)` plus a dict-comprehension rebuild -- O(n log n) time and a full O(n) copy of the whole `cached_MIs` structure (singles + all pairs) -- run twice for no reason, since `cached_MIs` is not written to between the two calls. At the pool sizes this file's own comments target ("thousands-to-low-hundred-thousands pairs"), this is a clean, mechanical duplicate-work bug of exactly the class this same file's other 2026-07-11 perf-fix comments (operand-cache memoization, single-corr-cache memoization, batched usability pre-pass) were written to eliminate. Trivial fix: compute the sorted view once and pass/reuse it in both places. | NEW |

## Proposals

- Fix FE_STEP_B-1 by mirroring the exact pattern already applied at `_step_score.py:547-556`: compute `_safe_code_dtype(self.quantization_nbins, self.quantization_dtype)` once and allocate `_esc_new_codes`/`_fz_codes` at that widened dtype, then narrow only at the final `data`/`X` append via the existing `.astype(data.dtype, copy=False)` step (which already exists for `data` and should be added for the `X[...] = ...` assignments too). Add a regression test that actually drives `materialise_and_finalise_fe_candidates` (or a full `MRMR().fit()`) through the escalation and additive-fusion paths under `quantization_dtype=np.int8`, `quantization_nbins=200`, asserting no negative codes -- the existing `test_step_score_discretize_batch_and_dtype_wrap_fix.py` only tests the isolated helper, not either live call site.
- Fix FE_STEP_B-2 by routing the "auto" debias fallback through the same `dispatch_batch_pair_mi_chunked`-style row-block chunking already used for the primary pair-MI sweep, or by capping it with the same `_MRMR_BATCH_PRECOMPUTE_MIN_PAIRS`-style pair-count gate and falling back to per-chunk `pairwise_mm_joint_bias` calls above that.
- Fix FE_STEP_B-3 by canonicalizing every `cached_MIs` pair-key write to `tuple(sorted(pair))` at the point of insertion (both in `compute_pairs_mis` in `feature_engineering.py`, out of this cluster, and in the batch-precompute write loop here at `_step_pairmi.py:196-201`), then dropping the now-redundant `tuple(sorted(...))` calls scattered around `_pair_mm_bias` lookups once the invariant holds everywhere. A cheap regression test: run a `fe_max_steps=2` fit on a synthetic pool sized so the operand-pool set mixes small and large column indices (e.g. after one step's engineered columns are appended) and assert `len({tuple(sorted(k)) for k in cached_MIs if len(k)==2}) == len([k for k in cached_MIs if len(k)==2])` (no two keys collapse to the same sorted pair).
- Fix FE_STEP_B-4 by hoisting `_sorted_pairs = sort_dict_by_value(cached_MIs)` once in `score_prospective_pairs` and passing it into `_prepass_gate_and_usability_candidates` instead of recomputing.
- Consider FE_STEP_B-9's fix (top-K-by-MI prescan instead of first-256-by-insertion-order) as a one-line change once FE_STEP_B-4's hoisted sorted view exists -- it would double as the prescan's candidate source at zero extra sort cost.
- Consider carving FE_STEP_B-11's two prune blocks into a `_step_score_prunes.py` sibling next time this file is touched for an unrelated change, to keep draining the LOC-budget exempt list the way the rest of this refactor wave already has for every other sibling.
