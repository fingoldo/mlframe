# FE Pairs Core — audit (2026-07-22)

## Scope

`src/mlframe/feature_selection/filters/_feature_engineering_pairs/` — the FE unary+binary
pair-search subpackage carved out of the legacy `feature_engineering.py` monolith. This is the
engine behind MRMR's engineered-feature step: for every prospective raw-variable pair it builds a
per-operand unary pool (library unaries + the optional learned `prewarp` / adaptive `gate_med`
pseudo-unaries), evaluates every configured binary operator on top, scores each resulting column's
MI against the (optionally subsampled/stratified) target via a batched CPU-njit/GPU dispatch with a
permutation noise-gate, and admits the winning form(s) once they clear the joint-prevalence gate or
one of three additive-recall fallback gates (prewarp-uplift, marginal-uplift, tail-concentration
usability). Admitted pairs are packed into survivor columns + leak-safe recipes for `_mrmr_fe_step`.
The ten files split cleanly: `_pairs_common` (shared logger/lock), `_pairs_gates` (thresholds +
`_select_single_best` winner picker), `_pairs_materialise` (njit column-fill kernels + op-code
registry), `_pairs_dispatch` (CPU/GPU noise-gate routing), `_pairs_chunks` (cross-pair batch
planning + execution), `_pairs_setup` (prewarp/gate_med fitting + operand-table build),
`_pairs_core` (the orchestration loop + GPU-gate predicates), `_pairs_score` (per-pair
scoring/acceptance-gate body), `_pairs_emit` (admitted-pair survivor emission), and `__init__.py`
(facade re-export).

This is an extremely heavily-audited and heavily-instrumented cluster: the 2026-07-20 audit's
`c4_gpu_infra.md` / `test_coverage.md` / `edge_cases.md` / `fe_expansion.md` / `c7d_fe_orchestration.md`
already cover large parts of it, and the mypy backlog for every file here (`_pairs_gates.py`,
`_pairs_chunks.py`, `_pairs_emit.py`, `_pairs_materialise.py`, `_pairs_dispatch.py`,
`_pairs_setup.py`, `_pairs_core.py`, `_pairs_score.py`) was already closed to 0 by commits
`9efc8e541` / `e342ed106` / `08a4ccf2e` / `ab0229229` / `21a233a09` / `e6fb1a96a` / `3e83e4f76` /
`6759281b7`. A fresh `mypy --cache-dir=.mlframe_mypy_cache_shared` run over all 10 files today
confirms **0 errors**. The code is exceptionally densely commented with rationale, prior
bench-attempt-rejected notes, and prior bug postmortems, which made most obvious bug classes
already-fixed; the findings below are the residue after cross-referencing the two prior audit
generations plus a full line-by-line read of all 10 files.

| FE_PAIRS_CORE-1 | P1 | thread-safety / test-coverage | `_pairs_core.py:1040-1075`, `_pairs_score.py:208-272`, `_gpu_resident_materialise.py:336,357` | The 2026-07-02 "chunk pipeline" feature spins up a `ThreadPoolExecutor(max_workers=1)` that computes chunk *k+1* (`_produce` → `_compute_one_fe_chunk`, which reaches into `_gpu_resident_fe`/`_gpu_resident_materialise` helpers) **concurrently** with the main thread consuming chunk *k* (which itself calls `_resolve_col` → `_resident_operand_table`). | FE_PAIRS_CORE-2 | P1 | efficiency / hot-loop hygiene | `_pairs_core.py:123-198`; called from `_pairs_score.py:427,510,534` and `_pairs_chunks.py:225,354` and `_pairs_emit.py:375` | `_fe_gpu_discretize_enabled` / `_fe_gpu_binning_enabled` are **not** hoisted per-call the way their sibling `resolve_fe_dispatch_env_gate()` explicitly is (see the "PER-CALL HOISTS" comment at `_pairs_core.py:1083`, threaded down as `_fe_env_gate`). Instead they are called up to 3x per pair in the per-pair path, once per chunk, and once per ext-val tied-leader-set — each call re-reads 1-2 env vars, imports+calls `is_cuda_available()`, and (on the default `"auto"` setting) imports+calls a `kernel_tuning_cache`-backed backend-choice lookup. This directly violates the repo's own documented rule ("Hoist the dispatch decision out of hot loops (~4us/call overhead adds up)"). Compounding it, the per-pair GPU-fused-materialise block in `_pairs_score.py:405-424` unconditionally builds the whole `(a_cols, b_cols, ops, _gpu_cands)` candidate-spec lists *before* checking `_fe_gpu_binning_enabled` — on a CPU-only host (or any host where the KTC declines GPU below the crossover) that list-construction work is thrown away and is redundantly re-done by the CPU fallback loop immediately below it (`_pairs_score.py:453-486`). Actual wall-clock impact is unmeasured (no profiling was run as part of this read-only audit) but the pattern is unambiguous by inspection and touches every pair of every fit. | New — the analogous noise-gate dispatcher hoist (`_fe_env_gate`) was clearly added deliberately (its own comment cross-references the pattern), but the GPU-discretize/binning gates were left un-hoisted across three call sites; not flagged in either prior audit generation. |
| FE_PAIRS_CORE-3 | P2 | correctness (comment/behavior mismatch) | `_pairs_setup.py:187-215` | The comment "Reject no-variance operands (a constant gate is dead)" does not match the code: the only guard is `if not np.isfinite(_gmed): continue` (rejects all-NaN/empty operands). A literal **constant, non-NaN** numeric operand (e.g. a degenerate/dummy column) has a well-defined finite median and is *not* rejected — it gets registered under the `gate_med` pseudo-unary and materialises an all-zero dead column (`(x > median) == False` everywhere when `x` is constant) that then participates in every binary combo for that operand. Not silently wrong (the dead column's MI is 0 and it is later dropped by the joint-prevalence gate / the emit-tail's non-constant `std<=1e-9` guard at `_pairs_emit.py:659`), just wasted unary+binary+MI-sweep work for every constant column in the frame whenever `fe_gate_med_enable=True` (opt-in, default OFF), and a maintainer reading the comment would incorrectly believe the guard already exists. | New. |
| FE_PAIRS_CORE-4 | P2 | edge case (approximation only, opt-in feature) | `_pairs_core.py:511-517` | When `_use_subsample` is active, `freqs_y` is recomputed as `np.bincount(classes_y.astype(np.int64))` **without** `minlength=`. If the random subsample happens to drop every row of the numerically-highest class label, the recomputed `freqs_y` (and hence `k_y = freqs_y.shape[0]`, used at `_pairs_core.py:1096` for `mi_tie_band` and inside `mm_debiased_prevalence_ratio` when `fe_mm_debias_prevalence=True`) silently under-counts the true class count by the number of missing trailing labels. This cannot index-error (every consumer derives its bounds from the same subsampled `classes_y`), so it only skews the MM-debias / tie-band width — a purely cosmetic mis-calibration of an already-opt-in, default-OFF debias knob (`fe_mm_debias_prevalence=False`). Flagged for completeness rather than as a live bug; a `minlength=int(np.asarray(freqs_y).shape[0])` (using the pre-subsample width) would remove the ambiguity cheaply. | New; low-confidence/low-impact — recorded as an edge-case observation, not a verified failure. |

## Proposals

- **Hoist `_fe_gpu_discretize_enabled`/`_fe_gpu_binning_enabled` once per `check_prospective_fe_pairs` call**, mirroring the existing `resolve_fe_dispatch_env_gate()` → `_fe_env_gate` pattern: resolve both to plain bools (or a small `NamedTuple`) once, thread them down as parameters instead of re-deriving them at every call site. This directly retires FE_PAIRS_CORE-2 and is a small, mechanical, low-risk change (all call sites already receive several other per-call-hoisted values the same way).
- **Reorder the per-pair GPU-fused-materialise block** in `_pairs_score.py` so the cheap enablement check runs *before* building the `(a_cols, b_cols, ops)` lists, not after — avoids the wasted list-construction on any host/size where GPU is unavailable or below the KTC crossover (the common CPU-only case).
- **Add a `MLFRAME_FE_PIPELINE_CHUNKS=1` regression test** (even a CPU-fallback-only smoke test that forces `fe_gpu_strict_enabled()` True via monkeypatch and asserts selection is byte-identical to the non-pipelined path on a small fixture) before this feature sees any real traffic — it is the only concurrency-introducing code change in this whole cluster and currently has no dedicated coverage of any kind.
- **Fix the stale `gate_med` comment** in `_pairs_setup.py` (either add the variance guard the comment promises, or reword the comment to match reality) — cheap, and removes a genuine trap for the next person who trusts the comment instead of re-reading the code.
- Consider passing `minlength=` to the subsample `np.bincount(classes_y...)` recompute (FE_PAIRS_CORE-4) — a one-line defensive fix with no behavior change on the common path (every class represented).
- The huge (60+ parameter) `check_prospective_fe_pairs` signature is fully docstring-documented but almost entirely un-annotated (bare `prospective_pairs`, `X`, `cols`, etc.). mypy is clean today because the project's config does not enable `disallow_untyped_defs` on this module, but if that gate is ever tightened this function (and `_score_one_pair`'s similarly large kwarg-only signature in `_pairs_score.py`) would be the first to fail. Not urgent, but worth noting as the type-hint-completeness item this cluster's dense docstrings otherwise satisfy well.

## Checklist confirmations

- **CPU/GPU parity**: every GPU twin found in this cluster (`_materialise_chunk_njit` vs the fused GPU materialise, `_dispatch_batch_mi_with_noise_gate`'s CPU/GPU branches, the resident-CUDA noise-gate) carries an explicit "bit-identical / maxdiff 0" claim backed by a cross-reference to a dedicated test file (`test_fe_narrow_code_dtype.py`, `test_gpu_resident_extval.py`, `test_batch_pair_mi_*`, etc.); spot-checked several of these claims against the actual kernel bodies and found the arithmetic genuinely matched (float32 ops, float64-promoted div/ratio_abs, identical `nan_to_num` semantics) — no parity gap found.
- **Security / SQL / HTTP / UI**: confirmed N/A. No DB access, no network calls, no HTML/report generation, no `eval`/`exec`/`subprocess`/`os.system`, no pickle/joblib/yaml deserialization of untrusted data anywhere in these 10 files. The only "generated artifact" is Python log messages (`logger.debug`/`logger.warning` with user column names via `cols[var]`) — these are plain `%s`-style logging calls (not string-interpolated into anything executed or rendered), so no injection surface.
- **Determinism/reproducibility**: the external-validation factor subsample uses a locally-seeded `np.random.default_rng(subsample_seed)` (not the process-global RNG) and the raw-pair iteration order is a plain dict (insertion-ordered, not hash-ordered); the one place a bare Python `set` was previously iterated for column ordering (`this_pair_features`) is already sorted by feature name before use (`_pairs_emit.py:599-602`) specifically to avoid `PYTHONHASHSEED`-dependent ordering — this was clearly already fixed by a prior wave and holds up under this reading.
- **Edge cases** (empty input / all-NaN / constant column / single row): the `gate_med` all-NaN case is correctly guarded (`np.isfinite(_gmed)` continue); the constant-but-finite case is the FE_PAIRS_CORE-3 gap above. Zero-row / zero-pair inputs short-circuit cleanly (`if not perf: return None` in `_select_single_best`; `if col == 0: return out` in `_compute_one_fe_chunk`). No crash paths found for degenerate inputs during this review.
