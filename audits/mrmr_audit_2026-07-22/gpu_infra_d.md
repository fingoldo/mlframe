# GPU Infra D — hinge/fusion/pure-form GPU-resident twins, CMI perm-null GPU, polynom-pair optimizers, batched pair-MI dispatch

This cluster covers 9 files (3,211 LOC total, none over the ~800-900 LOC guideline; largest is
`_numba_polynom_optimizer.py` at 785 LOC): three "STRICT-resident" GPU twins of host FE stages
(`_hinge_detect_gpu_resident.py` + its batched precheck sibling `_hinge_detect_gpu_resident_batch.py`,
`_fe_additive_fusion_gpu_resident.py`, `_fe_pure_form_retention_gpu_resident.py`), the GPU-resident
permutation-null estimator for the CMI redundancy gate (`_fe_cmi_perm_null_gpu.py`), the two
polynomial-pair coefficient-search backends for hermite/orthogonal-basis pair-FE
(`_cupy_polynom_optimizer.py` and its numba/CPU twin `_numba_polynom_optimizer.py`), and two
older GPU dispatch entry points split out of `gpu.py` for size (`_gpu_batched.py`'s batched/streamed
permutation-MI kernels, `_gpu_pairs.py`'s multi-pair batched joint-MI kernel for cat-FE). All files
are pure numerical/GPU-kernel code — confirmed via full read + grep (`eval(`/`exec(`/`subprocess`/
`os.system`/`pickle.`/`yaml.load`/`dill.` all absent) that there is no DB, network, or
HTML/UI-report surface anywhere in this cluster, so SQL/HTTP/UI best-practice angles are N/A.
`mypy --cache-dir=.mlframe_mypy_cache_shared --ignore-missing-imports` is clean on all 9 files
(0 errors). Five files were already covered by the 2026-07-20 audit (mostly for residency/subsample
angles); this pass cross-references those and adds findings from applying the full checklist
(CPU/GPU parity, RNG-seed reproducibility, thread-safety of module globals, missed vectorization,
API-contract consistency) that the prior pass did not systematically run over every file.

| GPU_INFRA_D-2 | P1 | thread_safety | `_gpu_pairs.py:204` (sibling: `_batch_pair_mi_cuda_shared_fused.py:208`, outside this cluster) | `_gpu_module.compute_joint_hist_multi_pair_shared_cuda.max_dynamic_shared_size_bytes = _needed_shared_bytes` mutates a process-wide, module-level `cp.RawKernel`/compiled-function object's CUDA driver attribute with no lock. Two threads calling `mi_direct_gpu_batched_pairs` concurrently (e.g. two `MRMR.fit()` calls in different threads of the same process) with different `_needed_shared_bytes` requirements can race: thread A sets its (larger) budget, thread B's smaller value overwrites it before A's own `compute_joint_hist_multi_pair_shared_cuda(...)` launch enqueues, so A's kernel runs under-provisioned relative to what its `extern __shared__` access pattern needs — an out-of-bounds shared-memory read/write inside the kernel (silently wrong joint-histogram counts, or a CUDA crash). Only triggers when the module's own single-call-per-fit assumption is violated by cross-thread concurrency AND `max_joint_size_y` differs between the racing calls (small/typical joint sizes never touch this opt-in branch, since it's gated behind `_needed_shared_bytes > 49152 - 2048`). | NEW — not raised by the 2026-07-20 audit for this file. |
| GPU_INFRA_D-3 | P1 | cpu_gpu_parity | `_numba_polynom_optimizer.py:634` and `:726` | `run_numba_kernel_search` and `optimize_all_pairs_numba_kernel` both do `rng = np.random.default_rng(seed if seed > 0 else 1)`, silently substituting `1` for any `seed <= 0` — including the very common, perfectly valid `seed=0`. The cupy twin `run_cupy_kernel_search` (`_cupy_polynom_optimizer.py:217`) uses `np.random.default_rng(seed)` directly, with no such substitution. So `fe_optimizer="numba_kernel"` and `fe_optimizer="cupy_kernel"` called with the identical `seed=0` draw from *different* RNG seeds (0 vs 1) — a genuine, silent CPU/GPU reproducibility divergence for the most ordinary seed value, and a violation of the "seeded-RNG reproducibility" contract in its own right (any two callers passing `seed=0` vs `seed=-7` also collide onto the identical stream). Currently not reachable through the one production call site (`polynom_pair_fe.py:385` always passes `seed=42 + seed_offset`, so never <= 0), but both functions are public API entry points (also directly unit-tested), so a caller/test invoking `seed=0` today already hits the divergence. | NEW. |
| GPU_INFRA_D-4 | P1 | cpu_gpu_parity | `_fe_additive_fusion_gpu_resident.py:312` (CPU counterpart: `_fe_additive_fusion.py:326`) | The OLS multiple-R separability razor's margin is `getattr(self, "fe_additive_fusion_ols_r_margin_sd", 2.0) / max(sqrt(n_sc), 1.0)` where `n_sc` is the *scoring-subsample* row count (`≤ MLFRAME_FE_FUSION_MAX_ROWS`, default 250k). The CPU sibling computes the identical margin as `.../ max(sqrt(n_rows), 1.0)` using the *true, full* fit row count. Above the 250k-row subsample threshold this is not merely "the same decision scored on fewer rows" (the already-known B-20 divergence) — the calibration formula itself is evaluated at the wrong `n`, making the GPU threshold systematically ~2x larger (stricter) than the CPU threshold at n=1M (`2/sqrt(250k)=0.004` vs `2/sqrt(1M)=0.002`), a compounding, previously-undocumented mechanism on top of B-20's sampling-noise argument. | NEW (elaborates the already-open B-20 / `c7d_fe_orchestration.md` finding with a distinct formula-level root cause, not just sample selection). |
| GPU_INFRA_D-5 | P1 | efficiency | `_gpu_pairs.py:234-255` | The per-pair joint-MI reduction after the single batched CUDA histogram launch is a pure-Python triple-nested loop (`for k in range(n_pairs): for m in range(merged_size): for y in range(nbins_y):`), i.e. O(total joint cells) at native Python speed — up to the function's own admitted ceiling of `total_cells < ~1.07e9` cells (the 4 GB guard at line 110). The module's docstring frames this reduction as "cheap relative to histogram aggregation," but at a few hundred thousand to low-millions of cells (well short of the 4 GB cap, and plausible at high-cardinality categorical pairs / large `n_pairs`) a Python-level loop of that size (tens of seconds to minutes) would dominate and defeat the entire point of collapsing per-pair kernel launches into one batched launch. Trivially fixable with vectorized numpy per pair (`np.outer(marg_m, marg_y)` + `np.where` + `.sum()`), zero semantic change to the formula (verified: `mi += jf * log(jc*n/(mm*my))` is exactly `sum(p_xy * log(p_xy/(p_x*p_y)))`, no off-by-one or formula bug in the loop itself — only a missed-vectorization efficiency issue). | NEW. |
| GPU_INFRA_D-6 | P1 | api_design / cpu_gpu_parity | `_cupy_polynom_optimizer.py:255` vs `_numba_polynom_optimizer.py:690-696` | `_cupy_polynom_optimizer.py`'s module docstring states `run_cupy_kernel_search` has "same return contract as `run_numba_kernel_search`" and both docstrings describe the shape `(coef_a_best, coef_b_best, bf_idx_best, raw_mi_best, best_score)`. ## Proposals

### Wire the shared GPU opt-out check into the polynom-pair optimizer dispatch (closes GPU_INFRA_D-1)
Add `if gpu_globally_disabled(): return None` (or an equivalent inline `MLFRAME_DISABLE_GPU`/`CUDA_VISIBLE_DEVICES` check) at the top of `run_cupy_kernel_search`, and make the `_hermite_fe_optimise_pair.py:589` dispatch also respect the estimator's own `use_gpu` flag (thread it through `eval_kwargs` or a new keyword) before importing/calling `run_cupy_kernel_search` — mirroring the pattern already used correctly by `_fe_pure_form_retention_gpu_resident.py` and the STRICT-resident dispatch chain in this same cluster. Add a regression test analogous to `test_noise_gate_gpu_optout_regression.py` (spy on `run_cupy_kernel_search`, assert it's never entered under `CUDA_VISIBLE_DEVICES=""`/`MLFRAME_DISABLE_GPU=1`/`use_gpu=False`).

### Lock (or eliminate) the shared `max_dynamic_shared_size_bytes` mutation (closes GPU_INFRA_D-2)
Guard the property-set + launch pair in `_gpu_pairs.py` (and the identical pattern in `_batch_pair_mi_cuda_shared_fused.py`) with a module-level `threading.Lock`, or avoid the shared mutable state entirely by requesting a lazily-created per-shared-size kernel variant (cached by `_needed_shared_bytes` in a dict) instead of mutating one singleton kernel's attribute. Add a targeted test that drives two different `max_joint_size_y` shapes through `mi_direct_gpu_batched_pairs` from two threads concurrently and asserts no launch-config exception / no histogram corruption.

### Fix the seed<=0 substitution in the numba polynom optimizer (closes GPU_INFRA_D-3)
Change `seed if seed > 0 else 1` to just `seed` in both `run_numba_kernel_search` and `optimize_all_pairs_numba_kernel` (matching the cupy twin and `np.random.default_rng`'s native support for `seed=0`), and add a regression test that runs both backends at `seed=0` and asserts they draw distinct-but-individually-reproducible streams (bit-identical across repeated calls with the same seed), not the same stream as `seed=-1`/`seed=-99`.

### Use the true fit row count in the GPU-resident OLS-R margin (closes GPU_INFRA_D-4)
In `_fe_additive_fusion_gpu_resident.py:312`, divide by `max(np.sqrt(float(n_rows)), 1.0)` (the full row count, matching the CPU sibling) rather than `n_sc` (the scoring-subsample count), so the two backends calibrate the same statistical margin even when the scoring subsample differs. Add a parity test at n > 250k that asserts the OLS-R gate's pass/fail verdict (not just its output values) matches between CPU and GPU on the same borderline-separable fixture.

### Vectorize the per-pair joint-MI reduction (closes GPU_INFRA_D-5)
Replace the `for k / for m / for y` triple loop in `_gpu_pairs.py` with, per pair, `outer = np.outer(marg_m, marg_y); ratio = np.where((joint_2d > 0) & (outer > 0), joint_2d * n_total / np.where(outer > 0, outer, 1.0), 1.0); mi = float(np.sum(np.where(joint_2d > 0, (joint_2d / n_total) * np.log(ratio), 0.0)))` — same formula, no semantic change, but native-numpy speed. Add a benchmark at realistic (n_pairs, cardinality) shapes to confirm the batched-launch win is actually realized end-to-end rather than reclaimed by the host-side reduction.

### Reconcile the 5th-tuple-element contract between the two polynom optimizers (closes GPU_INFRA_D-6)
Either add `n_evals`/`best_score` consistently to both backends' return tuples (extend to a 6-tuple with both, in a fixed order), or fix the docstrings to state the true, *different* per-backend contracts. Add a direct-call test asserting `run_cupy_kernel_search(...)[4]` and `run_numba_kernel_search(...)[4]` mean the same thing, or that callers are documented to never rely on positional element 5 across backends.

### Clean up the dead resident-`y` check and the stride off-by-something idiom (closes GPU_INFRA_D-11, GPU_INFRA_D-12)
Remove the unreachable `isinstance(y_h, cp.ndarray)` branches in `_fe_cmi_perm_null_gpu.py` (or, if a future resident-`y` fast path is intended, thread an actual `y_dev`-carrying call site through first). Change the shared stride idiom in both hinge/fusion files to `-(-n // max_rows)` (ceiling division) or an explicit `if n > max_rows: stride = max(1, n // max_rows)` with a a follow-up bump when `stride == 1` still leaves `n > max_rows`, so the row cap and the docstring's stated behavior actually agree at every n.
