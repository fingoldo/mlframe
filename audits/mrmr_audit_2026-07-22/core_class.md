# Core MRMR class & fit orchestration -- audit (2026-07-22)

This cluster is the `mrmr/` subpackage: the `MRMR` sklearn estimator's irreducible class body
(`_mrmr_class.py`, 4016 LOC -- `__init__`'s ~300-parameter signature, `fit`/`_fit_body` orchestration,
`__getstate__`/`__setstate__`, `__repr__`, the thin `transform` delegator), its three carved-out mixins
(`_mrmr_class_config.py` -- ctor-default resolution/seeding/subsample-profile knobs,
`_mrmr_class_fit_helpers.py` -- stability outer-loop/multioutput/identity-shortcut/sample-weight-resample/
export_artifacts, `_mrmr_class_transform.py` -- `get_feature_names_out`/`get_support`/usability-union),
the nested-pydantic-config additive migration (`_mrmr_config_dataclasses.py`), the constructor-param
validation allow-lists (`_mrmr_param_constants.py`), the legacy-pickle default-injection roster
(`_mrmr_setstate_defaults.py`), a tiny shared leaf (`_mrmr_class_shared.py`), and the package facade
(`__init__.py`) that re-exports `MRMR` and binds the sibling-module method implementations onto it. This
is the same logical cluster the 2026-07-20 audit's `c1_core_class.md` covered, but the file layout has
since changed (that report's line numbers, e.g. `_mrmr_class.py:3556`, referred to a pre-split monolith
whose relevant fix commit is `741926f8c`; its OTHER findings live in sibling files -- `_mrmr_stability_report.py`,
`_mrmr_tree_rescue.py`, `_mrmr_partial_fit.py`, `_mrmr_fit_helpers_mixin.py`, `_mrmr_degenerate.py` -- that are
**not** in this file-set and were not re-verified here).

**Headline finding**: as of this session, `MRMR.fit()` is completely non-functional for every caller,
including every existing test -- not a bug in this cluster's own logic, but a live, uncommitted-nowhere-else
cross-repo regression from the sibling `pyutilz` dependency (see CORE_CLASS-1). Everything below CORE_CLASS-1
was verified by direct source-code reasoning (cross-checked against the installed `sklearn.base.clone`
source) since the runtime is currently unable to complete a real `.fit()` call to exercise it end-to-end.

## Non-findings / confirmed-clean angles

- **CPU/GPU parity**: no CPU/GPU kernel-twin pairs exist in this cluster's files (matches 2026-07-20's own conclusion) -- the only GPU-touching import is `..gpu.mi_direct_gpu`/`..gpu.init_kernels`, consumed elsewhere. Confirmed no divergence introduced since.
- **SQL/HTTP/UI surface**: none. No DB/network calls, no generated HTML/report strings, no subprocess/eval/exec/os.system. The one `os.environ` read/write (`_apply_fast_search_profile`'s Fourier-detect-cap save/restore) is a thread-local-adjacent config knob, not an injection surface. `pickle`/`__setstate__` only accept the estimator's own prior pickled state (no untrusted-network-input deserialization path).
- **mypy**: all 9 assigned files are mypy-clean (`mypy --cache-dir=.mlframe_mypy_cache_shared`, zero errors) using the repo's shared cache.
- **B-3 (2026-07-20, thread-local leak on mid-activation raise)**: fixed, commit `741926f8c` -- verified both trigger paths (`redundancy_aggregator` typo at `_mrmr_class.py:3580`, `group_aware_mi` + mismatched-length `groups` at `:3634`) now route through `_restore_toggles_snapshot_and_raise` before re-raising. See CORE_CLASS-4 above for a related-but-dormant residual gap in that same helper.
- **`_maybe_resample_for_sample_weight`** (`_mrmr_class_fit_helpers.py:292-344`): the non-uniform-`sample_weight` path resamples rows with replacement (`rng.choice(n_rows, size=n_rows, replace=True, p=probs)`) as a Monte-Carlo approximation of a weighted bincount rather than threading weights through the binned-histogram MI estimator directly. This is a documented, seeded, deliberate design tradeoff (not a bug) -- flagged only as a Proposal below since the MC noise floor at small n with sharply peaked weights is unquantified.
- Ruff: only the pre-existing, repo-blessed-ignored `C901 _fit_body is too complex (80 > 40)` fires; per `CLAUDE.md`'s own description of the blocking gate (`ruff check . --ignore C901`), this is not a fresh finding.
- LOC budget: `_mrmr_class.py` is 4016 LOC, `_mrmr_class_fit_helpers.py` 588, `_mrmr_class_config.py` 515, `_mrmr_config_dataclasses.py` 255, `_mrmr_setstate_defaults.py` 394, `_mrmr_class_transform.py`/`__init__.py` 253 each, `_mrmr_param_constants.py` 99, `_mrmr_class_shared.py` 27. `_mrmr_class.py` is the one file over the ~800-900 LOC guideline by roughly 4x, but this is **already tracked**, not a new finding: `tests/test_meta/test_no_file_over_1k_loc.py`'s `LOC_BUDGET_EXEMPT` set carries a detailed, dated carve history for exactly this file ("the irreducible `MRMR` estimator class body... `__init__`'s ~2080-line parameter docstring + fit; further LOC drop needs relocating that docstring, not more logic carving") and explicitly documents it as still-exempt-by-design pending the next carve wave. Re-flagging here per the audit brief's instruction to always state exact line counts, but the disposition is already "known, tracked, deferred," not "undiscovered."

## Test coverage notes

- `tests/feature_selection/mrmr/core/` has ~90 files covering this cluster's surface reasonably thoroughly (sklearn contract + thread-locals, concurrency fixes, config-dataclass migration, setstate/pickle, multioutput, sample-weight, safe-restore helper, degenerate frames, etc.) -- this is not an under-tested cluster in general.
- No test exercises `clear_fit_cache()` concurrently with an in-flight `fit()` on another thread (CORE_CLASS-2's gap) -- `test_fit_cache_thread_safety.py` is otherwise a strong, well-designed suite (structural lock-ownership instrumentation rather than a flaky timing race) but doesn't cover this one path.
- No test constructs a nested-config-kwarg MRMR, calls `set_params()` on one of that config's own covered fields, and then calls `clone()` or fits it through `GridSearchCV`/`Pipeline` (CORE_CLASS-3's gap) -- `test_mrmr_config_dataclass_migration.py`'s clone test never intervenes with `set_params` first.
- Because of CORE_CLASS-1, essentially every test in this tree would currently fail at collection-adjacent or first-fit time in this exact environment; that is an environment/dependency-version issue, not a test-coverage gap in mlframe's own suite.

## Proposals

1. **(fix-scope, not itself a code change here)** Add an explicit `postfix=""` argument at all ~10 mlframe `store_params_in_object(...)` call sites (or add a cross-repo API-stability pin/test so a `pyutilz` default-value change like commit `8128f16` cannot silently break every downstream caller again) -- see CORE_CLASS-1.
2. Add a lock-protected `clear_fit_cache()`: `with getattr(cls, "_FIT_CACHE_LOCK", _dummy_nullcontext): cls._FIT_CACHE.clear()`, guarding against the class attribute not yet existing (pre-first-fit) with a no-op fallback, then a regression test that calls `clear_fit_cache()` from one thread while several others are mid-`fit()` on distinct small frames (extending `test_fit_cache_thread_safety.py`'s existing harness) and asserts no `KeyError`/`RuntimeError` from either side.
3. Either (a) have `set_params()` invalidate/null out any nested config object whose covered field was just individually overridden (keeping `get_params()` self-consistent), or (b) have `apply_mrmr_config_objects` skip a field that the CURRENT flat attr already disagrees with the config's own recorded value for (i.e., only apply a config field when the flat attr is still at ITS OWN raw ctor-signature default, mirroring `_override_if_at_default`'s "explicit user value always wins" pattern already used elsewhere in this same cluster for `_apply_fast_search_profile`) -- the latter is more consistent with the codebase's existing convention and requires no new invalidation state.
4. Add a `-> None` restore for the 4 currently-dead-stored variables in `_restore_toggles_snapshot_and_raise` (mirror `_restore_synergy_bonuses` from the `finally` block) purely for defense-in-depth against a future reordering, plus a regression test that adds a raise point after line 3666 (e.g., temporarily monkeypatching `_set_dcd_active` to raise) and asserts all 9 thread-locals -- not just 5 -- are restored.
5. A dedicated, low-risk comment-cleanup pass over this cluster's ~100 "finding #"/date-stamp/audit-filename references, folding the WHY into plain prose (the underlying rationale in each comment is usually good and worth keeping -- only the audit-tracking metadata needs to go) -- natural to batch with proposal 4's edit since both touch the same handful of files.
6. Quantify `_maybe_resample_for_sample_weight`'s Monte-Carlo resampling noise floor (a small-n, sharply-peaked-weight synthetic comparing selection stability against a hypothetical exact-weighted-histogram MI path) and document the practical n/weight-skew regime where it's safe, rather than leaving the tradeoff purely qualitative in the docstring.
