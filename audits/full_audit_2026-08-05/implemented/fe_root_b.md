## Narrative

**FE_ROOT_B-1 (P0, data leakage).** `spatial.py`'s `knn_aggregate` docstring explicitly promises: "The actual query asks for `k + 1` and skips the self-match if the same point appears in both pools (so `query is ref` is leak-safe by construction)." Tracing the code: `q_k = k + 1` is indeed used when no group filtering is requested, but the branch that consumes it (`else: compact_indices = indices[:, :k]`) simply truncates to the first `k` of `q_k` sorted-by-distance results — it never checks whether the returned index equals the query's own row index. When `query_coords is ref_coords` (the exact scenario the docstring calls out as safe — a common "each row's k nearest OTHER rows" in-sample feature pattern), each query point's own coordinate is present in the KDTree and returns itself at distance 0 as `indices[:, 0]`. That self-match is then kept as one of the `k` neighbours whose label is aggregated, leaking the row's own label into its own feature (at full weight for min/max/median, and typically the DOMINANT weight for `distance_weighted=True` mean, since `1/(0+weight_eps)` is the largest possible weight). The group-filtered branch happens to sidestep this only incidentally (a row's own group ID equals its own group, so the `same_group` filter excludes it as a side effect) — but that's not documented as the actual safety mechanism, and the plain (no-group-filter) path, which the docstring's wording covers unconditionally, has no such protection at all.

**FE_ROOT_B-2 (P1, formula mismatch).** `compute_hurst_rs` (the multi-scale/ladder Hurst estimator) computes standard deviation with an explicit `ddof=1` correction and documents this choice ("Standard deviation uses ddof=1 (sample std) per the Mandelbrot/Hurst convention"). `_hurst_rs_single` (the single-scale rolling-window estimator, used by `rolling_hurst`) instead calls `x.std()`, numpy/numba's default `ddof=0`. Its docstring claims "Same definition as `compute_hurst_rs` but inlined for the rolling-kernel hot path" — a claim that is not true. The bias is `sqrt(n/(n-1))`, e.g. ~2.6% at the minimum allowed rolling window (`K=20`, enforced by `rolling_hurst`'s own guard). This means the two "families" of Hurst features shipped from this module are not actually computing the same statistic despite explicitly documented equivalence, which could mislead anyone reconciling values between `compute_hurst_exponent` and `rolling_hurst` on the same data.

**FE_ROOT_B-3 (P1, memory-safety doc/code mismatch).** `variance_gated_pairwise_diff`'s module docstring is explicit about its purpose: avoid materializing the full `C(n,2)` combinatorial diff set by pruning chunk-by-chunk, "so peak memory scales with the chunk size, not the full combinatorial count." The current implementation (evidently rewritten for speed via a single covariance-matrix pass) computes the survival decision for ALL pairs up front from `np.cov(X, rowvar=False)`, then iterates `surviving_pairs` in `chunk_size`-sized slices purely as a loop-batching convenience — every chunk's resulting diff columns are written into the SAME `out` dict, which is never flushed, so by the time the function returns, every surviving pair's full-length diff array is resident in memory simultaneously. For a low `min_variance` threshold and hundreds of columns (exactly the scenario the docstring's own math example cites — "872 choose 2 = ~380k pairs"), this can still materialize a very large fraction of the full combinatorial set, precisely the blowup the module claims to prevent. This is a documentation-vs-implementation mismatch important enough to flag given this repo's explicit "Memory / RAM discipline" convention (frames can be 100+GB; a helper marketed as memory-bounded needs to actually be memory-bounded).

**FE_ROOT_B-4 (P1, batched-linalg blast radius).** `knn_gradient_features` solves a per-row weighted local-linear-regression system for ALL `n_q` query rows in one batched `np.linalg.solve(XtX + eye, Xty)` call, wrapped in a single `try/except np.linalg.LinAlgError: beta_all = np.full((n_q, d+1), np.nan, ...)`. NumPy's batched `linalg.solve` raises `LinAlgError` for the WHOLE stacked call if even one (d,d) submatrix in the batch is (near-)singular. Real spatial data (rounded/quantized coordinates, azimuth-bucketed or gridded geo data — exactly the kind of input this module's own docstring calls out as a use case) can easily produce one degenerate all-duplicate-coordinate neighbourhood among thousands of well-conditioned ones. When that happens, the except clause discards gradient features for EVERY row in the batch, not just the offending one — a silent, large-blast-radius correctness/robustness bug that would be very hard to notice downstream (the whole feature column would just be NaN for that fit, with no indication why).

**FE_ROOT_B-5 (P1, asymmetric skip-guard).** `create_windowed_features` builds an explicit "past-side / future-side symmetric" incompleteness check for skipping a training row with insufficient window data, and the code comment for the past-side check says it is "symmetric with the future-side check." Reading both checks carefully: the future-side check when `targets_creation_fcn` is `None` compares `len(row_targets) < future_nwindows_expected` — an exact expected-vs-actual window count. But when `targets_creation_fcn` IS supplied, `window_features=None` is passed to `create_and_process_windows`, which routes results into the `future_windows_features` dict instead of `row_targets`, and the completeness check degrades to `len(future_windows_features) == 0` — true only when NO window at all was produced, not when SOME (but not all) requested window sizes hit a data boundary and were skipped. This is a genuine, non-cosmetic asymmetry: a row with, say, 2 of 3 requested future windows successfully computed would be skipped in the default mode but silently kept (with a partial window set) in `targets_creation_fcn` mode.

**FE_ROOT_B-6 (P1, catastrophic-cancellation risk).** `multi_window_aggregate` computes each `(horizon, agg)` windowed feature as the difference between two full calls to `leakage_safe_aggregate` — one queried at the true cutoff (`upper`), one queried at `cutoff - horizon` (`lower`) — then subtracts (`upper[colname] - lower[colname]`). Both `upper` and `lower` are themselves CUMULATIVE aggregates over an entity's ENTIRE eligible history up to their respective cutoffs, not just the requested window. When an entity's full history span is large relative to the requested horizon (the module's own stated use case — "last 3 months" out of potentially years of history), `upper` and `lower` can both be large, nearly-equal floating-point numbers, and their difference for a genuinely small windowed contribution loses significant digits. This is the exact bug class ("silent correctness bug classes: subtractive cancellation") that this codebase's own change history documents fixing repeatedly in other, similarly-shaped subtractive derivations (global-minus-test-fold moment calculations, per-cell stats, etc.) — it appears not to have been checked here.

**FE_ROOT_B-7 through FE_ROOT_B-10 (P2)** are all real, but narrower-impact: a return-type inconsistency on a degenerate `len<=1` input path (`compute_numaggs`), a missing minimum-value guard that causes silent division-by-zero-derived NaN grid points (`recency_density`'s `n_grid`), a missed algorithmic-efficiency opportunity specific to the module's own three compact-support kernels (`nadaraya_watson`'s always-O(n²) scan), and an undocumented NaN-to-zero silent-corruption risk on inputs with mid-series NaNs (`frac_diff`).

**FE_ROOT_B-11 through FE_ROOT_B-20 (P3)** are hygiene/robustness/naming items: dead code (`_ordinal_rank`), a misleading parameter name that could mislead a future optimizer (`x_sorted`), a redundant `.copy()`, a missing negative-value validation (`mps.py`'s `shift`), two classes of benchmark-script hygiene issues (hardcoded personal/transient paths in `ab_grouped_10m.py`; a stale Anaconda-interpreter run-comment in two other bench files), one genuinely broken/no-op verification check inside a benchmark script (`bench_graddir_gradient_colcopy.py`), a validation gap for a rarely-exercised `fallback_by_chain` misuse pattern (`nearest_past_join`), an undocumented API-surface inconsistency between two sibling kNN-aggregator functions (`agg_fns` support), and a missing diagnostic for a known-heuristic degradation path (`knn_aggregate`'s group-filter overquery cap).
