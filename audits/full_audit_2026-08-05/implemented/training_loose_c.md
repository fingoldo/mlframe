## Narrative

### TRAINING_LOOSE_C-1 (P1) — `_compute_oof_preds` crashes on a single-distinct-group train fold
`trainer.py:253-262` branches on `group_ids`: `splitter = GroupKFold(n_splits=min(n_splits, len(set(np.asarray(group_ids)))))`. I verified directly that `sklearn.model_selection.GroupKFold(n_splits=1)` raises `ValueError: k-fold cross-validation requires at least one train/test split by setting n_splits=2 or more, got n_splits=1` **at construction time**, not inside `cross_val_predict`. The function's own `try/except (ValueError, TypeError, RuntimeError, NotImplementedError)` block starts several lines later, wrapping only the `cross_val_predict(...)` call — the `GroupKFold(...)` construction on line 258 is unguarded. This function is called from `_trainer_train_and_evaluate.py:744` with **no** surrounding try/except at the call site either, and only fires *after* the real model has already trained successfully (`oof_n_splits and oof_n_splits >= 2 and not just_evaluate`). A training fold whose `group_ids` happen to reduce to a single distinct value (small folds, heavily skewed grouping, or a composite-target-discovery sub-slice) crashes the entire per-model training call and discards the already-trained model, rather than gracefully falling through to `(None, None)` as every other degenerate-input path in this function (and its own docstring: "Empty/None inputs return (None, None) so callers proceed with normal training") promises. No existing test (`grep`ped `tests/training/test_oof_*.py`, `test_training_loose_b_fixes.py`) exercises a single-group `group_ids` input.

### TRAINING_LOOSE_C-2 (P1) — elasticnet classifier silently ignores the user's `l1_ratio`
`models.py:312-323`'s `_build_elasticnet_classifier` sets `l1_ratio=_get_l1_ratio(config)`. `_get_l1_ratio` (line 103-105) returns `config.l1_ratio if config.penalty == "elasticnet" else 0.15`. `LinearModelConfig.penalty` defaults to `"l2"` (`_model_configs.py:112`) and there is no validator or dispatch logic anywhere that sets `penalty="elasticnet"` when `model_type="elasticnet"` — I traced the only production call site (`_trainer_configure.py:770-771`, `config = LinearModelConfig(**linear_config_kwargs); create_linear_model(model_type, config, ...)`) and confirmed nothing there sets `penalty`. So for the common case (a caller sets `LinearModelConfig(model_type="elasticnet", l1_ratio=0.7)` and does *not* separately set `penalty="elasticnet"`), the CLASSIFIER builder silently trains with the hardcoded fallback `l1_ratio=0.15` instead of the user's `0.7` — the documented, user-facing hyperparameter ("Mix of L1/L2 for ElasticNet (0=L2, 1=L1)") is dead for this path. By contrast, `_build_elasticnet_regressor` (line 181-191) uses a ternary `_get_l1_ratio(config) if config.penalty == "elasticnet" else config.l1_ratio` that resolves to `config.l1_ratio` on **both** branches (a redundant-but-harmless tautology), so the regressor path is unaffected — only the classifier is broken. Confirmed via `tests/training/test_linear_models.py::test_elasticnet_with_custom_l1_ratio`, the only existing `l1_ratio` test, which uses `use_regression=True` exclusively; the classification path has zero test coverage for this parameter.

### TRAINING_LOOSE_C-3 (P1) — lgb_shim train-Dataset cache hit silently drops a new `init_score`
`lgb_shim.py`'s `_DatasetReuseMixin.fit` (lines 519-582) accepts an `init_score` parameter. On a cache MISS, `_build_dataset(..., init_score=init_score)` correctly threads it through. On a cache HIT (same X content signature, same `categorical_feature`), the code only calls `dtrain.set_label(...)` and `dtrain.set_weight(...)` — it never calls `dtrain.set_init_score(...)`, even though I confirmed `lightgbm.Dataset.set_init_score` exists as a public API. This means a second `.fit(X, y, init_score=new_offset)` call reusing the same cached Dataset silently trains against whatever init_score (or none) the Dataset happened to be built with originally. The module's own docstring explicitly documents this shim's target use case as "multi-target / multi-weight sweeps" over identical X — and `init_score` is heavily used elsewhere in this exact training package (`baselines/_baseline_diagnostics_init_score.py`, `composite/glm.py`, `composite/classification.py`) for residual-learning workflows that re-fit the same feature matrix with a different offset. This is exactly the class of "cache serves stale auxiliary state" bug the file's own weight-reset logic (lines 556-561) was written to prevent for `sample_weight` — `init_score` got missed. No test in `tests/training/test_lgb_dataset_reuse_shim.py` or its siblings exercises `init_score` at all (grepped).

### TRAINING_LOOSE_C-4 (P1) — lgb_shim val-Dataset cache hit doesn't reset stale weight
`lgb_shim.py:646-649`:
```python
if dval is not None:
    dval.set_label(np.asarray(y_val))
    if w_val is not None:
        dval.set_weight(np.asarray(w_val))
    ...
```
When `w_val` is `None` on a cache hit, the code simply skips `set_weight` entirely, leaving whatever weight a *previous* call left on the shared cached Dataset object. Compare this to (a) the same file's TRAIN Dataset cache-hit path a few dozen lines above, which explicitly handles the "was weighted, now isn't" transition (`dtrain.set_weight(np.ones(...))` in the `else` branch, with an explicit comment: *"When sample_weight was set previously and now None is passed, 'uniform weights' is the desired semantic"*), and (b) the sibling `xgb_shim.py:537-542`, whose analogous val-DMatrix cache-hit path DOES have the `else: dval.set_weight(np.ones(...))` branch. This is a direct, provable asymmetry between two near-identical shims solving the same caching problem — one got the fix, the other didn't. Practical impact: in a multi-weight sweep (the shim's stated purpose) where sweep A supplies `eval_sample_weight` and sweep B (reusing the same val X) does not, sweep B's early-stopping / reported val metrics would silently be computed against sweep A's stale weights instead of uniform weights.

### TRAINING_LOOSE_C-5 (P1) — honest-diagnostics calibration block can mismatch OOF probs to unrelated test labels
`honest_diagnostics.py:326-338`:
```python
y = getattr(model_entry, "oof_target", None)
if y is None:
    y = getattr(model_entry, "test_target", None)
...
n = min(oof_arr.shape[0], y_arr.shape[0])
oof_arr = oof_arr[:n]
y_arr = y_arr[:n]
```
`oof_probs` are in train-row (`cross_val_predict`) order; `test_target` is a disjoint split in a completely different row order. Truncating both to `min(n_oof, n_test)` and zipping element-wise pairs unrelated rows together — the exact "positional slice across splits" bug the same codebase's `evaluation.py::post_calibrate_model` has extensive, explicit commentary about having fixed twice (see that file's "OOF y must be the train-aligned target stamped alongside oof_probs... NOT a positional target_series[:len(oof)] slice" comments). In the normal path, `oof_target` is always stamped alongside `oof_probs` in the same `try` block (`_trainer_train_and_evaluate.py:755-773`), so this fallback is dormant for the common case — but it fires whenever that stamping partially fails (e.g. the documented `except AttributeError: pass` on a frozen-attribute estimator that allows `oof_probs` but not `oof_target`) or for any legacy/external caller that stamps `oof_probs` without `oof_target`. When it fires, `pick_best_calibrator`'s "chosen calibrator" + ECE verdict in the honest-diagnostics report — the artefact whose entire purpose is to give a reviewer an honest evaluation trail — is computed on scrambled (prob, label) pairs with no warning to the operator that anything is wrong.

### TRAINING_LOOSE_C-6 (P2) — categorical PSI ignores `feature_names` restriction
`feature_drift_report.py`'s `_compute_drift_invariant` (line 716) correctly uses `cols = feature_names or _numeric_columns(train_df)` for the numeric z-stat side, but the categorical side (line 774) calls `compute_categorical_drift_psi(train_df, val_df, test_df)` with no `feature_names=` argument at all, even though `compute_categorical_drift_psi` accepts one (line 597) and would honor it. The module's own docstring lists this exact scenario ("Feature selection runs inside per-model pre_pipeline... Drift on a dropped feature is observationally uninteresting") as a designed-for use case for `feature_names` filtering — but only half of the drift report actually respects it. Currently dormant: I grepped the sole production call site (`core/_phase_diagnostics.py:133-140`) and confirmed it never passes `feature_names`, and the bench script that exercises this function (`_benchmarks/bench_feature_drift_zstats_cache.py`) doesn't either — so this is a real, provable inconsistency with zero current blast radius, waiting for the first caller (or future wire-in of the parameter) to hit it.

### TRAINING_LOOSE_C-7 (P2) — binary drift summary has no NaN handling
`drift_report.py:62-72`'s `_binary_split_summary` computes `n_pos = int((arr == 1).sum())` directly over the raw array. Every OTHER split summarizer in the same file (`_regression_split_summary` uses `np.nanmean`/`np.nanstd`/`np.nanquantile`; `_multiclass_split_summary`/`_multilabel_split_summary` at least operate over exact value counts) is explicitly NaN-aware or count-exact, but the binary path silently treats `NaN != 1` as a negative, folding any missing-label rows into the negative bucket with zero signal that they were missing. Given this module's whole reason for existing is to catch label-shift between splits before 5 hours of training are wasted, a val/test split with a meaningful fraction of unlabeled rows (plausible in this same package's PU-learning / semi-supervised context — see `pu_learning.py` in this same cluster) would silently under-report `p_positive` and could either trigger a false drift alarm or mask a real one.

### TRAINING_LOOSE_C-8 (P2) — dead `calib_set_size` parameter with misleading docstring
`evaluation.py:155,193-195`: `post_calibrate_model`'s docstring explicitly claims `calib_set_size` is "only honoured for the multi-output per-class isotonic path when `calib_probs` is not supplied" — but grepping the entire function body for `calib_set_size` after the signature/docstring turns up zero usages. The multi-output branch (lines 262-341) never reads it either. A caller who sets `calib_set_size=500` expecting to control the OOF-fallback calibration-slice size on the multi-output path gets no effect whatsoever, with no warning.

### TRAINING_LOOSE_C-9 (P2) — `exploss` metric crashes (not skips) on empty input
`metrics_registry.py:409-418`'s `_exp` builtin: `pos_label = uniq[1] if uniq.shape[0] > 1 else uniq[-1]`. When `y_true` is empty, `np.unique(yt)` is a zero-length array and `uniq[-1]` raises `IndexError`. `iter_extra_metrics` (the sole caller path, lines 93-132) explicitly narrows its except clause to `(ValueError, ZeroDivisionError, TypeError, FloatingPointError)` — deliberately excluding unexpected exceptions so "a real bug is not masquerading as 'metric not applicable'" per its own docstring — but this means `IndexError` from a genuinely-degenerate-but-legitimate input (an empty test split, one of this audit's required edge-case dimensions) propagates uncaught and aborts the entire metrics-registry report instead of just omitting `exploss`. Confirmed no test exercises an empty `y_true` against the registered classification metrics (`tests/training/test_metrics_registry_classification.py`).

### TRAINING_LOOSE_C-10 (P2) — MLP memory-probe cache conflates CPU and GPU budgets
`mlp_runtime_defaults.py:335-380`'s `_probe_available_memory_bytes` caches the FIRST successful probe result into a single scalar `_PROBE_MEM_CACHE`, checked before even looking at the `cuda_available` argument on subsequent calls (`if _PROBE_MEM_CACHE is not None and not os.environ.get("MLFRAME_FORCE_REPROBE"): return _PROBE_MEM_CACHE`). The function can be probed in either CPU mode (`psutil.virtual_memory().available`, typically tens of GB) or GPU mode (`torch.cuda.mem_get_info`, typically a handful of GB on a workstation card) — these are very different-magnitude quantities, and nothing in the cache key distinguishes which mode produced the cached value. Both current production call sites (`neural/data.py:379`, `neural/base/_base_predict.py:129`) always pass `cuda_available=None` (real auto-detect), which is self-consistent within one process on stable hardware — but the function's own test-facing parameters and the module's explicit `MLFRAME_FORCE_REPROBE` escape hatch show its authors already anticipated staleness as a real risk for repeated same-mode probing; they didn't extend that awareness to the cross-mode case. A test harness (or a future caller) that probes CPU mode once and GPU mode later in the same process would get the wrong-magnitude budget, risking either an overly-conservative CPU-sized batch on GPU (perf loss) or — the dangerous direction — a GPU batch sized against a cached CPU-RAM number if a CPU probe happened to run first, right on the edge of the CUDA-OOM failure mode this whole module was built to prevent (see the module's own opening paragraph about the historical OOM regression).
