## Narrative detail

**MODELS-1 (P1).** `MBHOptimizer` is documented as a general "optimize hyperparameters, select best features" surrogate search (see `optimization.py`'s module docstring), and nothing in its public signature (`search_space: Sequence`) restricts it to integer-valued spaces — `compute_candidates_exploration_scores` (used internally) works fine on arbitrary numeric arrays. However, `submit_evaluations` (`_optimization_search.py:646`) does `self.known_candidates = np.concatenate([self.known_candidates, np.asarray(new_candidates_batch)]).astype(int)` — every submitted evaluation's `x`-value is forced to `int`, even though `self.best_candidate`/`self.worst_candidate` (also set in the same function) retain the caller's original (possibly float) value. Because `suggest_candidate`'s membership checks (`known_candidates_set = set(self.known_candidates.tolist())`, line 377) are built from this int-cast array while candidates being tested (`next_candidate = self.search_space[best_idx]`, line 543) retain `search_space`'s original dtype, a continuous `search_space` (e.g. a learning-rate grid) would never register any candidate as "already checked" — the optimizer would keep re-suggesting already-evaluated points, defeating the entire search, silently (no exception, no warning). I confirmed via `grep` that every current internal caller (RFECV feature-count search) only ever passes integer feature counts, so this is unexercised in production today, but it is directly reachable through the public API and untested for the continuous case (`tests/models/test_cpx16_optimization_membership_identity.py` only uses `np.arange(...)`).

**MODELS-2 (P1).** This is the most consequential finding in the cluster. `score_ensemble`'s pipeline (`score.py`) calls three sibling gate helpers in sequence — `catastrophic_drop_kn`, `catastrophic_drop_k2`, then `apply_quality_gate_kn` — each of which is supposed to keep `level_models_and_predictions` and the two parallel tag lists (`_ensemble_member_tags`, `_ensemble_short_tags`) in lock-step when it drops members. I verified by reading `score_gate.py` that the first two helpers correctly slice all three lists together (e.g. `score_gate.py:221-224`, `:307-309`). `apply_quality_gate_kn` (`score_flavours.py:366-477`) is the odd one out: it slices `level_models_and_predictions = [level_models_and_predictions[i] for i in _kept_idx]` (line 411) but returns the ORIGINAL, unsliced `_ensemble_member_tags`/`_ensemble_short_tags` (line 467-477), with a comment (lines 461-466) claiming this is deliberate because "the downstream code already realigns via `_ensemble_member_tags.index(...)`". That claim does not hold: the very next call in `score.py` (`compute_high_correlation_pairs(level_models_and_predictions, _ensemble_member_tags, ...)`, `base.py:833-915`) indexes the tag list *positionally* (`member_tags[ii]` for `ii` in `range(K_use)` where `K_use` is the size of the SLICED member set) — there is no `.index()` call anywhere in that function. I traced a concrete failure scenario: 4 members [A,B,C,D], gate drops B (`_kept_idx=[0,2,3]`), so `level_models_and_predictions=[A,C,D]` (3 entries) but `_ensemble_member_tags` stays `[tagA,tagB,tagC,tagD]` (4 entries). `compute_high_correlation_pairs` then reports any correlated pair between positions 1 and 2 (which are C and D) using `tagB` and `tagC` — the wrong labels, off by one for every member after the dropped one. With the default `auto_drop_diversity_above=None` this only corrupts diagnostic output (`res["_diversity"]["high_correlation_pairs"]`, WARN log lines) — still a real "silently wrong result" in production reporting. With `auto_drop_diversity_above` set (an intentionally-supported, documented knob), `apply_diversity_drop` (`score_flavours.py:90-136`) uses these mislabeled pairs to decide which member to drop, and because `_ensemble_member_tags.index("tagB")` still succeeds (the string is literally present in the unsliced list, just semantically stale), the auto-drop logic can remove the WRONG surviving member (e.g. C instead of whichever member was actually part of the flagged correlated pair), silently corrupting the final ensemble's membership. No test in `tests/models/test_ensembling_score_flavours_split.py` (which is the dedicated test file for this exact function) exercises the combination of "K>2 gate fires" + "diversity check downstream" together.

**MODELS-3 (P1).** `CatboostParamsOptimizer.__init__` builds three rule dictionaries (`drop_if_not_rules`, `allow_if_values_or`, `allow_if_values_and`) that reference `grow_policy` (lines 940, 947, 967) and `model_shrink_mode` (lines 993-998) as condition fields, clearly intending them to be swept search-space dimensions (the rules encode real CatBoost constraints: "Ordered boosting requires SymmetricTree grow policy", "posterior sampling requires Constant model-shrink-mode + Langevin boosting"). I grepped the entire ~115-line `self.params` dict (lines 784-898) and confirmed neither `grow_policy` nor `model_shrink_mode` is ever added as a key. Since `ParameterSampler` only ever samples keys present in `self.params`, every candidate dict passed to `check_rules` has `params.get("grow_policy")` / `params.get("model_shrink_mode")` return `None`, and `check_condition`'s `value_by_key` (`dct.get(key) == expected_value`) treats a missing key as "condition false" unconditionally. For `allow_if_values_or`'s `boosting_type=="Ordered"` gate (line 967), this means the REQUIRED companion condition `grow_policy=="SymmetricTree"` can never be satisfied, so `check_rules` returns `False` for every single candidate where `boosting_type` was sampled as `"Ordered"` — permanently vetoing one of the three `boosting_type` options (~33% of that dimension) from ever appearing in an approved candidate. The same mechanism permanently vetoes `posterior_sampling=True` via the `allow_if_values_and` rule (lines 993-998). This silently narrows the effective HPT search space the tuning system explores, with no error, warning, or test coverage — confirmed via `grep` that no test file references `CatboostParamsOptimizer` beyond `test_favorize_unexplored_cat_loop_identity.py`'s unrelated helper-fixture use of the string `"grow_policy"`.

**MODELS-4 (P2).** In `check_rules`'s `allow_if_values_or` block (`tuning.py:149-166`), the gate-check loop `for condition in conditions: if not check_condition(condition, params): skip=True; break` leaves `condition` bound to its last-iterated value in Python (loop variables outlive the loop). The subsequent `if not skip: if check_condition(condition, params):` re-checks that same last condition — which, given the loop only reaches `not skip` when every condition (including the last) already returned `True`, is provably always `True` and therefore dead code in the common case. The real defect is what happens when `conditions` is an empty tuple `()`: the `for` loop body never executes, `skip` stays `False` (its initial value), and `condition` is never assigned — `if check_condition(condition, params):` then raises `NameError: condition is not defined` (Python has no `UnboundLocalError` protection for names never assigned in any branch of a function once the interpreter reaches that line). The DSL otherwise treats an empty conditions/fields list as legitimate elsewhere in the same function (`skip_if_values_or`'s inner `for field_cond in fields:` degrades gracefully to a no-op loop on an empty `fields`), so an empty `conditions` key here is a plausible, currently-untested caller input that would crash.

**MODELS-5 (P2).** `favorize_unexplored(candidates, probs, trials, cat_features, order: int = 1)`'s docstring promises "Assign higher select probabilities to combinations of order N that were never chosen yet" but the implementation (lines 358-381) only ever iterates `for param in cat_features:` checking each individual categorical VALUE against `already_sampled[param]` — there is no notion of an order-2+ "combination" anywhere in the body, and the `order` parameter is never referenced after its declaration. The one call site in the codebase (`tuning.py:724`) always passes `order=1`, so the gap is currently invisible, but the function signature and docstring actively invite a future caller to pass `order=2` expecting pairwise-combination favorization and silently get single-value behavior instead — the classic "parameter accepted but silently ignored" bug class this project's own memory notes call out as a recurring correctness-bug class to watch for.

**MODELS-6 (P2).** `masked_multilabel_logloss_objective`'s `objective` closure (`masked_multilabel_objective.py:85`) computes `care_mask = y_true_arr != sentinel` where `y_true_arr = np.asarray(dtrain.get_label(), dtype=np.float64)`. XGBoost's `DMatrix` stores labels internally as `float32` regardless of what dtype was passed to its constructor, so `dtrain.get_label()` returns values that have already been rounded through a float32 round-trip. The default sentinel `2.0` is an exact float32 value so this is safe by construction today, but the function's own docstring explicitly documents `sentinel` as a caller-configurable parameter ("must be outside {0, 1}") with no mention of the float32-representability constraint. A caller who picks e.g. `sentinel=1.0001` (a value that reads as "clearly outside {0,1}" to a human) would get a value that, after `flatten_masked_multilabel`'s float64 write followed by XGBoost's internal float32 downcast, may no longer compare bit-equal to the float64 `1.0001` this closure re-derives — silently un-masking or over-masking "don't care" cells and corrupting the trained model's gradients with no error surfaced anywhere.

**MODELS-7 (P2).** `combine_probs`'s "qube" flavour (`ensembling/base.py:723-728`) computes `_safe = np.clip(stacked, 1e-103, None) if (stacked > 0).all() else stacked`. The intent (per the surrounding comment) is to protect against `p**3` underflow for extremely-small-but-positive probabilities. Because the guard is gated on a single `.all()` reduction over the WHOLE `(K, N[, C])` tensor, one exact `0.0` prediction anywhere at all (routine at production scale — millions of rows across multiple members, hard-thresholded probabilities, or a genuinely certain prediction) disables the clip for every OTHER cell in the same call too, including cells belonging to entirely different rows/members that may hold genuinely tiny-but-positive values that DO need the floor. The fix is a strict improvement at the same cost: `np.where(stacked > 0, np.clip(stacked, 1e-103, None), stacked)` protects every positive cell individually while leaving true zeros untouched, with no `.all()` reduction needed at all.

**MODELS-8 (P2).** `enrich_ensemble_preds_with_numaggs` (`ensembling/base.py:405-424`) guards its `numaggs_kwds` parameter against the mutable-default-argument foot-gun correctly (`if numaggs_kwds is None: numaggs_kwds = {"whiten_means": False}`), but then calls `numaggs_kwds.update(dict(directional_only=False, return_hurst=..., return_entropy=...))` directly on whatever object was passed in — if a caller supplies their OWN dict (not `None`), that dict is mutated in place as a side effect the function's signature gives no indication of. I confirmed via `grep` that no current in-repo caller passes an explicit `numaggs_kwds` to this specific function (the risk is currently latent, not exercised), but the function is exported and any future/external caller reusing a `numaggs_kwds` dict across multiple calls (a natural pattern, since it looks like a read-only config dict) would see it silently drift.

**MODELS-9 (P1).** `additive_interaction_diagnostic`'s inner `_cv_score` closure (lines 89-103) splits `X` and `y` per fold. For `X`, the function is careful: `X_train = X_source.iloc[train_idx] if is_frame else X_source[train_idx]` — explicitly using `.iloc` (positional) when `X` is a DataFrame, to avoid pandas' label-vs-position ambiguity. For `y`, no equivalent care is taken: `model.fit(X_train, y[train_idx])` / `metric_fn(y[test_idx], pred)` index `y` directly. The function signature types `y: np.ndarray`, but nothing enforces that at the call boundary, and `y` is exactly the kind of object (`the full feature/target arrays`, per the docstring) that in real mlframe pipelines is very commonly a `pandas.Series` sliced from a DataFrame column upstream — which frequently carries a non-default (non-`RangeIndex`) index after any prior row filtering, deduplication, or `train_test_split`. For such a `Series`, `y[train_idx]` performs pandas' bracket-indexing, which is either label-based (silently returning the WRONG rows whenever `train_idx`'s integer values happen to collide with different index labels) or raises a confusing `KeyError` (when they don't collide at all) — neither of which is the intended positional row selection. This is a textbook train/test-split misalignment bug (a form of the "ML correctness: data leakage" dimension the audit brief calls out), and it is completely untested: both dedicated biz-value tests (`test_biz_val_additive_interaction_diagnostic.py`, `test_biz_val_additive_interaction_diagnostic_per_feature.py`) construct `y` as a plain `np.ndarray`.

**MODELS-10, MODELS-14 (P3, both in `create_ctr_params`).** MODELS-10 is a purely defensive-coding nit (unreachable today, given the specific call site never passes rule kwargs). MODELS-14 is a real, if narrow, type-coercion bug: `"CrossEntropy" in params.get("loss_function", [])` relies on `params["loss_function"]` being a list; if it is ever a bare string (a very natural thing for a caller of the free function `create_ctr_params` to pass, since CatBoost's own `loss_function` kwarg IS a bare string in normal usage), Python's `in` silently degrades to a substring test, so `"QueryCrossEntropy"` would incorrectly match. I confirmed this exact call path is unreachable via `CatboostParamsOptimizer` today only because `loss_function` is never a key in its `self.params` (see MODELS-3), so this is presently a latent trap for the standalone function's other callers, not an active production bug.

**MODELS-11 (P3).** Representative broad-except sites at `DEBUG` level (as opposed to the many *other* broad-excepts in this same package that correctly log at `WARNING`, e.g. `score_gate.py:233-237`, `score_flavours.py:333-334`) were sampled at `_optimization_shared.py:212-215` (matplotlib plotting), `ensembling/process_method.py:370-372` (member-disagreement-panel stashing), and `ensembling/score_flavours.py:223-225,451-453` (identical-predictions collapse check, ensemble-label regex rebuild). None of these are individually severe (all are best-effort diagnostic/cosmetic code paths where failure genuinely shouldn't block training), but the inconsistency in log level across near-identical `except Exception` patterns in the same package is worth normalizing, and a silent `DEBUG`-only swallow is the specific pattern this project's own memory notes flag as a recurring "error swallowing" bug class.

**MODELS-12 (P3).** `_gate_cache` (`ensembling/predict.py:44-107`) is a well-reasoned, carefully-documented memoization (it correctly retains a strong reference to the cached prediction arrays specifically to prevent `id()` reuse after garbage collection — a subtlety many caches get wrong). The one gap it does not close is in-place mutation of a still-live, still-cached array: because the key is purely `id()`-based with no content fingerprint, a caller that mutates a prediction array's VALUES (not its identity) between two calls with the same thresholds would silently get back the first call's stale gate decision. Given the module runs one per `loky` worker process (not shared across threads, confirmed via `score.py`'s `backend="loky"` comment), the practical risk window is narrow, but the invariant is undocumented and untested.

**MODELS-13 (P3).** `compute_candidates_exploration_scores` (`_optimization_shared.py:86-109`) explicitly documents "Assuming search_space is sorted" but doesn't document (or guard) the additional implicit assumption that `search_space` holds unique values — `indices = {el: i for i, el in enumerate(search_space)}` silently keeps only the LAST index for any repeated value, which would compute wrong per-point distances for the earlier duplicate(s) if `known_candidates` ever referenced the ambiguous value. Given every current caller passes a unique-valued integer range, this is unexercised but undocumented.

**MODELS-15 (P2).** Verified empirically (see meta-test cell) that `import mlframe.models as m; m.__all__` currently contains 13 names that are not `mlframe`-owned symbols at all: `pd`, `np`, `db` (the `pyutilz.db` module object), `uniform`, `loguniform`, `randint` (scipy.stats distributions), `KFold`, `train_test_split`, `cross_validate`, `check_scoring` (sklearn), `Enum`, `auto` (stdlib), plus the mutable process-global `trained_models` dict. All of these leak in because `tuning.py` — unlike its sibling `rf_proximity.py`, which correctly defines its own `__all__` — has no `__all__` of its own, so `mlframe.models.__init__`'s `from mlframe.models.tuning import *` pulls in every non-underscore name in the module's namespace, which `models/__init__.py`'s own subsequent `__all__ = sorted(name for name in globals() if not name.startswith("_"))` curation step cannot distinguish from genuinely intended exports. This directly contradicts the design comment immediately above that line ("Curate the star-import surface explicitly (mirrors mlframe.metrics.__init__'s pattern)"). The existing `test_f5_package_has_curated_all` meta-test only checks that `__all__` exists, is non-empty, and has no duplicates — it does not check for exactly this class of leak, so the regression is currently invisible to CI.
