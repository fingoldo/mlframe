## Narrative

### FS_WRAPPERS-1 (P0): NaN-impute crashes on non-numeric columns
`rfecv/_nan_policy.py`'s `apply_nan_in_X_policy` (the default `nan_in_X_policy='impute'` path) computes `nan_cols = [c for c in X.columns if X[c].isna().any()]` across **every** dtype, then unconditionally imputes each with `col.to_numpy(dtype=float, na_value=np.nan)` followed by `np.nanmedian`. For a genuine string/object/category column with NaN (a routine shape whenever `cat_features` are used with a non-tree or non-CatBoost-family core estimator, or in a multi-estimator run mixing a tree model with a linear one — `_any_core_tolerates_nan` requires ALL configured estimators to tolerate NaN, so one linear estimator in the mix forces imputation across the board), the cast raises `ValueError: could not convert string to float`. Confirmed live: `apply_nan_in_X_policy(self, X)` with `X = {'num': [...NaN...], 'cat': pd.Series(['a','b',None,'a'], dtype='object')}` and `self.estimator = LogisticRegression()` raises exactly this error. This directly defeats the module's documented purpose ("RFECV used to hard-crash [on NaN]... `nan_in_X_policy` closes that gap with a graceful default") for a realistic subset of its own intended domain. Rated P0 per the rubric's explicit inclusion of "crash" as P0 material — this crash happens inside RFECV's own preprocessing on the default configuration, not a rare or opt-in path.

### FS_WRAPPERS-2 (P1): minority-class CV validation skipped for float y
`rfecv/_fit_init.py`'s `_init_fit_state` guards the "minority class has fewer samples than `cv`" check behind `class_counts = np.bincount(y_arr.astype(int)) if y_arr.dtype.kind in "iu" else None` — restricted to signed/unsigned integer dtype. Any float-typed classification target (e.g. `y = df['label'].to_numpy()` on a float64 column, or a `LabelEncoder` output someone forgot to cast) skips the check entirely, even though `len(unique_y) < 2` (a few lines above) already proves classification labels can arrive as float. Confirmed live: a 30-row frame with a float `y` whose minority class has exactly 1 sample and `cv=5` sails past `_init_fit_state` (only a soft sklearn `UserWarning`), then crashes deep inside `LogisticRegression.fit` with `"This solver needs samples of at least 2 classes... but the data contains only one class"` — precisely the failure mode the skipped validation exists to catch with a clear, actionable message ("Minority class has %d samples but cv=%d... Reduce cv or oversample the minority class").

### FS_WRAPPERS-3 (P1): select_features_fdr is O(p²), contradicts its own "sub-second" promise
`_knockoffs.py`'s `select_features_fdr` computes, for every distinct `|W|` value (up to p of them), `n_neg = sum(1 for v in W.values() if v <= -t)` and `n_pos = sum(1 for v in W.values() if v >= t)` — two full Python-level scans of `W` per candidate threshold, i.e. O(p²) total. Measured directly: `select_features_fdr` on p=5000 synthetic `W` values takes **6.41s**. `rfecv/_validate.py`'s own p≥5000 warning message explicitly tells users to use `importance_getter='knockoff'` / this function "for sub-second selection on this scale" — the measurement flatly contradicts that documented claim, and at p≥10000 (a realistic wide-data scenario this exact code path targets) the cost would scale to tens of seconds. This is squarely in the perf-efficiency review dimension: an O(n) or O(n log n) vectorized rewrite (sort `|W|` once, use cumulative counts / `searchsorted`) is straightforward here.

### FS_WRAPPERS-4 (P2): stability_selection dispatches before estimator-presence validation
`rfecv/_fit.py:fit()` checks `if self.stability_selection: return self._fit_stability_selection(...)` at line 289, but the `estimators_list = list(self.estimators) if self.estimators else (...)` + `raise ValueError("RFECV requires either estimator= or estimators=.")` guard sits at lines 295-297 — after the stability-selection early-return already fired. Confirmed live: `RFECV(stability_selection=True).fit(X, y)` with no `estimator=`/`estimators=` raises `AttributeError: 'NoneType' object has no attribute '__sklearn_tags__'` (from deep inside `sklearn.base.clone(None)` in `_fit_stability_selection`'s bootstrap loop) instead of the intended, much clearer `ValueError`. A simple config mistake (forgetting `estimator=` while trying stability selection) produces a confusing stack trace pointing at sklearn internals rather than RFECV's own validated contract.

### FS_WRAPPERS-5 (P2): transform() omits the polars self_destruct ownership gate
`rfecv/_fit_init.py`'s `_init_fit_state` explicitly gates `X.to_pandas(..., self_destruct=_frame_is_internally_owned)` on an ownership marker, with the comment: "ad-hoc / notebook callers who pass their own polars frame would silently lose data" if `self_destruct=True` ran unconditionally. `rfecv/__init__.py`'s `transform()` performs the structurally identical conversion (`X.to_pandas(use_pyarrow_extension_array=True, split_blocks=True, self_destruct=True)`) but with **no** such gate — `self_destruct=True` unconditionally, for ANY polars `X` a caller passes to `.transform()`. I attempted to reproduce actual data loss on the installed polars 1.41.2 (comparing a polars DataFrame's own byte-sum before and after `.transform()`) and did **not** observe corruption — the pyarrow-extension-array bridge in this version appears to destruct only a transient Arrow Table, not the caller's own polars buffers. I'm flagging this as a design-consistency gap (the same safety rationale that motivated the fit-path's gate applies verbatim to `transform()`, and the two code paths have silently diverged) rather than a confirmed corruption, per the project's evidence-based severity discipline — but it is worth closing defensively since a different polars version, or a `pl.LazyFrame`-derived / already-referenced object, could behave differently.

### FS_WRAPPERS-6 (P2): asymmetric error handling in conditional-permutation-importance's two branches
`_helpers_importance.py`'s `_conditional_permutation_importance` has two structurally parallel code paths for the per-repeat scoring loop: the general (`p>1`, conditioning-set) branch wraps `model.score(X_for_score, y)` in `try/except Exception` with an explicit comment ("so a custom scorer crash on the permuted X doesn't kill the whole CPI loop... NaN signals the failure to the consumer"), while the `p==1` (single-feature, vanilla-shuffle fallback) branch a few lines above calls `model.score(X_for_score, y)` completely unguarded. Given the whole point of the surrounding `try/finally` is to restore `X_perm` even on failure, the omission of the score-call try/except on the `p==1` path is very likely an oversight rather than an intentional difference — it means a single-feature CPI computation is strictly less robust to a flaky/crashing scorer than the general multi-feature path, for no stated reason.

### FS_WRAPPERS-7 (P3): split_into_train_test's public fast-path crashes on a valid-looking misuse
`_helpers.py`'s `split_into_train_test` selects its `X_estimator` fast-path sub-branch via `elif col_pos is not None and not isinstance(features_indices[0], (int, np.integer)): ... else: fi_arr = np.asarray(features_indices, dtype=np.intp)`. When `X_estimator` is supplied but `col_pos` is `None` (and `features_indices` are feature-name strings, not integers), the `elif` condition is False (because `col_pos is not None` fails), so control falls into the `else` branch, which tries to cast the string names directly to `np.intp` — an opaque `ValueError: could not convert string to float`-style crash with no hint that `col_pos` was the missing piece. This is not reachable today (the sole in-scope caller, `rfecv/_fit.py`, always sets `X_estimator` and `col_pos` together), but `split_into_train_test` is exported in `wrappers/__init__.py`'s `__all__` as public API with no docstring warning about this pairing requirement, so any future or external caller hits a confusing failure mode instead of a clear contract violation.

### FS_WRAPPERS-8 (P3): concurrent set_params mutation of a shared estimator across joblib threads
`rfecv/_fit_outer_loop.py`'s `_eval_fold_pinned` wrapper (used when `n_jobs_effective>1 and _is_multithreaded and self.force_parallel`) calls `pin_threads_to_one(estimator)` — which internally does `estimator.set_params(**pinned)` — once per fold, from inside the per-fold closure that `joblib.Parallel(prefer="threads", ...)` dispatches across multiple worker threads. Since `estimator` is the single shared outer-scope object (not a per-fold clone — the clone happens later, inside `_eval_fold_body`), multiple threads race to call `.set_params()` on the SAME object concurrently. This happens to be safe today only because every thread writes the identical `{thread_count: 1, ...}` values, so there's no observable corruption — but it's an unguarded, undocumented concurrent-mutation pattern on a shared mutable object that would silently break if a future change made the pinned values vary per fold.

### FS_WRAPPERS-9 (P3): SFFS swap-pass log denominator can overstate attempted pairs
`rfecv/_sffs.py`'s `_sffs_swap_pass` builds `swap_out = kept_sorted[:K]` and `swap_in = not_sorted[:K]` (each independently capped at `K = self.swap_top_k`, but each can be shorter than `K` if fewer candidates exist), then iterates `for out_f, in_f in zip(swap_out, swap_in)`. `zip` silently truncates to the shorter of the two lists. The final summary log line reports `n_swaps_accepted, len(swap_out)` as "X/Y paired swaps accepted" — when `len(swap_in) < len(swap_out)` (fewer features are available to swap IN than the K worst-kept features), `len(swap_out)` overstates how many pairs the loop actually attempted, producing a misleading (inflated) denominator in the log/diagnostic output.

## Coverage notes by review dimension

1. **Correctness bugs**: FS_WRAPPERS-1, -2, -6, -7 (crashes / exception-swallowing asymmetry / cast failures).
2. **ML correctness (leakage / reproducibility / sample_weight)**: no new issues found. The existing code is unusually well-hardened here (deterministic per-fold RNG seeding, `must_include`/`must_exclude` handling, leakage-corr scan, nested-prescreen honesty fix, sample_weight threaded through every fold/scorer/swap-pass path) — reviewed in depth and found no gaps.
3. **Computational efficiency**: FS_WRAPPERS-3 (O(p²) `select_features_fdr`). No other unbounded/quadratic hot paths found; the rest of the codebase is heavily perf-annotated with prior documented fixes (streamed hashing, vectorized aggregation, cached signature lookups) that were verified consistent with their stated rationale.
4. **Edge cases / robustness**: FS_WRAPPERS-1, -2, -4, -5, -7.
5. **Test coverage gaps**: no dedicated test found exercising `apply_nan_in_X_policy` on an object/category-dtype column with NaN (FS_WRAPPERS-1's exact failure mode); no test found calling `stability_selection=True` with no estimator configured (FS_WRAPPERS-4); no test found round-tripping `.transform()` on a caller-owned (not suite-internally-marked) polars DataFrame twice to check for `self_destruct` side effects (FS_WRAPPERS-5); no benchmark/perf-regression test bounding `select_features_fdr`'s wall time at realistic p (FS_WRAPPERS-3).
6. **Code quality / architecture**: FS_WRAPPERS-6, -8, -9 are all inconsistency/hygiene issues (asymmetric error handling, undocumented concurrency pattern, a cosmetic log-denominator bug). No dead code, no misleading docstrings, and no overly-broad `except Exception` clauses without an accompanying debug-log were found beyond what's already itemized — the module is unusually disciplined about narrow excepts + debug logging (`# nosec B110 - swallow converted to debug-log, non-fatal by design` pattern is used consistently).
7. **OSS / hygiene**: no stale audit-wave markers, mojibake, or comment-cruft found in this cluster; comments consistently explain WHY, not WHAT, matching project convention. No P3 "pure cleanup" findings beyond FS_WRAPPERS-7/-8/-9 above.
