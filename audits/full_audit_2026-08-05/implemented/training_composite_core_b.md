## Narrative detail

**TRAINING_COMPOSITE_CORE_B-1 (qrf.py, P1, efficiency).** `_leaf_weights_kernel` (numba-parallel) and its numpy fallback in `_LeafResidualForest._leaf_weights` build the `(n_query, n_train)` QRF membership-weight matrix by, for every query row and every tree, scanning **all** `n_train` training rows to test `train_leaves[j, t] == leaf`. The kernel's own docstring is explicit about this ("Looping (tree, query, train) in machine code... it walks the integer leaf ids directly") — it optimizes away the *dense boolean allocation* the naive numpy broadcast would need, but not the underlying O(n_query·n_trees·n_train) work. Since a Meinshausen QRF's whole point is that only the ~`min_samples_leaf` rows sharing a query's leaf matter, this scan does up to `n_train / min_samples_leaf` times more work than necessary per (query, tree) pair. At realistic production scale (n_train in the 1e5-1e6 range, n_estimators=200 default, `_PREDICT_BATCH=512`) a single predict batch does on the order of `512 * 200 * 1e5 ≈ 1e10` elementary comparisons — this can turn a "single QRF fit serves any query cheaply" design (the module's own selling point) into a multi-minute-per-batch bottleneck. This is a pure algorithmic-complexity gap, not a wrong-result bug: the output is correct, just far slower than the leaf-bucketed alternative (sort each tree's training rows by leaf id once at fit; predict-time work becomes proportional to the matching leaf's own size).

**TRAINING_COMPOSITE_CORE_B-2 (pseudo_labeling.py, P1, ML-correctness / sample_weight threading).** `PseudoLabelingLoop._fit_final` is the single call site that fits the class's `final_model_` on the mix of real-labeled rows (weight 1.0) and pseudo-labeled rows (weight `pseudo_label_weight`, default 0.5 — the class's documented "confirmation-bias guard"). It is implemented as `try: model.fit(X, y, sample_weight=sample_weight) except TypeError: model.fit(X, y)`. This is precisely the anti-pattern `post_shim.py`'s `_model_fit_accepts_sample_weight` docstring (same directory, same review cluster) describes fixing: *"a TypeError raised DEEP inside a fit that does accept sample_weight (a bad dtype, a shape mismatch, a downstream library bug) was mis-attributed to 'no sample_weight support' and the model was silently re-fit UNWEIGHTED — dropping the weighting the caller asked for AND hiding the real error."* Here the consequence is specific and severe for this class: if the underlying `TypeError` fires for any reason other than "no sample_weight parameter", the final model silently trains with real and pseudo-labeled rows at EQUAL weight, defeating the class's entire "confirmation-bias guard" design promise — with no log line, no exception surfaced, nothing observable short of a downstream accuracy regression. `post_shim.py` in the exact same directory already has the fix pattern (`sklearn.utils.validation.has_fit_parameter`) ready to reuse.

**TRAINING_COMPOSITE_CORE_B-3 (meta.py, P2, edge case / robustness).** `CompositeOrRawStacker.fit` derives its KFold split count as `n_splits = int(max(2, min(self.n_splits, n)))`, intending "clamp to at most `n` rows, but never below 2". For `n=0` or `n=1` this clamp still returns `n_splits=2` (since `max(2, ...)` floors the result), so `KFold(n_splits=2, ...).split(np.arange(n))` is called with more splits than samples, and sklearn raises its own internal `ValueError` ("Cannot have number of splits n_splits=2 greater than the number of samples"). This is a legitimate edge case explicitly in this audit's scope (single-row input); the failure is not silent (it does raise), but it surfaces as an opaque sklearn internals error rather than a clear, actionable message naming `CompositeOrRawStacker` and the actual problem (too few rows to OOF-split).

**TRAINING_COMPOSITE_CORE_B-4 (panel.py, P2, efficiency + hygiene).** `_compute_offsets`'s docstring reads *"Computed in one vectorised groupby pass over the fit data"*, but the actual body is `for e, val in zip(ids.tolist(), y.tolist()): if e in sums: sums[e] += val; counts[e] += 1 else: sums[e] = val; counts[e] = 1` — a pure Python per-row loop with dict lookups, not a vectorized groupby by any definition. The accompanying inline comment ("a single argsort-free dict reduction... is cheaper than building a full index") is honest about the mechanism, but the docstring's headline claim is not, which is itself a documentation-accuracy issue (this audit's "stale/misleading docstrings" dimension). Separately, this loop is a genuine efficiency concern: the module's own header docstring targets "repeated-measures data (entity x time)" at panel scale (customers across months, sensors across cycles) which routinely runs into millions of rows, and a Python-level per-row loop with `.tolist()` materialization is orders of magnitude slower than the `pandas.Series.groupby(ids).agg(['sum','count'])` or `np.bincount`-on-factorized-ids alternative that would still be O(n) but with a far smaller constant.

**TRAINING_COMPOSITE_CORE_B-5 (venn_abers.py, P2, efficiency).** `_ivap_saddle_njit`'s own docstring is unusually candid about its complexity: *"the outer max over lo explicitly rescans lo = i..0 for every bin i -- that scan alone is sum_{i=0}^{g-1}(i+1) = O(g^2) total, NOT near-linear in g... a caller with a very large calibration set should be aware the cost grows quadratically in g."* This is a real, currently-unmitigated cost: nothing in `calibrate_venn_abers` warns, caps, or subsamples when `g` (the number of *unique* calibration scores) is large — and for a continuous model score with little tying, `g` scales with the calibration-set row count directly. A caller who reasonably calibrates Venn-Abers on a full val split (tens of thousands of rows, common in this codebase's own suite-wide holdout conventions) can hit a multi-second-to-minutes calibration step for what the module's docstring otherwise describes as "O(n log n) once" calibration. Flagged here (rather than accepted as a documented, closed tradeoff) because there is no size guard or fallback path — only a comment.

**TRAINING_COMPOSITE_CORE_B-6 (glm.py, P3, ML reproducibility hygiene).** `CompositeGLMEstimator._default_inner` builds `lgb.LGBMRegressor(n_estimators=300, objective=objective, verbose=-1, n_jobs=-1)` with no `random_state`. The directly comparable sibling default-builder in this same cluster, `highlevel.py._default_inner_estimator`, explicitly sets `random_state=0` with an inline rationale about `HistGradientBoostingRegressor`'s auto early-stopping drawing a random split. Today LightGBM's default `_default_inner` config has no `bagging_fraction`/`feature_fraction` set, so its own internal randomness likely doesn't fire — but that is an implicit, undocumented invariant this function relies on for reproducibility, not an explicit contract, and it is inconsistent with the established pattern one file over in the same cluster.

**TRAINING_COMPOSITE_CORE_B-7 (long_format_gbm.py, P2, edge case).** `melt_to_long_gbm_features`'s within-column frequency count is computed via `melted.groupby(["_feature_name", "_value"])["_value"].transform("count")`. pandas' `groupby` defaults to `dropna=True`: any row whose `_value` (the melted original feature value) is `NaN` is excluded from grouping entirely, and `.transform` returns `NaN` for those excluded rows rather than a valid count. `X` (the wide feature frame this function melts) is exactly the kind of table that routinely carries missing values in production feature engineering — yet there is no test, comment, or documented behavior for this path; the `NaN` silently propagates into `X_long`'s `"_count"` column (and if `context_columns` further references the same rows, into those too), and depending on `model_factory`'s NaN tolerance this can either silently degrade the OOF fit (for a NaN-tolerant learner like LightGBM/CatBoost) or crash deep inside a NaN-intolerant one with an unhelpful stack trace.

**TRAINING_COMPOSITE_CORE_B-8 (glm.py, P3, error-swallowing / diagnosability).** `_default_inner`'s lightgbm import is wrapped as `try: import lightgbm as lgb except Exception as exc: raise ImportError("...requires lightgbm...") from exc`. Catching `Exception` (rather than the narrower `ImportError`) means any other failure during the import — a broken/mismatched native binary, a version-incompatible C extension, an OS-level DLL load failure — gets relabeled as "requires lightgbm. Install it (`pip install lightgbm`)", actively misleading a user who *does* have lightgbm installed but hitting a genuine environment bug. This is the same bug class this codebase's own CLAUDE.md change-log documents fixing twice already this session (the MI-backend `_select_mi_backend` broad-except downgrade, and the per-call numba/GPU MI dispatch silent fallback) — the general lesson ("narrow the except to the one genuine case, let everything else propagate with its real type") had not yet been applied here.
