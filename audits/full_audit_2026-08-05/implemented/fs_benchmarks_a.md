## Narrative

### FS_BENCHMARKS_A-1 — `_datasets.py` shared-scenario module is unimportable (P1)

`_datasets.py` is documented in its own module docstring as "Deterministic synthetic dataset generators for the MRMR benchmark suite" and its `Scenario` dataclass is left at module scope (correctly importable). However every other top-level binding — the `SCENARIOS` dict, the derived `CPU_SCENARIOS`/`GPU_SCENARIOS` lists, `make_scenario_data`, and `list_scenarios` — is indented one level inside `if __name__ == "__main__":` (lines 30-77). Python only executes that block when the file itself is the entry point (`python -m ...bench_mrmr` does NOT execute `_datasets.py` as `__main__`; it merely imports it), so on import none of those five names exist on the module object.

I confirmed this is not a hypothetical concern: `grep -n '_datasets\.' bench_mrmr.py` (the package's own documented entry point, referenced in `_benchmarks/__init__.py`'s docstring: *"Run with: `python -m mlframe.feature_selection._benchmarks.bench_mrmr --scenarios all --tag pre-refactor`"*) shows it calling `_datasets.Scenario`, `_datasets.make_scenario_data`, `_datasets.list_scenarios(include_gpu=...)`, `_datasets.GPU_SCENARIOS`, and `_datasets.SCENARIOS[n]` — every one of the names trapped inside the `__main__` guard. Running the package's own documented command therefore raises `AttributeError: module '...._datasets' has no attribute 'list_scenarios'` (or similar) immediately upon `--scenarios all/all-with-gpu/<any name>` handling, before a single benchmark scenario executes. This is a hard crash on the primary, doc-advertised way to run this benchmark suite, and it also means no benchmark in this directory (or the sibling `fs_benchmarks_b`/`fs_benchmarks_c` shares) has ever actually exercised `bench_mrmr.py`'s scenario grid since this file was last touched, because the very first import-time-adjacent call would fail. `bench_mrmr.py` itself lies outside this cluster's alphabetical slice, but `_datasets.py` — the broken file — is squarely in scope.

### FS_BENCHMARKS_A-2 — unseeded RNG for the "legacy" comparison arm in `bench_hermite_fe.py` (P2)

`bench_hermite_fe.py` benchmarks an "improved" Hermite-pair feature-engineering search against a reproduction of the pre-existing "legacy" implementation, printing an uplift ratio per synthetic regime. All data generation uses `np.random.default_rng(seed)` and the "improved" path (`optimise_hermite_pair(..., seed=42)`) and its Optuna sampler (`TPESampler(..., seed=42)`) are both explicitly seeded — the file is clearly written with reproducibility as a design goal. But inside `_legacy_hermite` (lines 216-217), the number of Hermite coefficients tried per trial (`length_a`, `length_b`) is drawn via the legacy, module-global `np.random.randint(3, 8)`, which this file never seeds anywhere (no `np.random.seed(...)` call exists in the file). Consequently the "legacy" column of the printed comparison table is non-deterministic across runs even though every other column is pinned — two engineers re-running this bench to sanity-check a regression will see the "legacy" baseline drift run-to-run for reasons unrelated to any code change, which is exactly the kind of hidden-nondeterminism class the project's ML-correctness review dimension calls out. I verified via `grep -n 'np\.random\.(randint|rand|randn|choice|shuffle|permutation|seed)'` (excluding `default_rng`/`RandomState`) across all 67 files that this is the only occurrence of legacy-global-RNG usage in the entire cluster — every other file consistently uses seeded `Generator` instances.

### FS_BENCHMARKS_A-3 — dead self-mapping dict with a misleading comment in `bench_adaptive_nbins_ab.py` (P3)

Both `_treatment_applies` (line 160) and `_run_fold_ab` (line 174) construct `{"fayyad_irani": "fayyad_irani", "blocks": "blocks"}.get(method, method)`. Since every key in the dict maps to itself, and the fallback for any other key is the key itself, this expression is identical to `method` for every possible input — the dict does no translation whatsoever. The comment directly above the second occurrence ("blocks/mdlp method names in dispatcher") implies an MDLP name alias is being resolved here, but no `"mdlp"`-keyed entry exists anywhere in the dict, so the comment describes behavior the code does not have. This is harmless today (no wrong routing results, since `method` passes through unchanged either way) but it is dead code that actively misleads a future maintainer into thinking a name-translation layer exists between the treatment table and the `per_feature_edges` dispatcher's `method` kwarg space. Found by direct reading of both call sites and confirming the dict's key/value pairs are textually identical.
