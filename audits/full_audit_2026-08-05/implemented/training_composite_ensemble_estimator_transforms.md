## Narrative

### TRAINING_COMPOSITE_ENSEMBLE_ESTIMATOR_TRANSFORMS-1 (P1) — `predict_quantile` skips the soft-base-shrink OOD guard

`CompositeTargetEstimator.__init__` documents `soft_base_shrink` as default-ON ("Default ON... False keeps the raw additive inverse. In-range predict is bit-identical either way") and `estimator/_predict.py`'s `_predict_unclipped` (backing `predict()` / `predict_pre_clip()`) faithfully calls `_soft_shrink.compute(self, transform, base_arr, params)` before inverting, then `apply_smart_fallback` for deeply-OOD rows (causal-lag failsafe). `predict_quantile` (same file, `estimator/_predict.py:358-536`) implements a parallel path — it duplicates the domain-check gate and the T-clip gate from `predict()` — but never calls `_soft_shrink.compute` or `apply_smart_fallback`; `_invert_one`'s closure passes the raw `base_arr` straight into `_inverse_with_fallback`. I confirmed this by reading both functions side-by-side and grepping the whole `_predict.py`/`_soft_shrink.py` pair for every call site of `_soft_shrink.compute` — there is exactly one, inside `_predict_unclipped`. For any `ADDITIVE_BASE_TRANSFORMS` member (`diff`, `linear_residual`, `linear_residual_multi`, ...) with a predict-time base value outside the fit-time calibration range, `.predict(X)` bounds the extrapolation (soft-clip toward the boundary, saturating at one IQR) while `.predict_quantile(X, 0.5)` on the identical row extrapolates linearly and unbounded, and neither gets the causal-lag smart-fallback for deep-OOD rows. This also silently propagates into any conformal/CQR interval built on `predict_quantile` (though `conformal.py` itself is out of this cluster's scope). No test in `tests/training/composite/estimator/` exercises this combination (`grep predict_quantile tests/training/composite/estimator/test_biz_val_soft_base_shrink.py` returns nothing).

### TRAINING_COMPOSITE_ENSEMBLE_ESTIMATOR_TRANSFORMS-2 (P2) — `linear_residual_multi_robust` missing from the soft-shrink allow-list

`transforms/_multi_extra.py`'s `_linear_residual_multi_robust_fit` is a trimmed-LS refit that returns the *same* `{"alphas", "beta", "condition_number", "collinear_fallback"}` dict shape as `_linear_residual_multi_fit`, and the registry entry (`transforms/_registry_extended.py:528-538`) wires `forward=_linear_residual_multi_forward, inverse=_linear_residual_multi_inverse` — literally the same function objects `linear_residual_multi` uses. `estimator/_soft_shrink.py`'s `ADDITIVE_BASE_TRANSFORMS` frozenset (the allow-list gating both `capture_base_fit_range` at fit time and `is_enabled`/`compute` at predict time) lists `"linear_residual_multi"` but not `"linear_residual_multi_robust"`. Since both `capture_base_fit_range` and `is_enabled` key off `transform.name` (a plain string), not the underlying forward/inverse identity, `linear_residual_multi_robust` never gets `BASE_FIT_RANGE_KEY` captured at fit and `is_enabled` always returns `False` at predict — it silently runs the raw, unbounded additive inverse on out-of-range multi-base rows while its mechanically-identical sibling does not. I verified there is no test referencing `ADDITIVE_BASE_TRANSFORMS` at all (`grep -r ADDITIVE_BASE_TRANSFORMS tests/` — no hits), so this asymmetry is unguarded.

### TRAINING_COMPOSITE_ENSEMBLE_ESTIMATOR_TRANSFORMS-3 (P3) — `second_diff` also missing from the same allow-list

`transforms/_second_diff.py`'s inverse is `y = T_hat + 2*b1 - b2`, a fixed-coefficient purely-additive-linear-in-base combination in the same family as `diff` (`y = T_hat + base`, alpha implicitly 1) — and `diff` IS a member of `ADDITIVE_BASE_TRANSFORMS`. `second_diff` is not, so an out-of-range lag pair (`b1`/`b2` far outside train range — plausible for a persistent-target predict batch that continues far past train) extrapolates through the fixed `2*b1 - b2` term unbounded instead of being soft-clipped like `diff`'s single-base case. This is a secondary/lower-confidence instance of the same finding class as -2: `second_diff` is explicitly documented as "NOT in the default transform list", so the practical blast radius is smaller, but the gap is real and the fix is identical (one frozenset entry) — `shrink_base`'s `(n, K)` code path already handles a 2-column base without modification.

### TRAINING_COMPOSITE_ENSEMBLE_ESTIMATOR_TRANSFORMS-4 (P3) — dead duplicate constants in `nonlinear.py`

`transforms/__init__.py` defines `_MAD_FLOOR_FRAC = 1e-3` and `_MAD_SOFT_CAP_K = 10.0` at module scope (lines 24-27), with a docstring explaining they exist so `logratio`'s soft-cap doesn't collapse to zero on a degenerate train fit. `transforms/nonlinear.py` (lines 146-150) re-defines the identical two names with the identical docstring — but I grepped the whole file for both identifiers and the only hits are the two definition lines themselves; nothing in `nonlinear.py` reads either name (the file has no `logratio` logic — that lives in `linear.py`, which correctly lazy-imports the constants from the *parent* `transforms/__init__.py` via `from . import _MAD_FLOOR_FRAC, _MAD_SOFT_CAP_K` inside `_logratio_fit`). This is leftover dead code from the original monolith-to-siblings carve (both copies were probably present in the pre-split file and only one was ever wired up). It is currently harmless (nothing reads the `nonlinear.py` copy) but is a drift trap: a future edit to `nonlinear.py` that starts referencing "the local `_MAD_FLOOR_FRAC`" (plausible, since the name and docstring look authoritative in-file) would silently diverge from the parent's value the moment one of the two is tuned without editing the other.

## Dimension coverage notes

- **Correctness bugs** (crashes / silently wrong results / off-by-one / mutable defaults / type coercion): no crash-class bug found; no mutable-default-argument bugs (`grep`-verified across the full cluster); the two soft-shrink coverage gaps above (-1, -2, -3) are the only "silently produces a different/worse result than the documented contract" findings. `_rolling_median`'s bottleneck-fast-path centering arithmetic (previously flagged in git history as an off-by-one class of bug and since fixed) was independently re-verified bit-identical to the pandas reference across 200 randomized `(n, k)` trials including `k > n`.
- **ML correctness** (leakage / reproducibility / calibration / sample_weight / honest OOS / class imbalance): `_oof_split.py`'s `_carve_inner_eval_split` and `_cross_target.py`'s OOF paths were read in full — group-aware carving, per-fold transform refit, and sample_weight alignment (`_align_fit_sw`) are all leak-conscious and internally consistent; no imbalance-relevant logic in this cluster (no classification target handling here — regression-only composite transforms). No RNG-reproducibility issue found (`_theilsen_residual_fit`'s hardcoded `default_rng(0)` is intentional/documented determinism, not a bug — different calls always operate on different underlying `(y, base)` slices).
- **Computational efficiency**: extensive, already well-optimized (numba/parallel dispatch ladders with `kernel_tuning_cache` integration throughout `nonlinear.py`, `_soft_shrink.py`, `unary.py`); no new O(n²)-where-O(n)-available pattern found; `_RingBuffer` in `_update.py` was independently property-tested against `collections.deque(maxlen=...)` across 300 randomized trials and is correct and allocation-free.
- **Edge cases / robustness**: single-row / empty / all-NaN / all-constant paths are explicitly handled in every transform's `fit` (degenerate fallbacks to global median/mean, `n < threshold` guards) — reviewed across all ~30 transform implementations; no gap found beyond -1/-2/-3 above.
- **Test coverage gaps**: the soft-base-shrink × `predict_quantile` interaction (-1) and the `ADDITIVE_BASE_TRANSFORMS` completeness invariant (-2, -3) are the two coverage gaps found; both are named in the meta-test column above as directly promotable regression tests.
- **Code quality / architecture**: the cluster is unusually well-documented (nearly every non-trivial line carries a WHY comment); no dead code beyond -4; no misleading docstrings found beyond the implicit gap in -1 (the `soft_base_shrink` docstring's blanket "Default ON" claim doesn't scope itself to `predict()` only); no overly-broad `except Exception`/bare `except:` clauses in the cluster (grep-verified: zero bare `except:`, and the one narrowed-except comment in `_estimator.py:838` is itself a documented deliberate narrowing).
- **OSS/hygiene**: no mojibake; the handful of non-ASCII characters in the cluster (`nonlinear.py`, `linear.py`) are legitimate Greek-letter/math-notation glyphs (α, β, Σ, σ, ·) in docstrings, not encoding corruption; no stale audit/phase markers found in comments (the cluster's comments consistently follow the "WHY not WHAT" convention).
