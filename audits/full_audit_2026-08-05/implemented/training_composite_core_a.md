## Summary

This is an unusually well-engineered corner of the codebase: extensive docstrings, careful edge-case handling (empty inputs, tiny-n conformal contracts, NaN/Inf guards), leakage-conscious design (OOF splits, held-out calibration, purge/embargo CV), and repeated evidence of prior optimization/correctness passes (numba-fused reductions with documented bench numbers, a `_composite_report_shared.py` / `_composite_array_shared.py` / `_composite_utils.py` trio explicitly created to stop logic drift). Despite that quality bar, two classes of real, reproducible bugs turned up, both confirmed empirically (not just by reading):

1. **A P1 silent-no-op bug** in `_estimator_dispatch.py`: the E3 distribution-driven-estimator injection feature never fires in the realistic case (an actual train/val/test split), because its base-column picker receives the *unfiltered* full training frame while the target vector has already been sliced to `train_idx`. Confirmed empirically — reproduces on toy data, and the existing unit tests never cover a strict-subset `train_idx`, which is exactly why it was never caught.
2. **A P1 polars-down-conversion bug**, independently present in two sibling files (`gated_outlier.py`, `gated_regression_mixture.py`): row-subsetting falls back to `np.asarray(X)[mask]` whenever `X` lacks `.iloc`/`.loc`, silently flattening a polars `DataFrame` to a raw (possibly `object`-dtype) ndarray and losing column names/dtypes — confirmed to actually corrupt/crash on a polars frame containing any non-numeric column, while every sibling module in the same directory (`bagging.py`, `classification.py`, `glm.py`, `classification_discovery.py`) handles polars explicitly via `is_polars_df`/`get_column`.

The remaining findings are lower-severity: a documented-but-unmet NaN-handling contract in a shared helper's no-pandas fallback, a duplicated (and independently-buggy) reimplementation of that same helper, a train/val CV-fold-boundary leak of an imputation statistic (not a label leak), a memory-blowup risk in a CDF plotting/scoring helper, and two very minor hygiene nits.

Dimensions with **zero findings** in this scope: security, mutable-default-argument bugs, class-imbalance handling (not applicable to this cluster — no classifiers with intrinsic class-weighting logic beyond what's already covered), and RNG reproducibility (every stochastic path reviewed seeds explicitly and documents its seed discipline).

## Narrative

### TRAINING_COMPOSITE_CORE_A-1 — E3 distribution-driven estimator injection silently never fires under a real split

`_estimator_dispatch.py`'s `maybe_inject_distribution_driven_estimator` slices the full target vector `y_full` by `train_idx` to get `y_train`, then calls `_pick_base_column(train_df, y_train)` — but `train_df` at this call site (traced through `_main_train_suite.py` → `run_distribution_analyzer_and_estimator_injection` → `_main_train_suite_phases.py`) is the FULL, unfiltered frame (the codebase's own `filtered_train_df` naming convention elsewhere in `training/core/` confirms `train_df` at this point in the pipeline has NOT yet been row-filtered to the train split). `_pick_base_column`'s per-column loop has a `if x.shape[0] != y_arr.shape[0]: continue` guard, so with a real split (`len(train_idx) < len(train_df)`) EVERY column is skipped and the function returns `None`, silently disabling the entire E3 feature (base-column auto-pick → composite-estimator auto-injection) for any run with an actual val/test split — which is virtually every real invocation. Confirmed empirically: with a 100-row synthetic frame and a `train_idx = np.arange(60)`, `_pick_base_column(df, y_full[train_idx])` returns `None` even though the same call with matching-length `y_full` correctly identifies the strongly-correlated column `"f_signal"`. The existing unit tests (`tests/training/test_estimator_dispatch.py`) never exercise a strict-subset `train_idx` — `test_maybe_inject_appends_estimator_and_updates_ctx` uses `train_idx=np.arange(n)` (covering every row), which is exactly the one case where the bug does NOT manifest, explaining how this shipped undetected. Since the feature is opt-in (`behavior_config.distribution_driven_estimator`, default off) the blast radius is limited to callers who explicitly enable it, but for those callers the feature is a complete, silent no-op with zero logged signal.

### TRAINING_COMPOSITE_CORE_A-2 — polars input silently flattened to an untyped/object ndarray in two gated estimators

Both `gated_outlier.py` (`GatedOutlierEstimator.fit`, line 129) and `gated_regression_mixture.py` (`fit`/`_predict_branch`, lines 153/167) subset rows via `X.loc[mask]`/`X.iloc[...]` when the attribute exists, else fall back to `np.asarray(X)[mask]`. Neither branch checks for polars (`hasattr(X, "get_column")`), even though `gated_regression_mixture.py`'s own `_concat_feature` helper explicitly imports and handles `polars.DataFrame` a few lines away — evidence the class is meant to accept polars input, making the row-subset gap an inconsistency within the same file rather than an intentional pandas-only restriction. Confirmed two ways: (1) fitting `GatedOutlierEstimator` on an all-numeric polars frame succeeds but leaves the inner `LinearRegression` fit WITHOUT feature names while `predict` is later called with a named polars frame, producing a real sklearn `UserWarning` ("X has feature names, but LinearRegression was fitted without feature names") — a live fit/predict-path inconsistency; (2) `np.asarray()` on a polars frame containing even one non-numeric (categorical/string) column produces an `object`-dtype ndarray mixing floats and Python strings, which breaks or silently mis-trains most sklearn/GBDT regressors that expect either a homogeneous numeric array or an explicitly-typed/named frame for categorical handling. Sibling modules in the same directory (`bagging.py`'s `_take_rows`/`_is_polars_df`, `classification.py`'s `_extract_margin_column`/`_drop_margin_column`, `glm.py`'s `_extract_mean_column`) all handle this correctly via the shared `is_polars_df`/`get_column` pattern, so the fix is to reuse that pattern rather than invent one. No test in `tests/training/composite/test_biz_val_gated_outlier.py` / `test_biz_val_gated_regression_mixture.py` exercises a polars `X`, matching the E3 finding's pattern of an untested input shape being exactly the one that's broken.

### TRAINING_COMPOSITE_CORE_A-3 — `factorize()`'s no-pandas fallback doesn't honor its own NaN-mapping contract

`_composite_report_shared.py`'s `factorize()` docstring states "NaN / null labels map to code -1 (excluded downstream)" and the pandas branch (`pd.factorize`) does exactly that, but the `np.unique(..., return_inverse=True)` fallback (used only when pandas is unavailable — labeled a "hard dep in practice" so low real-world exposure) gives NaN its own valid, non-`-1` group code instead. Any downstream consumer relying on the documented `-1`-excludes-NaN contract (all three sharing modules: `_value_report.py`, `_moe_gate.py`, `_regime_headroom.py`) would, in the fallback-only path, silently treat a NaN-labeled group as a genuine reportable group rather than excluding it. Low real-world likelihood (pandas absence is rare) but a genuine, silent, docstring-violating divergence between the two code paths of the SAME function — exactly the "coercion + silent behavior divergence" bug class the review brief calls out.

### TRAINING_COMPOSITE_CORE_A-4 — CV-fold-boundary leak of the imputation median in classification discovery

`classification_discovery.py`'s `_stage1_screen` (`col = _impute_column(values[:, j])`, line 222) and `_stage2_paired` (`col_full = _impute_column(_extract_named_column(X_screen, col_name))`, line 256) both impute non-finite candidate-column values with the median of the WHOLE screening split, computed once BEFORE the `StratifiedKFold` loop, then slice that already-imputed array by `[tr]`/`[va]` per fold. Because the median is a function of every row in the screening split (not just the fold's train rows), each fold's "train" imputation value has technically seen the fold's own held-out validation rows — a genuine, if narrow (single summary statistic, not a full row/label leak), train/validation boundary violation. This mildly and systematically overstates the honesty of the reported `margin_gain` (Stage 1) and `cv_gain` (Stage 2), both of which directly gate whether a candidate composite is proposed at all. The fix is a per-fold median computed from `col[tr]` only, applied to both halves of that fold.

### TRAINING_COMPOSITE_CORE_A-5 — `predict_cdf`'s dense 3-D broadcast is an unguarded memory-blowup risk

`distributional.py`'s `predict_cdf` computes `leq = qmat[:, :, None] <= t[None, None, :]`, an `(n_rows, K, len(y_grid))` boolean array, to derive the step-CDF at arbitrary query points. The module's own docstring stresses "No frame copy" and bounded `(n, K)` matrices elsewhere, but this specific method's memory footprint scales with the PRODUCT of `n_rows` and `len(y_grid)` (both caller-controlled and potentially large — `n_rows` up to the composite package's stated 100+GB-frame scale, `y_grid` an arbitrary-length caller-supplied query array), unlike every other reduction in this cluster which the audit found deliberately fused into O(n) or O(n·K) numba/bincount passes specifically to avoid such temporaries (see `_value_report.py`/`_regime_headroom.py`/`_winkler.py`'s documented "single fused pass instead of N full-array masked sweeps" pattern). At realistic large-n scale with even a moderately fine `y_grid` this can allocate tens of GB.

### TRAINING_COMPOSITE_CORE_A-6, -7, -8 — hygiene / duplication nits

- **-6**: `winkler_score_per_group` duplicates group-factorization logic that `_composite_report_shared.py` exists specifically to consolidate, and as a result independently reproduces the same NaN-mapping gap as -3 in its own `np.unique` fallback branch — a clean case for the "grep every instance, fix once" pattern.
- **-7**: `_composite_array_shared.py`'s `n_features()` mishandles a 1-D `X` (returns 0 instead of 1), a minor edge case unlikely to be hit given most composite estimators receive 2-D frames, but a real gap against the "single feature column passed as a bare 1-D array" input shape.
- **-8**: `sklearn_set_params` (used to bind `set_params` onto small helper classes like `_UnivariateColumnMargin`) is more permissive than sklearn's own contract, silently swallowing a typo'd kwarg instead of raising — low practical risk (helper classes have few params) but a real deviation from the sklearn API contract this codebase otherwise adheres to closely.
