## Narrative

### TRAINING_LOOSE_B-1 (P1) — silent fallback on njit multilabel-stratification failure

`_stratified_split_3way` (`_split_helpers.py`) tries a fast njit port of iterstrat's `IterativeStratification` (`_iterative_stratification_njit`, claimed 50.8x speedup) and, on **any** exception, falls back to the pure-Python `iterstrat.ml_stratifiers.IterativeStratification`. The `except Exception:` block at line 157 has no `logger.warning`/`logger.debug` call at all — every OTHER broad-except site examined in this cluster (dozens, e.g. `_model_factories.py`, `_predict_guards.py`, `_trainer_configure.py`) logs at least at `debug` level before swallowing. This one file is the outlier. This is exactly the bug class this codebase has already been bitten by twice (documented in CLAUDE.md: the `_select_mi_backend` transient-`ImportError`-vs-any-`Exception` bug, and the per-call numba/GPU MI dispatch silent fallback) — a broad except around a numba path silently downgrades performance (and, worse, could mask a genuine correctness bug in the njit kernel that only some inputs trigger) with zero operator-visible signal. Found by reading the fallback structure and comparing it against every sibling `except Exception` in the same cluster, all of which log.

### TRAINING_LOOSE_B-2 (P1) — cache keyed on ephemeral object `id()`

`_get_training_configs_cached` (`_trainer_configure.py`) memoizes `get_training_configs(**kwargs)` in a module-level `_GTC_CACHE` dict that lives for the process lifetime (spanning every target/model/pre_pipeline combination in a multi-target suite, and even across separate `train_mlframe_models_suite` calls in the same process). For the `subgroups` kwarg it deliberately keys on `id(indexed_subgroups)` rather than content, with the comment "stable enough for the 2-call CPU+GPU pair" — true only for the two calls made from a single `configure_training_params` invocation (which do share the same object). Across DIFFERENT targets, a fresh `indexed_subgroups` dict is built every call (line 381 `create_fairness_subgroups_indices(...)`); if the previous target's dict has already been garbage-collected by the time the next one is built — the common case for a short-lived local with no other references — CPython's small-object allocator can (and often does) hand back the same memory address, giving the new dict the SAME `id()` as the old one. If the OTHER memoized kwargs (`config_params`) are identical between targets — which the function's own comment says is the common case ("`config_params` is derived from `hyperparams_config.model_dump()` once and never changes between targets") — the cache returns a stale `deepcopy` of the PREVIOUS target's `get_training_configs` result, including `custom_ice_metric`/`custom_rice_metric` built from the wrong fairness-subgroup structure. This only manifests when `use_robust_eval_metric=True` and fairness subgroups are configured (the `indexed_subgroups is not None` gate), which narrows but does not eliminate the exposure in a fairness-aware multi-target suite. Found by tracing the cache-key construction end to end and cross-checking CPython's documented small-object reuse behavior.

### TRAINING_LOOSE_B-3 (P2) — unbounded `(n_test, n_cal)` allocation in `smearing_predict`

`smearing_predict` (`_regression_calibration.py`) computes `inverse_fn(p[:, None] + r[None, :])`, an `(n_test, n_cal)` dense array. `n_cal` (the calibration residual pool) is explicitly capped via `max_cal` (default 2000), but `n_test` (the prediction batch) is not bounded anywhere in the function. On a large predict batch this blows up memory quadratically-in-effect (e.g. n_test=2M rows x max_cal=2000 = 4e9 float64 elements = 32 GB) with no chunking or size gate — directly contrary to this repo's own documented "frames can be 100+ GB, never materialize a full frame when batching suffices" discipline. It is not currently called from the production suite path (only `PointRecalibrator` and `cv2_recalibration_gain` are wired into `_phase_finalize_calibration.py`), but it is public API, exported, and covered by `test_smearing_backtransform.py`, so a caller applying Duan smearing directly to a large test/predict batch would hit this. Found by reading the broadcast shape and checking call sites via grep (confirmed unbounded on the `n_test` axis, and confirmed no current caller bounds it either).

### TRAINING_LOOSE_B-4 (P2) — neural-component import failure not cached

`_get_neural_components` (`_model_factories.py`) lazily imports `MLPNeuronsByLayerArchitecture`/`PytorchLightningRegressor`/`PytorchLightningClassifier` from `mlframe.training.neural` and caches the result into module globals, using `MLPNeuronsByLayerArchitecture is None` as the "not yet loaded" sentinel. On `ImportError` it returns `(None, None, None)` WITHOUT setting any of the globals — so the sentinel stays `None` and the NEXT call retries the exact same import. The module's own comment states this import can take "30-180 s cold" on Windows when `mlframe.training.neural` is present (it eagerly imports `lightning` + `torchmetrics`). If the package is installed but broken partway through that chain (a plausible real-world state — mismatched `lightning`/`torch` versions, missing native extension), every MLP-model configuration call in a multi-target suite pays the full, failing import cost again, instead of failing fast after the first attempt. Found by reading the success/failure branches of the cache-populate `if` and noting the asymmetry.

### TRAINING_LOOSE_B-5 (P3) — hash-based pseudo-group collapse

`reconstruct_pseudo_group_ids`'s exact path (`_pseudo_group_reconstruction.py`) reduces a multi-column rounded key to one `pd.util.hash_pandas_object` 64-bit hash before grouping via `np.unique(..., return_inverse=True)`, explicitly for speed (1.74x measured) over `groupby(cols).ngroup()`. This is a real, if very low-probability, hash-collision surface: two rows with genuinely different rounded feature vectors could theoretically hash to the same 64-bit value and be merged into one pseudo-group. Because the function's whole purpose is feeding `GroupKFold` for leakage prevention, an accidental over-merge is safety-preserving (it can only make the split MORE conservative, never leak two truly-different entities' rows across folds) — so this is a documentation/robustness gap, not a leakage bug, hence P3 rather than higher.

### TRAINING_LOOSE_B-6 (P3) — profiling harness doesn't persist stats

`_profile_fs_suite_integration.py`'s `main()` runs the full-suite cProfile harness and prints top-30 cumulative / top-20 tottime frames to stdout, but never calls `pstats.Stats.dump_stats(...)`. This contradicts the project's own standing rule that cProfile runs must always save stats (not print-only), since a print-only run cannot be re-analyzed (e.g. `snakeviz`, diffing two runs) after the fact.

### TRAINING_LOOSE_B-7 (P3) — pervasive date/wave/iter markers in source comments

CLAUDE.md explicitly and repeatedly (marked CRITICAL) bans "process/audit metadata in code comments: no phase/wave markers, finding IDs, date stamps, fuzz-seed refs, refactor-history narration ... that belongs in git history / the PR description." This cluster is thoroughly permeated with exactly that pattern: literal dates (`2026-04-19`, `2026-05-13`, ...), `Wave N`, `iterNNN`, `Fix N`, audit-row references (`C10`, `FS-P1-1`) embedded directly in docstrings and inline comments across nearly every file (representative, non-exhaustive: `_model_factories.py` lines 26, 42, 78-83; `_predict_guards.py` lines 9-36; `_training_loop.py` lines 215-227, 849-851; `_trainer_train_and_evaluate.py` lines 363-367; `_ram_helpers.py` lines 46-50; `_reporting_configs.py` lines 38-41, 117-121, 128-144). Reported as ONE aggregate finding (not one per occurrence) since it is a single, repo-wide-scale hygiene issue best fixed as its own dedicated pass rather than enumerated per line.
