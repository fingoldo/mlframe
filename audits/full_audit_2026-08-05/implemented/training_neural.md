## Narrative

### TRAINING_NEURAL-1 (P0): `partial_fit` corrupts categorical-embedding codes across incremental calls

`_FitMixin._fit_common` (`base/_base_fit.py:93-99`) calls `self._encode_emb_text_fit(...)` and `self._factorize_cats_fit(...)` unconditionally at the very top of the method, on both `fit()` and `partial_fit()` calls alike — neither helper receives or checks `is_partial_fit`. `_FitPrepMixin._factorize_cats_fit` (`base/_base_fit_prep.py:44-111`) always resets `self._cat_code_maps_`/`self._cat_cardinalities_`/`self._cat_cols_` to fresh values derived from `pd.factorize(X[col], sort=False)` on *whatever batch of `X` this particular call received* — the code assigned to a given category value depends on that value's first-appearance order **within the current batch**, not a stable global order. Meanwhile, a few lines later in the same function (`base/_base_fit.py:370-372, 449-450`), the network is explicitly *not* rebuilt on `partial_fit` continuation (`if not is_partial_fit: self.network = None`), so the already-trained `CategoricalEmbedding` table from the first call is reused verbatim against the *newly recomputed* (and generally different) code mapping. Two consecutive `partial_fit` batches with even a slightly different category distribution will therefore feed the same embedding row index to two semantically different category values, silently corrupting the trained embedding associations with no error, no warning, and no test coverage (`tests/training/neural/test_estimators.py`'s `test_partial_fit`/`test_partial_fit_keeps_network` and `test_integration.py`'s `test_sequential_partial_fit` all use `cat_features`-free numeric data). Strong internal evidence that this is an oversight rather than a deliberate limitation: the *label*-encoder handling directly above (`base/_base_fit.py:204-217`) explicitly documents and implements exactly the reuse-across-`partial_fit`-calls contract this bug is missing ("so the index space stays stable across partial_fit calls" / "partial_fit continuation with encoder already built; reuse"), but the equivalent care was never extended to the categorical-embedding code maps living in the very next helper call.

### TRAINING_NEURAL-2 (P0): recurrent wrapper's cat-code replay crashes on `Categorical` dtype

`base/_base_fit_prep.py:129-134` (flat MLP `_apply_cat_codes`) carries an explicit, well-documented fix: cast to `object` *before* `.map(mapping)` because `Series.map` on a pandas `Categorical`-dtype column returns a `Categorical` result, and the subsequent `.fillna(card)` unknown-code fill then tries to add `card` as a brand-new category, raising `"Cannot setitem on a Categorical with a new category"`. The parallel implementation for the recurrent wrappers, `_RecurrentCatEmbeddingMixin._apply_cat_codes` (`_recurrent_cat_embeddings.py:77-95`), does `mapped = features[col].map(code_maps[col])` at line 91 with **no** `.astype(object)` cast — the exact same crash reproduces for any `RecurrentClassifierWrapper`/`RecurrentRegressorWrapper` fit with a `pandas.Categorical`-dtype `cat_features` column that has an unseen value in the validation `eval_set` at fit time, or in `X` at predict time. This is a straightforward regression/inconsistency: the fix landed in one sibling implementation of an identical code path but was never ported to the other, despite both files' docstrings describing themselves as mirroring each other's contract ("mirrors the flat-MLP `_FitMixin` cat-embedding contract").

### TRAINING_NEURAL-3 (P1): `MuonAdamWHybrid` silently ignores any attached LR scheduler

`MuonAdamWHybrid.__init__` (`_muon_optimizer.py:172-204`) calls `super().__init__([{"params": param_list}], defaults)`, which sets `self.param_groups` to a single placeholder group holding *every* parameter (both the 2D-Muon-routed and 1D-AdamW-routed ones) with `lr=lr` (the facade's own `lr` kwarg, default `1e-3`) — entirely disconnected from `self._muon.param_groups` (built with `muon_lr`) and `self._adamw.param_groups` (its own separate list). `MLPTorchModel.configure_optimizers` (`_flat_torch_module/__init__.py:487-519`) constructs `scheduler = self.lr_scheduler(optimizer, **kwargs)` directly against whatever `optimizer` object `self.optimizer(...)` produced; any stock `torch.optim.lr_scheduler.*` reads/writes `optimizer.param_groups[i]['lr']` — for `MuonAdamWHybrid` that mutates only the disconnected placeholder, never the real inner optimizers' learning rates. The net effect: pairing `optimizer=MuonAdamWHybrid` with any `lr_scheduler=` (e.g. `OneCycleLR`, which several other parts of this same codebase treat as the *recommended* short-fit scheduler) trains at a constant, un-annealed LR for the entire run with zero error, warning, or difference in Lightning's own scheduler-configured log lines. Sibling wrapper classes `SAM` and `Lookahead` (same file family, `_optimizer_wrapper_shared.py`) both correctly delegate `param_groups` via the shared `wrapper_param_groups` property; `MuonAdamWHybrid` is the one wrapper in this family that owns *two* inner optimizers and never got the equivalent treatment. Confirmed via `tests/training/neural/test_muon_optimizer.py`: no test anywhere combines `MuonAdamWHybrid` with an `lr_scheduler`.

### TRAINING_NEURAL-4 (P2): `FieldGroupedMLPRegressor` never validates its `field_groups` partition contract

The class docstring (`field_grouped_mlp.py:53-58`) states "Every column index must appear in exactly one field," but neither `_FieldGroupedMLPModule.__init__`/`forward` nor `FieldGroupedMLPRegressor.fit` enforces it. `forward` (`field_grouped_mlp.py:39-47`) only ever reads `x[:, idx]` for the indices actually present in `self.field_indices`; any raw feature column whose index the caller forgot to list in any group is simply never seen by the model (silently reduced capacity, no signal it happened), and any index listed in two groups is silently fed to two independent sub-encoders (inflating its effective weight in the merged representation). This is an easy misconfiguration to hit in practice (e.g. an off-by-one when hand-building `range()`-based index groups, exactly as the module's own `_benchmarks/bench_field_grouped_mlp.py` constructs them) and it fails silently rather than loudly.

### TRAINING_NEURAL-5 (P2): `build_keras_mlp`'s `num_layers` builds one extra hidden layer

`build_keras_mlp` (`keras_compat.py:24-89`) appends one `Dense(num_neurons, ...) + BatchNormalization() + Dropout(...)` block unconditionally (lines 51-62) *before* the `for _ in range(num_layers): ...` loop (lines 63-75) which appends `num_layers` more identical blocks. The resulting `Sequential` therefore has `num_layers + 1` hidden `Dense` layers, not `num_layers` as the parameter's name plainly promises. This is TF/Keras-optional legacy-compat code (gated behind `_HAS_TF`), so the blast radius is narrow, but it is a genuine off-by-one that silently over-builds every model constructed through this path (including via `KerasCompatibleMLP.fit`, which forwards `num_layers` straight through).

### TRAINING_NEURAL-6 (P2): recurrent wrapper's categorical auto-detection gap vs. its flat-MLP sibling

`base/_base_fit_prep.py:71-72` (flat MLP) unions the caller's explicit `cat_features` list with any *remaining* non-numeric column in `X` (`_auto`), so a forgotten/unlisted categorical column is still safely factorized rather than crashing `_validate_no_nan_inf`. `_RecurrentCatEmbeddingMixin._factorize_cats_fit` (`_recurrent_cat_embeddings.py:29-75`) has no equivalent union — it only factorizes columns present in the caller-supplied `cat_features` list (`present = [c for c in cat_features if c in features.columns]`, no auto fallback). A `RecurrentClassifierWrapper`/`RecurrentRegressorWrapper` fit in HYBRID/FEATURES_ONLY mode with an un-named string/object column therefore crashes downstream in `_ensure_numpy`/`StandardScaler.fit` (`ValueError: could not convert string to float`) instead of degrading gracefully the way the flat MLP does for the identical scenario — an API-consistency gap between two estimator families documented as mirroring one another's cat-embedding contract.

### TRAINING_NEURAL-7 (P3): `RecurrentDataModule` is exported public API with no production caller

`RecurrentDataModule` (`_recurrent_data.py:162-420`) is a full `LightningDataModule` implementation (train/val/test/predict dataloaders, its own stratified-sampler + `pin_memory`/`num_workers` logic) exported from `recurrent.py` and re-exported from the package `neural/__init__.py` (`__all__` at lines 34-37, 69, 123). Grepping the whole `src/` tree for `RecurrentDataModule(` shows it constructed only inside its own defining file; the actual production fit path (`RecurrentClassifierWrapper.fit`/`RecurrentRegressorWrapper.fit` in `_recurrent_wrappers.py`) builds its dataloaders directly via `_RecurrentWrapperBase._create_dataset`/`_create_dataloader` instead, which independently re-implements the same stratified-sampler logic. Only test files (`test_recurrent_workers_default.py`, `test_neural_high_severity_regressions.py`, `test_neural_core_polish.py`) ever instantiate `RecurrentDataModule`. This is dead/orphaned production surface: a public class with real behavior that no shipped code path exercises, and a second copy of logic that could silently drift from the copy that's actually load-bearing.

### TRAINING_NEURAL-8 (P3): stale cross-file docstring reference

`neural/__init__.py:57` and `:114` describe `FieldGroupedMLPRegressor` as carrying "its own module docstring['s] ... honest-negative note: the hypothesized generalization win did not reproduce." A full-file read of `field_grouped_mlp.py` (and a targeted grep for "honest-negative"/"did not reproduce"/"generalization win" across the whole cluster) turns up no such note anywhere in that file — the module docstring only describes the architecture, with no mention of any negative result. Either the note was removed from `field_grouped_mlp.py` in a later edit without updating the cross-reference in `__init__.py`, or it was never actually added; either way the comment currently misleads a reader into believing evidence exists that doesn't.
