## Narrative detail

**FE_TRANSFORMER_A-1 (P0).** `make_focal_objective` in `_focal_loss_shared.py` builds a LightGBM custom-objective closure for binary focal loss (Lin et al. 2017). I verified the returned gradient against both a central-difference numerical derivative and a `sympy` symbolic derivative of the exact loss function the code computes (`focal_term = (1-pt)**gamma`, `L = -focal_term * log(pt)`), using 20 random `(x, y)` pairs. The analytic gradient in the code diverges from the true gradient by up to 51.9 (vs. ~1e-5 for a correct implementation at this scale) and the Hessian by up to 0.30 — not a rounding-level discrepancy, a structurally wrong formula (the closed-form correct gradient, `y=1: gamma*p*(1-p)^gamma*log(p) - (1-p)^(gamma+1)`, does not match the code's chained expression at all). Both consumers (`focal_lgb.py`'s `compute_focal_lgb_features`, `multi_aux_ensemble.py`'s aux-LGB ensemble) train real LightGBM boosters against this wrong gradient every time `focal=True`, meaning the "focal-loss-emphasized rare-class predictions" these two shortlist mechanisms are built around are silently miscalibrated — the model still trains (gradient boosting is somewhat robust to imperfect gradients) but is not actually optimizing focal loss, undermining the entire stated rationale of both modules ("focal loss objective... produce predictions that capture rare-positive signal more sharply").

**FE_TRANSFORMER_A-2 (P1).** Comparing `bidir_residual_band.py`'s `_fit_baseline_predict` (explicitly inner-`KFold(3)`-OOF, with a 5-line docstring explaining why in-sample residuals "systematically understate the true baseline residual and distort which rows look easy/hard for band assignment") against `disagreement_band.py`'s `_fit_3baselines_in_sample` (named "in_sample" and genuinely in-sample: `preds[:, 0] = model.predict_proba(Xt)`, fit and predict on the identical rows), `class_balanced_hard_row.py`'s `_fit_baseline_predict` (also plain in-sample), and `fisher_weighted_residual.py`'s `_process` (fits then immediately predicts on `Xt_s`) shows the exact same understated-residual bias the sibling file already diagnosed and fixed was never propagated to these three. Since band membership (which rows count as "hardest"/"most disagreeing") directly determines which training rows become the anchors/centroids that the softmax-attention output is computed against, an in-sample-biased hardness ranking systematically mis-selects anchors — rows that appear "easy" in-sample (because the same-fit model has partially memorized them) are under-represented as anchors even when they'd be genuinely hard out-of-sample.

**FE_TRANSFORMER_A-3 (P1).** Grepped the full `[:, None, :] - ... [None, :, :]` broadcast pattern across the scoped directory: 4 occurrences fall within this cluster's scope (`band_conditional_anchor.py:140`, `bidir_residual_band.py:151`, `class_balanced_hard_row.py:162`, `disagreement_band.py:151`), all producing an `(n_query, n_anchors, d)` cube before reducing over the last axis. `_squared_dists_shared.py` — a file in the SAME directory — exists specifically to avoid this ("Avoids the (len(A), len(B), d) broadcast cube... only the (len(A), len(B)) result is allocated") and is already used by `anchor_attention.py` and `class_conditional_anchor.py`. `validate_numeric_input` in this same package enforces a hard cap of `d <= 32768`, and the module docstrings throughout this cluster explicitly discuss production data at N=10M+ rows, so `n_query` in the hundreds-of-thousands-to-millions range combined with `d` in the thousands is a realistic, reachable configuration where these 4 files would materialize a multi-GB-to-multi-hundred-GB temporary array per call, directly the kind of pattern CLAUDE.md's memory-discipline rule calls out.

**FE_TRANSFORMER_A-4 (P2).** `_adasyn_synthesize`'s first kNN call, `NearestNeighbors(n_neighbors=k_global + 1).fit(X_full)` where `X_full` is the full (positive+negative) standardized fold, has no cap against `X_full.shape[0]`. Every other kNN construction in this package caps `k` (e.g. `_utils.kth_nearest_dists`: `k_request = min(k_max, n_sub)`; `borderline_smote._find_borderline_positives`: `k_used = min(k + 1, X_full.shape[0])`). With the default `k_global=10`, any fold where the combined pos+neg row count is `<= 10` (a realistic small-fold or tiny-dataset scenario, especially inside inner cross-validation on rare-class data where this whole family of mechanisms is explicitly designed to operate) raises an uncaught `ValueError` from sklearn instead of the graceful degrade every sibling function performs.

**FE_TRANSFORMER_A-5 (P2).** `conformal_locally_adaptive.py`'s `_make_df` hardcodes `f"{column_prefix}_width_a01"` and `f"{column_prefix}_width_a02"` as literal strings, while `_process` derives `widths_q[:, i]` from `enumerate(alphas)` where `alphas` is a caller-configurable parameter (`alphas=(0.1, 0.2)` default). I traced the full call path: nothing in the function validates `len(alphas) == 2`, so `alphas=(0.05,)` would `IndexError` inside `_make_df` (`feats[:, 1]` out of bounds relative to the emitted 5-column block whose 2nd slot never got written meaningfully), and `alphas=(0.1, 0.5)` would silently produce a column literally named `_width_a02` holding the alpha=0.5 result — a column-name lie that would corrupt any downstream analysis keying off the name (e.g. "what's the 20%-alpha interval width" reading the 50%-alpha value). Contrast with `distributional_moments.py` in the same directory, which explicitly guards this exact class of bug (`if len(quantiles) != 7: raise ValueError(...)`) with a comment calling out precisely this failure mode.

**FE_TRANSFORMER_A-6 (P2).** `cross_feature_reconstruction.py`'s module docstring literally says "fit **OOF** LGB predicting x_j from `{x_k : k≠j}`", but `_process`'s loop does `m.fit(Xt_j_in, Xt_s[:, j])` immediately followed by `x_hat_train = m.predict(Xt_j_in)` — the identical rows used for both fit and score, i.e. genuinely in-sample, not OOF. This matters because `mad_j` (the per-feature MAD scale used to standardize the query-row residual into `z_residuals_q`) is derived from `r_train = Xt_s[:, j] - x_hat_train`, and an in-sample reconstruction residual is understated relative to a genuinely held-out one (the model has partially memorized the rows it's scoring). A smaller `mad_j` inflates every subsequent `z_residuals_q[:, j] = r_q / mad_j` for genuinely out-of-sample query rows, systematically pushing the "outlierness" aggregate features (`sum_sq_z`, `max_z`, `n_extreme`) upward. I found the exact same failure mode explicitly diagnosed and fixed via inner-`KFold(3)` OOF in three sibling files in this same directory (`baseline_surprise.py:_fit_baseline_predict`, `bidir_residual_band.py:_fit_baseline_predict`, `decision_region_depth.py`'s `oof_resid` block) — this file is the one place in the cluster where the documented intent ("OOF") and the actual implementation diverge.

**FE_TRANSFORMER_A-7 / -8 (P3).** Two independent instances of the same docstring-arithmetic-error pattern: `baseline_disagreement_v2.py` claims 12 output features where the itemized breakdown and the code both agree on 11; `class_balanced_hard_row.py` claims `+8` scalar features where the itemized breakdown and the code both agree on `+9`. Both are pure documentation bugs (the actual `n_features`/column-count logic is internally self-consistent and correct in both files) but both would mislead anyone reading the docstring to predict the output shape without running the code.

**FE_TRANSFORMER_A-9 (P3).** `bgmm_quantile_bands.py`'s module docstring (lines 8-9) promises 12 additional "pairwise cross-band log-ratio" columns beyond the per-band k-NN distances; neither `_process` nor `_make_df` compute or emit them, and the function-level docstring (lines 103-106) correctly describes only the per-band distance columns that are actually produced. This reads as a stale module docstring left over from before a feature was descoped/refactored out, not a live bug (the function's own contract is internally consistent), but is exactly the kind of misleading module-level claim the P3 hygiene tier is meant to catch.

**FE_TRANSFORMER_A-10 (P3).** `fca_closed_concepts.py` accepts `standardize: bool = True` in its public signature (matching the contract of every other `compute_*_features` function in this package) but `_process` never references it — the FCA boolean context is always built from `Xt > median(Xt)` on the raw, unscaled array. Functionally this happens to be harmless (median-threshold binarization is invariant to any monotonic per-column rescaling, including `RobustScaler`), but the parameter silently doing nothing is a real API-consistency trap: a caller toggling `standardize=False` expecting a behavior change (as it would for every sibling function) gets none, with no warning.

**FE_TRANSFORMER_A-11 (P3).** Repo-wide grep for `smote_synthesize_rowloop` and `smote_synthesize_vectorized` (the plain, non-"minority" names) found matches only inside `_smote_kernels_shared.py` itself, four `_benchmarks/bench_*_synthesize_vectorized.py` files, and three `test_*_synthesize_vectorized_identity.py` files — and inspecting those benchmark/test files directly showed the matches are all comment/docstring prose referencing the sibling mechanism, not actual calls to these two functions. `active_virtual.py`, `borderline_smote.py`, `multiscale_smote.py`, and `pseudo_smote.py` all import the "minority"-suffixed twins instead.
