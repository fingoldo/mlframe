## Narrative

### TRAINING_CORE_A-1 (P1) — near-duplicate auto-drop can drop an entire correlated cluster

`_maybe_auto_drop_after_feature_analyzer` (`_main_train_suite_target_distribution.py`) is the opt-in auto-drop step for `behavior_config.auto_drop_near_duplicate_threshold <= 1.0` (default `2.0`, i.e. off unless the caller explicitly configures a real correlation threshold such as `0.98`). It walks `fd_report.diagnostics["redundant_feature_pairs"]` — a list of `(a, b, |corr|)` triples built by `_pairwise_redundant_features` in `_target_distribution_analyzer_features.py` via a plain `for i in range(len(cols)): for j in range(i+1, len(cols))` scan (`a`/`b` are the columns in **positional**, not alphabetical, order despite the comment's claim) — and is supposed to keep exactly one survivor per group of near-duplicates while dropping the rest, via:

```python
drop_set.add(_b if _a not in drop_set and _b not in drop_set else (_a if _b in drop_set else _b))
```

I traced this by hand for a 3-clique of mutually correlated columns A/B/C processed in pair order `(A,B), (B,C), (A,C)` (a realistic case for e.g. three exact-duplicate or unit-converted copies of the same feature, which `_pairwise_redundant_features` will indeed emit as three pairwise-redundant edges since it computes every `i<j` pair independently, not just adjacent chains):

1. `(A,B)`: neither in `drop_set` → adds `B`. `drop_set={B}`.
2. `(B,C)`: `B` already dropped (so the `and`-guard is false) → falls into the `else` branch, which (since `C` is not yet in `drop_set`) evaluates to `_b` → adds `C`. `drop_set={B,C}`.
3. `(A,C)`: `A` not dropped but `C` is → the `else` branch now sees `_b (C) in drop_set` → evaluates to `_a` → adds `A`. `drop_set={A,B,C}`.

All three columns end up dropped — the entire feature is silently removed from `train_df`/`val_df`/`test_df` with **zero survivors**, contradicting the function's own docstring ("drop the alphabetically-larger… so a correlated chain… collapses to a single survivor") and the general intent of near-duplicate collapsing (keep one copy). This is reachable any time three or more columns are simultaneously pairwise-correlated above the configured threshold — not a contrived edge case, since duplicate/near-duplicate columns very often come in groups of 3+ (e.g. a raw column plus two unit-scaled derivatives, or copy-pasted feature-engineering output). The bug is silent: no warning fires when a whole cluster is emptied, and the caller only logs the final `drop_list`, which looks like an ordinary drop.

### TRAINING_CORE_A-2 (P3) — stale docstring on `MTRPerColumnEqualMeanEnsemble.fit()`

Found while reviewing the honest-OOF MTR cross-target ensembling path (`_phase_composite_post_xt_ensemble/_post_xt_ensemble_mtr.py`), which is otherwise carefully written and leakage-free (`compute_mtr_oof_nnls_weights` in the sibling `_phase_composite_post_xt_mtr_oof.py` does genuine train-K-fold OOF refits, threads `sample_weight`, and gracefully degrades per-component rather than all-or-nothing). The class docstring (lines 30-33) and the `weights` property docstring (lines 111-114) both correctly state that NNLS weights are kept **raw** and deliberately **not** normalised to sum to 1 (with a sound rationale: normalising can push an optimal-but-unbounded solution off-optimum). But `fit()`'s own docstring (lines 121-126) still says "Then normalises w_k to sum to 1 (so the prediction is a convex combination)" — the opposite of what the code three lines above (`weights[:, k] = w_k  # Keep RAW NNLS weights (not normalised...)`) actually does. A maintainer skimming only `fit()`'s docstring (the most likely place to look when debugging a weight-sum-related issue) would draw the wrong conclusion about the shipped behaviour.

### TRAINING_CORE_A-3 (P2) — per-target Pool/Dataset/DMatrix rebuild instead of per-feature-set reuse

`_main_train_suite.py:722` carries an explicit, unresolved `!TODO!` immediately before the per-target-type/per-target loop: "optimize for creation of inner feature matrices of cb,lgb,xgb here. They should be created once per featureset, not once per target." I confirmed this is still live: the loop body (`pr._train_one_target`) re-enters the normal fit path for every `cur_target_name`, and the suite already invests in `_detect_dataset_reuse_capabilities` (`_misc_helpers.py`) plus a CB `Pool.set_label`/`set_weight` label-swap fast path specifically to avoid rebuilding the same binned/encoded dataset when only the label changes — but that reuse machinery is not wired into this loop for the common "same feature columns, several target columns" multi-target case (composite-target discovery in particular can add several additional regression targets per original target, multiplying the effect). This is a real, developer-flagged, still-open computational-efficiency gap in the target loop that owns most of the suite's model-fitting wall time on multi-target runs.
