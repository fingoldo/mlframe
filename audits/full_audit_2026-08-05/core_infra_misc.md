## Narrative detail

**CORE_INFRA_MISC-1 (hull_moving_average window=0/negative crash).** `hull_moving_average(values, window)` computes `half_window = max(1, window // 2)` and `sqrt_window = max(1, round(sqrt(window)))` — both defensively clamped to `>= 1` — but the *middle* SMA call, `_sma(x, window)`, passes the raw, unclamped `window` straight through. Inside `_sma_from_cumsum`, the windowed-mean reduction is `cumsum[window:] - cumsum[:-window]`. For `window == 0`, Python's slicing evaluates `cumsum[:-0]` as `cumsum[:0]` (an **empty** array, since `-0 == 0`), not the full array a reader would expect from "everything except the last 0 elements". This mismatches `cumsum[0:]` (full length) against `cumsum[:0]` (empty) and numpy raises a `ValueError` on the subtraction — a confusing crash bug rather than a clear "window must be positive" message. I found this by tracing every array-shape assumption in the file and noticing the two `max(1, ...)` guards conspicuously do NOT cover the third, unguarded call. This is a real, general bug class (Python's `x[:-0]` trap) — I grepped the whole `core_infra_misc` scope for the `[:-<name>]` slice pattern and this is the only occurrence in-scope, but the pattern recurs 87x repo-wide (mostly in the out-of-scope `feature_selection/filters` tree), so the proposed scanner has broad value beyond this one file.

**CORE_INFRA_MISC-2 (native_gpu_shap_available exception-type mismatch).** `native_gpu_shap_available(model_stub)` is documented and used as a boolean probe ("Whether `model_stub` is an XGBoost model fit with a CUDA-capable device") that callers are meant to branch on before falling back to `shap.Explainer`. It calls `model_stub.get_booster()` inside a `try/except AttributeError`. I verified directly against the installed xgboost's source (`inspect.getsource(xgboost.XGBModel.get_booster)`) that this method raises `sklearn.exceptions.NotFittedError` — not `AttributeError` — when the model has not been fit. Any caller that probes an as-yet-unfitted XGB estimator (a realistic path in code that checks capability before deciding whether to fit at all, or in a defensive capability-discovery loop) gets an uncaught `NotFittedError` instead of the documented `False`.

**CORE_INFRA_MISC-3 (knn_shapley unvalidated k).** `_knn_shapley_recursion` (the `@njit(fastmath=True)` core) divides by `k` in `value[p] = value[p+1] + (match[p] - match[p+1]) / k * min(k, i) / i`. The public `knn_shapley(..., k=5, ...)` never checks `k >= 1`. Under `fastmath=True`, a `k=0` division does not raise (it produces `inf`/`-inf`/`nan` per IEEE-754 float semantics, and fastmath additionally permits reordering that can turn genuine NaN propagation into silently "reasonable-looking" numbers in edge cases) — so a caller who passes `k=0` (e.g. from a misconfigured hyperparameter sweep) gets silently corrupted Shapley values with no exception and no warning, rather than a clear `ValueError`. This is exactly the kind of "coercion + error swallowing" correctness bug class called out as high-priority in review conventions.

**CORE_INFRA_MISC-4 (visualize_prediction_vs_truth single-sample crash).** `fig, axs = plt.subplots(1, len(samples), sharey=False, figsize=(20, 5))` uses matplotlib's default `squeeze=True` behaviour: when both `nrows` and `ncols` collapse to 1 (here `nrows=1, ncols=len(samples)==1`), `plt.subplots` returns a bare `Axes` object instead of an array, and the function's own loop body `axs[i].plot(...)` then raises `TypeError: 'AxesSubplot' object is not subscriptable`. The function's default argument (`samples=(1, 50, 75)`, 3 elements) never exercises this path, so the bug is latent until a caller passes a single-element `samples` tuple/list — a legitimate, easily-imagined call (e.g. debugging one specific row). Confirmed by matplotlib's own documented `squeeze` semantics; no live execution was needed since the code path is unconditional on `len(samples)==1`.

**CORE_INFRA_MISC-5 (duplicate gpu_disable_errors append).** The `gpu_disable_errors: list = []` module global carries an explicit docstring contract: `"0 or 1 entries -- the guard runs once per process"`. Reading `_disable_broken_cupy`'s NVRTC-probe-failure branch line-by-line, I found two back-to-back `.append(...)` calls with near-identical text (`"cupy NVRTC probe failed: ..."` vs `"cupy NVRTC probe raised: ..."`) — clearly a copy-paste leftover from an edit that intended to replace, not add to, the message. I grepped every reference to `gpu_disable_errors` repo-wide and found no consumer that currently assumes exactly one entry, so this is a documentation/hygiene violation today rather than an active crash — but it directly contradicts the code's own stated invariant and would silently break any future consumer written against that docstring (e.g. `gpu_disable_errors[0]` or a `len() <= 1` assertion).

**CORE_INFRA_MISC-6 (mlflow.py dead code).** `get_or_create_mlflow_run`'s run-lookup block reads `if runs: for run in runs: return run, True` immediately followed by `return None, False`. Since the `for` loop's body unconditionally `return`s on its very first iteration, the loop can never complete normally, and the trailing `return None, False` is unreachable — dead code that misleads a reader into thinking there is a "runs list was non-empty but somehow yielded no run" case being handled, when in fact the code is exactly equivalent to `if runs: return runs[0], True`. Found via straightforward control-flow tracing, no execution needed.

**CORE_INFRA_MISC-7 (MyDecorrelator stale TODO docstring).** `class MyDecorrelator(BaseEstimator, TransformerMixin): """TODO: TEST PROPERLY"""` is the entire class docstring. A grep for `MyDecorrelator` across `tests/` turned up 5 distinct test files exercising it (`test_cpx39_decorrelator_identity.py`'s bit-identity vs. the pre-vectorization double-loop, `test_custom_api_consistency.py`'s API30 type-preservation contract, `test_custom_estimators.py`'s attribute-name regression test, `test_serialization_memory_bugfixes.py`, and `test_core_infra_a_fixes.py`'s F6 fit/transform type-mismatch fix) — so the class is, in fact, thoroughly tested; the docstring simply was never updated after that work landed. This is a pure hygiene/documentation-quality issue (the class's actual `fit`/`transform` bodies were separately reviewed and found correct, with a well-reasoned inline comment about the integer-position canonicalization fix already in place).

**CORE_INFRA_MISC-8 (_resolve_stratify test_size=None overestimate).** `EstimatorWithEarlyStopping._resolve_stratify` computes the val-fold size it will use for its "is it safe to stratify" check as: `n_val = max(1, round(test_size * n))` if `test_size` is a float, `int(test_size)` if it's some other non-`None` value, else (when `test_size is None`) `n_val = n`. That last branch treats "no `test_size` given" as "the entire dataset becomes the validation fold" — but `train_test_split`'s actual behaviour when both `test_size` and `train_size` are `None` is to default `test_size` to `0.25`. Because `n_val = n` is a gross *overestimate* of the real validation-fold size, the subsequent gate `if n_val < classes.size: return None` is far more permissive than it should be, and stratification can be attempted on a real val fold too small to hold one member of every class, only to fail later inside `train_test_split`'s own `StratifiedShuffleSplit`. This is a narrow edge case (`EstimatorWithEarlyStopping`'s own `__init__` defaults `test_size=0.05`, so a caller must explicitly override to `None` to hit it), which is why it's rated P3 rather than P2.

**CORE_INFRA_MISC-9 (frame_compat.py debug-only silent fallback).** The module's own docstring explains its origin: a prior duck-typing bug in a different module ("the mini-HPT analyzer treated 25 Float32 polars columns as `high_cardinality_categorical`") because a naive `isinstance` check missed polars and `np.asarray(X)` silently produced an object-dtype array. `to_pandas_or_array` was built specifically to close that hole — yet its own polars-conversion branches wrap `to_pandas()` in `try/except Exception` and, on failure, do exactly the same silent `np.asarray(X)` fallback the module exists to prevent, logging only at `DEBUG` (invisible in production logs). This doesn't reproduce the ORIGINAL bug (the type dispatch itself is now correct), but it reintroduces the same *failure mode* — a caller silently getting an object-dtype array instead of a proper DataFrame — whenever the underlying `.to_pandas()` call itself fails for any reason (e.g. an exotic polars dtype not yet supported by the polars→pandas bridge).

**CORE_INFRA_MISC-10 (pelt_l2 min_segment_length=0 unvalidated).** `detect_regime_changepoints(y, min_segment_length=10, ...)` only special-cases `n < 2 * min_segment_length` (returning a trivial single-regime result); it never checks `min_segment_length >= 1`. With `min_segment_length=0`, the early-return guard `n < 2*0` is always false, so the function proceeds to call `pelt_l2(y, 0, penalty)`. Inside `_pelt_l2_kernel`'s `@njit(fastmath=True)` loop, the very first PELT step considers a candidate segment `s=0, t=min_size=0`, whose `length = t - s = 0`; the cost formula `seg_ss - seg_sum*seg_sum/length` divides by that zero length. Under `fastmath=True` this does not raise a Python exception — it silently produces `inf`/`nan`, which then propagates through `F[t]`/`cp[t]` and corrupts every subsequent breakpoint decision. This mirrors the exact same "unvalidated size-like parameter -> silent NaN in an njit kernel" bug class as CORE_INFRA_MISC-1 and CORE_INFRA_MISC-3, which is why I grouped them under the same meta-test idea.

**CORE_INFRA_MISC-11 (redundant double-sort in _knn_recommend).** `scored.sort(key=lambda t: t[0])` sorts the full candidate list by distance; `nearest = scored[:k]` takes a prefix of that already-sorted list (which is therefore itself already sorted); `nearest.sort(key=lambda t: t[0])` then re-sorts that already-sorted prefix — a guaranteed no-op given Python's `list.sort` is stable and the input is already in the target order. This costs essentially nothing in practice (`k=3` by default) so it is rated P3/pure cleanup rather than a real performance finding, but it is dead work worth removing during the fix wave.
