## Narrative

**X_SECURITY_ROBUSTNESS-1 (P0, secret leak via `str()`/format).** `EmbeddingProvider` (`training/feature_handling/providers.py`) builds an elaborate secret-scrubbing system for exactly the threat class it names in its own comments: "debugger / traceback / sentry doesn't leak them." It overrides `__repr__` to call `_scrub_dict(self.params)` before formatting. Pydantic v2's `BaseModel`, however, defines `__str__` independently of `__repr__` (verified: `BaseModel.__str__` calls its own `__repr_str__`, not the subclass's overridden `__repr__`). I reproduced this live: constructing `EmbeddingProvider(kind="openai", ..., params={"api_key": "env:TEST_OPENAI_KEY", ...}).resolve_secrets()` (the exact intended real-world pattern from the class's own docstring example) and calling `str(r)`, `f"{r}"`, and `"%s" % (r,)` all printed the literal API-key value `sk-ABCDEF-super-secret-value-12345`, while `repr(r)` correctly printed `***`. The project's own test suite (`tests/training/test_embedding_provider.py`) only asserts on `repr(p)` (`test_repr_masks_api_key`, `test_repr_masks_various_secret_keywords`) — there is no test on `str()`/format, which is exactly why this slipped through. Any future `logger.info("loaded provider %s", provider)` (a very natural Python idiom, and NOT the `%r`-style the codebase's other credential scrubber uses) or an uncaught-exception traceback embedding a resolved provider would leak the credential to logs.  <!-- pragma: allowlist secret -->

**X_SECURITY_ROBUSTNESS-2 (P0, fail-open `joblib.load`).** `estimators/pipelines.py::replay_cv_results` is the one `joblib.load` call site in the codebase whose path-containment check is conditional (`if trusted_root is not None: ...`) rather than mandatory. Every sibling site takes the opposite, fail-closed stance by design: `training/_data_helpers.py._validate_trusted_path` raises `ValueError("trusted_root is required...")` when `trusted_root is None`, with a docstring explicitly stating "the default posture refuses silently loading untrusted pickles"; `training/core/_misc_helpers.py._validate_trusted_path` does the same; `inference/predict.py::read_trained_models` defaults `trusted_root` to `inference_folder` specifically "so a malicious featureset... cannot escape and make read_trained_models joblib.load an arbitrary pickle" (its own comment). `replay_cv_results` was evidently not brought in line with this convention when it was established elsewhere. I confirmed neither the sole production reference nor the sole test (`tests/core/test_core_infra_a_fixes.py::test_f4_gridsearch_dump_round_trips_through_replay`) passes `trusted_root`, so the containment check never runs in the code as actually exercised today — the sha256 sidecar is the only remaining gate, and the function's own comment on the line right above the `joblib.load` call concedes that gate is integrity-only, not authenticity.

**X_SECURITY_ROBUSTNESS-3 (P2, duplicated security-critical logic).** The `abspath`+`os.path.commonpath` containment check appears near-verbatim in four files (`estimators/pipelines.py`, `inference/predict.py`, `training/_data_helpers.py`, `training/core/_misc_helpers.py`), each independently re-implemented rather than sharing one helper — found via `grep -n "os.path.commonpath(\[abs_root"` across the scope. The project already has precedent for centralizing exactly this class of security helper (`mlframe.utils.safe_pickle` explicitly re-exports pyutilz's sha256-sidecar logic "so any project depending on pyutilz gets the same verified-load primitive instead of re-implementing it"); the path-containment check never got the same treatment. This is the direct root cause that let X_SECURITY_ROBUSTNESS-2 happen — a shared helper with a single fail-closed default would have made the `pipelines.py` gap impossible without an explicit, visible opt-out.

**X_SECURITY_ROBUSTNESS-4 (P2, partial exception-credential-scrub).** `integrations/mlflow.py` built `_strip_userinfo`/`_USERINFO_RE` specifically to keep tracking-server `scheme://user:password@` credentials out of logs when `mlflow.start_run` raises (its own docstring: "so tracking-server credentials embedded in a raised exception don't leak into log files"). Reading the retry loop in `get_or_create_mlflow_run` (lines 131-153), the scrub is applied only to the string passed to `log_throttle` at line 150; the subsequent bare `raise` on line 151 re-raises the original `e` object unchanged, whose `.args`/`str()` still contain the raw credential. The mitigation is therefore incomplete — it protects this one log call but not the exception that continues to propagate, where a different logger, a Sentry SDK, or an outer `except Exception as e: logger.error(str(e))` would undo the scrub entirely.

**X_SECURITY_ROBUSTNESS-5 (P2, empty/all-NaN column crash).** `preprocessing/unseen_category_imputer.py::fit` computes `reliable = counts[counts >= self.min_count]`, falls back to `reliable = counts` when `reliable` is empty, then unconditionally does `self.mode_[col] = reliable.index[0]`. When the column being fit has zero non-null values (`pandas.Series.value_counts()` excludes `NaN` by default), both `counts` and `reliable` are empty and `reliable.index[0]` raises `IndexError: index 0 is out of bounds for axis 0 with size 0`. I reproduced this live against the installed package for both a zero-row DataFrame and, more realistically for production data, a column of all-`None` values — the latter is a case any upstream filtering step or a sparse/rarely-populated categorical column can produce. The crash message names neither the offending column nor the actual problem, making it hard to diagnose from a stack trace alone.

**X_SECURITY_ROBUSTNESS-6 / X_SECURITY_ROBUSTNESS-7 (P3, defense-in-depth gaps in not-yet-abused paths).** `LocalDiskBackend` is a deliberately "dumb primitive" per its own docstring, with the actual sanitization contractually owed by its caller — confirmed via grep that no current production code instantiates it, so there is no live path-traversal today, but the class will become the shared local/S3/GCS/Ray backend abstraction per its module docstring, and a defensive check costs nothing now versus finding this again after it is wired up. `embed_website_to_mlflow`'s `fname` argument has the identical unaddressed-in-the-docstring gap as its sibling `url` argument, which the docstring DOES call out.

**X_SECURITY_ROBUSTNESS-8 (P3, hygiene).** Pure duplication, no functional impact — noted per this audit's instruction to capture every real P3.

## Dimensions checked with zero findings

- **`eval`/`exec` of untrusted input**: zero instances — the two `df.eval(...)` calls in scope (`data/datasets.py`) use fixed, hardcoded formula strings, not user/config-supplied expressions; the module-level `__import__(...)` calls found are all either hardcoded sklearn/lightgbm/logging module names or (`calibration/post.py::_try_import_class`) called only with a fixed tuple of first-party/known-library `(module_path, class_name)` pairs, never user input.
- **`yaml.load` without `SafeLoader`**: zero instances of `yaml.load`/`yaml.safe_load` at all in scope.
- **`os.system` / `subprocess` with unsanitized input**: zero instances in production code; every `subprocess` call in scope lives in `_benchmarks/` dev-only scripts, uses fixed list-form args (no `shell=True`), and is already bandit-annotated (`# nosec B404/B603/B607`) with an accurate justification.
- **Hardcoded secrets/credentials**: zero matches for AWS-key/`sk-`/GitHub-token/PEM-private-key patterns, and zero literal credential values anywhere in scope; the one secrets-adjacent subsystem found (`training/feature_handling/providers.py`) is a deliberate env-var-indirection + scrubbing design (see X_SECURITY_ROBUSTNESS-1 for its one real gap).
- **Mutable default arguments**: zero instances of `def f(x=[]...)` / `def f(x={}...)` anywhere in scope (verified via a small AST-adjacent regex scan of every function signature in the tree, not just a literal grep).
- **Bare `except:`**: zero instances anywhere in scope. `except Exception:` (broad but typed) instances all carry a `logger.warning`/`logger.debug`/`log_throttle` call in the handler body in every sample inspected — consistent with this codebase's documented prior exception-swallowing audit passes (see `CLAUDE.md`'s 2026-08-02 bug-fix entries on exactly this class).
- **Unsafe pickle/joblib deserialization (the general case)**: the codebase's `_SafeUnpickler`/`_SafeJoblibUnpickler` allowlist/denylist system (`training/io.py`) is thorough and specifically anticipates the classic gadgets (`eval`/`exec`/`__import__`/`os`/`subprocess`/`__globals__`/`__subclasses__`/etc.), with restricted `getattr`/`setattr` reconstructors; no gap found in that machinery itself beyond the two call-site issues above (X_SECURITY_ROBUSTNESS-2, -3).
