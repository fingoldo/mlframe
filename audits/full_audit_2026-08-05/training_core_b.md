## Narrative

### TRAINING_CORE_B-1 (P1) — model schema record silently skipped on the identity-equivalent-pre_pipeline dedup shortcut

`_phase_train_one_target_body.py`'s innermost loop (`for weight_name, weight_values in ...`) calls `process_model(...)`, runs `_run_per_model_post_train_tail(...)`, and *then* checks whether the just-fitted `pre_pipeline` is `_mlframe_identity_equivalent` (i.e. it kept every input column, so it is redundant with the `ordinary` branch already present in the suite). When that check fires — which happens on `_model_idx_in_run == 1`, i.e. for *every* weight schema of the very first model trained under this pre_pipeline — the code sets `_break_model_loop = True` and `break`s out of the weight loop immediately, *skipping* the three statements that normally follow a successful iteration: `_forward_dataset_reuse_cache(...)`, `_build_and_record_model_schema(...)`, and `pipeline_cache.set(...)` (verified by reading the code in order at `_phase_train_one_target_body.py:764-866`). `_build_and_record_model_schema` is the sole writer of `metadata["model_schemas"][model_file_name]` (confirmed in `_phase_train_one_target_schema.py:153-246`), and that record is the only thing `_misc_helpers.py`'s per-model input-schema diff (`_misc_helpers.py:383-439`, explicitly labelled "HARD-FAIL on changes that silently corrupt predictions") checks against at serving time — the diff loop (`for model_file_name, rec in model_schemas.items()`) simply has nothing to iterate for a model with no recorded schema, so schema-drift protection (removed cat/text/embedding columns, role changes, dtype-family changes) is silently disabled for exactly the model that triggered this shortcut. I found this by tracing the control flow of the break statement against the three follow-on calls, then confirming `model_schemas`'s only consumer via grep across `src/`. There is no existing test covering this path with model-schema assertions (`tests/training/pipeline/test_dedup_identity_pre_pipelines.py` exercises the dedup itself but never asserts on `metadata["model_schemas"]`), so this is also a test-coverage gap. Secondary consequence (perf, not correctness): `pipeline_cache.set(...)` also never fires for this `cache_key`, so it stays a permanent MISS for the remainder of the per-target sweep.

### TRAINING_CORE_B-2 (P0) — disk-loaded predict path is missing three predict-time correctness guards its in-memory sibling has, most severely CTE-RAW-X

`mlframe.training.core.predict` exposes two functionally-equivalent public entry points: `predict_from_models` (in-memory `models` dict) and `predict_mlframe_models_suite` (loads a saved bundle from disk). Both are meant to replay the exact same per-model transform chain. `predict_from_models` (`_predict_main_from_models.py`) does this via the shared `_apply_pre_pipeline_with_passthrough` helper (`_predict_pre_pipeline.py:347-532`), which carries an explicit, well-documented "CTE-RAW-X" fix: `CompositeTargetEstimator.predict(X)` (confirmed in `src/mlframe/training/composite/estimator/_estimator.py`) re-extracts its `base_column` directly from whatever `X` it is given and applies an inverse transform whose `alpha`/`beta` were fit against the *raw* base-column scale; feeding it the post-main-pipeline (scaled/encoded) frame degenerates the inverse to `y_hat ~ t_hat` (predictions stay in residual/T-scale). `_predict_main_from_models.py:508-509` explicitly special-cases this: `_primary_for_model = df_pre_pipeline if isinstance(model, _CTE_cls) else input_for_model`. I grepped `_predict_main_suite.py` for `df_pre_pipeline` and `CompositeTargetEstimator` and got zero matches — the disk-loading path never even tracks a `df_pre_pipeline` snapshot, let alone routes CTE models to it; it calls `_predict_with_fallback(model, input_for_model, ...)` uniformly for every model (`_predict_main_suite.py:392,435`). Since `CompositeTargetEstimator` is a first-class, actively-used training feature (composite/residual targets), and `predict_mlframe_models_suite` is a heavily-used, documented public API (7 test files call it directly), any composite-target suite persisted to disk and served via this entry point will silently return wrong-scale predictions with no error raised — the textbook "silently corrupt a trained model's predictions" P0 class. I additionally confirmed no existing test exercises this combination: `tests/training/composite/test_composite_integration.py` only *mentions* `predict_mlframe_models_suite` in a comment describing a test-helper's mirrored guard, but never actually calls it. Two related, lower-but-still-real gaps compound the same root cause (the suite path's simplified inline `pre_pipeline.transform` handling at `_predict_main_suite.py:353-384` vs. the shared helper): on a transform failure it always warns-and-continues with the *untransformed* frame regardless of whether the pipeline was a value-altering step (the shared helper explicitly re-raises/drops the model in that case, `_predict_pre_pipeline.py:474-502`, specifically to avoid "shipping nonsense as if correct"); and it has no text/embedding-feature passthrough stash/reattach (`_predict_pre_pipeline.py:406-473`), so a per-model pre_pipeline that drops those columns silently narrows the serving frame relative to what the model was fit on.

### TRAINING_CORE_B-3 (P2) — 451-LOC dead-code duplicate of the live weight-iteration body

`_phase_train_one_target_weight_iteration.py` defines `_run_one_weight_iteration`, whose docstring says it is "one call = one pass of the innermost loop inside `_train_one_target`" — but grepping the entire `src/` tree for `_run_one_weight_iteration` turns up exactly one hit: its own definition. `_phase_train_one_target_body.py` carries its own separate, inline copy of the identical logic (same variable names, same comments, same control flow) directly in its nested loop rather than calling this extracted function. This is evidently an abandoned monolith-split: the function was carved out (presumably to shrink `_phase_train_one_target_body.py`) but the parent's loop body was never switched over to call it, leaving both copies live in source, only one of them reachable. A prior audit (`audits/full_audit_2026-07-21/training_core_a.md`, proposal PR1) describes this function as "the innermost per-(model, weight-schema) iteration ... already exercised indirectly via full-suite integration/e2e tests" — which is not accurate for the current codebase state, since the function is unreachable from any entry point; the earlier auditor evidently did not verify call sites. Confirmed by grepping `select:` style symbol search returned only the definition file plus this cluster's own test file's docstring mentioning it and the prior audit report. Because it is presently a byte-for-byte duplicate, it independently reproduces TRAINING_CORE_B-1's bug at its own lines 387-437 (`break_model_loop=True` returned before `_build_and_record_model_schema`/`pipeline_cache.set` run) — meaning if anyone wires this function in later trusting the "already exercised" claim, the bug ships a second time, and future maintainers fixing the live inline copy have no reason to know a stale duplicate exists to fix too.

### TRAINING_CORE_B-4 (P3) — comment style: wave/iter/date-stamp process metadata baked into code comments

CLAUDE.md's "Comment style" section is explicit and marked CRITICAL: "No process/audit metadata in code comments: no phase/wave markers, finding IDs, date stamps, fuzz-seed refs, refactor-history narration ... banner separators — that belongs in git history / the PR description." Nearly every file in this cluster violates this convention pre-existingly, e.g. `_phase_helpers_fit_split.py`'s module docstring opens with "Wave 105 (2026-05-21): split out from `training/core/_phase_helpers.py` ..."; `_phase_train_one_target.py:27-32` narrates a specific incident ("2026-05-21: wave-105 split-out forgot to mirror the parent's imports..."); `_setup_helpers_pipeline_cache.py` cites `iter193 (2026-05-23)` and `iter275 (2026-05-23)` inline; `_predict_main_from_models.py`'s module docstring cites "the 2026-05-22 sub-split". This is a systemic, repo-wide pattern rather than something introduced by recent edits in this cluster specifically, so it is reported once here (representative examples cited) rather than as dozens of near-identical rows, consistent with the instruction not to pad the finding count — but every P3 in this class is real and will need the dedicated cleanup pass the fix-everything wave is expected to run, since the project's own standard explicitly calls this out.

Sample_weight threading was traced through the recurrent path (`_phase_recurrent.py`) and the cross-target ensemble rerun (`_phase_train_one_target_ensembling.py`) and found correctly wired (with graceful signature-mismatch fallback + WARN). No new gaps found beyond TRAINING_CORE_B-1/2.
3. **Computational efficiency**: no new inefficiencies found in this cluster; the files are already heavily perf-tuned (batched Arrow bridges, id-keyed memoization, LRU caches with byte budgets) per the extensive prior optimization history visible in code comments. No unnecessary `.copy()`/materialization found beyond what's already justified by comments (e.g. the documented isolation-copy of `common_params` per weight iteration, which is required for correctness, not accidental).
4. **Edge cases and robustness**: spot-checked empty/degenerate inputs across `tune_decision_threshold`, `_group_local_volatility`, `_apply_purge_embargo`/`_apply_val_test_embargo`, and outlier-detection min-keep guards — all handle the degenerate case (empty, single-class, near-total-rejection) explicitly with a documented fallback or a loud raise. 5. **Test coverage gaps**: TRAINING_CORE_B-1, TRAINING_CORE_B-2, and TRAINING_CORE_B-3 are all, in part, test-coverage findings (missing regression/parity tests that would have caught each). No behavioral-tests-against-own-output anti-pattern found in this cluster (this cluster is orchestration code, not metric/kernel code, so this anti-pattern is less applicable here).
